# GitOps and Kubernetes: Continuous Deployment with Argo CD, Jenkins X, and Flux
**Authors:** Billy Yuen, Alex Matyushentsev, Jesse Suen, Todd Ekenstam
**Domain:** DevOps & Delivery — GitOps Practice and Tooling

## Core Concepts

- **The Four GitOps Principles (Ch. 1–2).** GitOps is defined by four properties, not a tool choice: (1) **Declarative** — the entire desired state of the system is expressed as declarations, not procedural scripts; (2) **Versioned and Immutable** — the declared state is stored in a version-control system in a way that enforces immutability of historical versions and provides a complete audit trail; (3) **Pulled Automatically** — approved changes to the desired state are automatically applied to the system by software agents; (4) **Continuously Reconciled** — software agents continuously observe the actual state and reconcile it with the desired state. A pipeline that pushes `kubectl apply` on merge is *not* GitOps by this definition — it satisfies declarative and versioned, but not pulled and continuously reconciled.
- **Argo CD: Application CRD as the GitOps Unit (Ch. 4–6).** Argo CD's central abstraction is the `Application` Custom Resource, which binds a source (a Git repository path or Helm chart reference) to a destination (a Kubernetes cluster + namespace) and a sync policy. Sync policies are either manual (a human triggers sync in the UI or via CLI) or automated (Argo CD syncs on every source commit, with optional self-healing to revert manual cluster edits). Argo CD's health assessment layer goes beyond Kubernetes resource Ready/Available conditions to application-semantic health — it can assess whether a Deployment is truly healthy based on its pods' restarts, an Ingress that has no backends, or a custom resource that reports its own health.
- **Flux: Source Controller + Kustomization + HelmRelease (Ch. 7–9).** Flux's architecture decomposes reconciliation into separate controllers with explicit CRDs: `GitRepository` (polls a Git repo, fetches a commit, makes it available to other controllers), `Kustomization` (applies a Kustomize-processed directory from a `GitRepository` source), and `HelmRelease` (renders a Helm chart with given values from a `HelmRepository` or `GitRepository` source). This composability means Flux can reconcile raw manifests, Kustomize overlays, and Helm charts from the same or different repositories — mixing them within a single environment. Flux uses the Kubernetes API server's watch mechanism rather than polling intervals wherever possible, reducing reconciliation latency.
- **App of Apps Pattern (Ch. 5, Argo CD).** Instead of deploying individual application manifests from a single monolithic Git path, a root `Application` CRD points to a directory whose only contents are more `Application` CRDs — the "app of apps." This lets environment-level configuration (which version of each service runs in this environment) live as code in one repository, while each service's Kubernetes manifests live in its own repository. The root Application bootstraps the entire environment from a single commit; tearing down or cloning an environment is a Git operation, not an imperative sequence of tool invocations.
- **Sealed Secrets and SOPS for Secrets in GitOps (Ch. 3, and scattered throughout).** The Git-as-source-of-truth principle creates a secrets problem: secrets cannot go into Git as plaintext. Two patterns dominate: **Sealed Secrets** (a controller runs in the cluster; `kubeseal` encrypts a Secret against the cluster's public key; only the in-cluster controller can decrypt; the encrypted `SealedSecret` resource is safe to commit); **SOPS** (Mozilla SOPS encrypts specific keys within a YAML or JSON file using an external key provider — AWS KMS, GCP KMS, age — and commits the encrypted file; Flux's kustomize-controller has native SOPS support). Both keep secrets under the same Git review workflow as manifests; the tradeoff is key management (SOPS externalizes it; Sealed Secrets internalizes it at the cost of cluster dependency for re-encryption on key rotation).
- **Argo Rollouts: Progressive Delivery as a GitOps-Native CRD (Ch. 10).** Argo Rollouts extends Kubernetes with a `Rollout` CRD that replaces `Deployment` for services requiring progressive delivery. A `Rollout` spec includes an explicit traffic-split strategy (canary with weighted steps and pause conditions, or blue-green with pre/post-promotion analysis runs), integration with `AnalysisTemplate` CRDs that query Prometheus/Datadog/Web metrics and pass/fail the rollout based on results, and webhooks for notification. This makes canary promotion criteria declarative and versioned in Git rather than imperatively scripted in a pipeline step.
- **Multi-Cluster Management (Ch. 11–12).** Both Argo CD and Flux support multi-cluster topologies — one "hub" cluster runs the GitOps controller and manages one or more "spoke" clusters via their API servers (Argo CD) or pushes resources to spoke clusters via a fleet controller (Flux's `Cluster` CRD in the multicluster extension). For this repo's per-tenant physical isolation model, the relevant pattern is: a single management plane (one Argo CD or Flux installation) maintains App-of-Apps or Kustomization resources for each tenant's cluster, so adding a new tenant is adding a new directory to the environment repo and applying a root CRD — not installing and configuring a new GitOps agent.
- **Preview Environments via Jenkins X (Ch. 13–14).** Jenkins X (the third tool covered) automates the creation of ephemeral preview environments for every pull request: a separate namespace (or cluster, for strict isolation) is provisioned with the PR's image, a bot posts the environment URL to the PR, and the environment is torn down on PR close. The namespace stamping integrates with `helm-chart`-style promotion: the same chart is installed into the preview namespace with PR-specific values. Jenkins X's implementation is more opinionated than Argo CD or Flux and assumes a specific monorepo or multi-repo layout; the *principle* (PR-level environments as a first-class GitOps object) is the transferable idea.

## Actionable Techniques

- Express every environment's desired state as a directory in an environment repository whose tree maps 1:1 to clusters/namespaces; the GitOps agent's source is a path in that tree, not a script or a pipeline stage.
- When choosing between Argo CD and Flux: use Argo CD when a UI-visible Application inventory and per-application sync status matters (multi-team, multiple applications, humans need a dashboard); use Flux when composability of CRD controllers and Kubernetes-native tooling integration matters more (SRE-mode, operator-heavy, no UI required).
- Use the App of Apps pattern for any environment with more than two services — the root Application (or Flux Kustomization pointing to a directory of CRDs) becomes the single commit that stamps or tears down the entire environment.
- Adopt SOPS over Sealed Secrets when the cluster is replaceable (tenant stamp, ephemeral preview) — Sealed Secrets couples decryption to a specific cluster's private key, which makes cross-cluster migration or cluster recreation a decryption-key management problem. SOPS with a cloud KMS key decouples decryption from cluster identity.
- Use Argo Rollouts `AnalysisTemplate` with Prometheus-sourced success rate metrics as the automated gate for canary promotions — the analysis outcome is versioned in Git alongside the rollout spec; a failed analysis creates a Git-observable event (the rollout status), not just a CI log artifact.
- Implement drift detection as an alert rather than a tolerance: any detected diff between actual cluster state and Git-declared state that persists beyond the reconciliation interval is an incident (`alerting-rules-design`'s drift alert) — not a background condition.

## Key Terminology

Worth adding to `skills/glossary-management/`'s Ubiquitous Language:

- **GitOps Reconciliation Loop** — the continuous control loop by which a GitOps agent compares desired state (Git) to actual state (cluster) and applies changes to close any gap; the architectural primitive that makes `cd-pipeline`'s drift-is-an-incident policy enforceable.
- **App of Apps** — a GitOps pattern where a root Application/Kustomization manages child Application/Kustomization CRDs, making an entire environment a single Git-committable object.
- **Sealed Secrets** — a Kubernetes controller + `SealedSecret` CRD that encrypts Secret data against a cluster-held private key, making encrypted secrets safe to store in Git.
- **SOPS** — Mozilla Secrets OPerationS; a tool that encrypts specific keys in YAML/JSON files using external KMS or age keys; Flux-native integration makes it the preferred GitOps secrets approach when the cluster is ephemeral.
- **AnalysisTemplate** — an Argo Rollouts CRD that defines a Prometheus/metric query and pass/fail threshold; attached to a `Rollout` to automate promotion and rollback decisions based on real traffic metrics.
- **Preview Environment** — an ephemeral, per-pull-request environment stamped from the same GitOps machinery as production, giving each PR a live URL for review and integration testing before merge.

## Caveats

- **The book covers three separate tools (Argo CD, Jenkins X, Flux) at a level of detail that dates quickly.** CRD field names, CLI flags, and operator versions change across minor releases; treat the book's specific YAML examples as illustrative patterns, not copy-paste production configuration — always check the current tool documentation for field-level accuracy.
- **Jenkins X is less widely adopted than Argo CD or Flux (as of mid-2026).** Its preview-environment mechanics are the book's most distinctive contribution; the broader Jenkins X opinions on Git repository layout and pipeline structure are less transferable and should not be introduced as standards unless a deliberate Jenkins X adoption decision is made. The preview environment *principle* is transferable regardless of implementation.
- **GitOps and Kubernetes assumes Kubernetes as the only runtime.** This is correct for this repo's platform stack, but the four GitOps principles are runtime-agnostic — they apply equally well to `opentofu-module`'s infrastructure as to `kubernetes-manifest`'s workloads. The book doesn't explore this generalization; see `opentofu-module`'s own remote-state and OPA-gated plan-before-apply as an independent GitOps-style application to infrastructure.
- **Multi-cluster management with a single control plane introduces a blast-radius concern.** A bug in the management plane (or a compromised environment repo commit) can propagate across all tenant clusters simultaneously. This repo's per-tenant physical isolation model (`multi-tenancy-design`) is the reason to run one GitOps agent per tenant cluster rather than one centralized agent, unless the hub/spoke model includes per-tenant App-of-Apps roots with independent RBAC.
