# Cloud Native DevOps with Kubernetes
**Authors:** John Arundel, Justin Domingus
**Domain:** DevOps & Delivery — Cloud Native Operations Practice

## Core Concepts

- **Kubernetes Is the New Operating System (Ch. 1–2).** The book's central framing: just as Linux is the OS for servers, Kubernetes is the OS for distributed systems. Applications declare their requirements (resources, health signals, dependencies) and the platform satisfies them — scheduling, auto-healing, scaling, networking. The developer's job is to build a 12-factor application that honours the Kubernetes contract; the platform engineer's job is to configure Kubernetes correctly so those declarations are acted on. The book is explicitly practitioner-oriented: it is a guide to operating Kubernetes for real services, not a theory text.
- **Container-First Development and Local Kubernetes (Ch. 2–4).** The book insists on running the same container image locally that will run in production — not a "dev mode" image or a locally-installed binary. It covers `kind` (Kubernetes IN Docker) as the preferred local cluster tool: a real, multi-node Kubernetes cluster running inside Docker containers on the developer's laptop, behaving identically to a cloud cluster. The local cluster runs the same Helm charts and manifests as staging; environment parity starts at the developer's workstation, not just at CI.
- **Resource Requests, Limits, and the Kubernetes Scheduler (Ch. 5).** The book gives the most practical and detailed treatment of resource management of any source: `requests` are the scheduler's signal (if no node has this much free capacity, the pod is unschedulable — it stays Pending forever, not killed); `limits` are the enforcement ceiling (CPU: throttled on breach, never killed; memory: OOMKilled on breach). The advice on limit setting: set memory limits tightly (close to actual peak, because OOM is a fast, observable failure); set CPU limits loosely or not at all for latency-sensitive services (CPU throttling is silent and produces latency jitter that is hard to diagnose, worse than a clear OOM). The book explicitly warns against setting memory limits too high (waste) and CPU limits too close to requests (latency pathology).
- **Twelve-Factor Applications as the Kubernetes Contract (Ch. 4).** The 12-factor methodology (Heroku-originated, applied here to Kubernetes) maps directly to Kubernetes primitives: configuration from environment variables (`ConfigMap`/`Secret` env var projection), stateless processes (enables horizontal scaling), backing services as attached resources (database URL as an env var, not hardcoded), logs as streams (stdout → Kubernetes logging pipeline), admin processes as one-off containers (`Job` or `kubectl exec` for migrations). The book treats 12-factor not as a style guide but as the compliance surface between an application and the scheduler.
- **Kubernetes Networking: Services, Ingress, and DNS (Ch. 9–10).** The book covers the full networking stack: `ClusterIP` for in-cluster service discovery via DNS (`<service>.<namespace>.svc.cluster.local`), `NodePort` and `LoadBalancer` for external access (cloud-specific; costs money per LB), `Ingress` for HTTP routing with TLS termination, and `NetworkPolicy` for east-west traffic restriction. The practical advice: use `ClusterIP` + `Ingress` as the default; use `LoadBalancer` only when a dedicated external IP is genuinely needed (e.g., a TLS-terminating ingress controller's own service). `NodePort` is a debugging tool, not a production pattern.
- **Continuous Delivery on Kubernetes (Ch. 14).** The book's CD chapter describes a push-based GitOps-adjacent model (deploy via `helm upgrade` in CI), but also covers the pull-based model (Flux, Argo CD). Its practical contribution: the **deploy-then-verify** pattern — after every Helm upgrade, the pipeline runs a health check (kubectl rollout status, a smoke test against the service URL, an SLO burn rate check) before declaring the deploy successful. A deploy that passes `helm upgrade` but fails the post-deploy verification rolls back automatically via `helm rollback`. This pattern is tool-agnostic; it applies whether CI pushes or a GitOps agent pulls.
- **Observability: Metrics, Logging, and Tracing (Ch. 15–17).** The book treats observability as three distinct signals, each with a different answer strategy on Kubernetes. Metrics: Prometheus scrapes Kubernetes-native metrics (cadvisor, kube-state-metrics) plus application `/metrics` endpoints; Grafana visualises. Logging: containers write to stdout; a DaemonSet agent (Fluent Bit) ships to a central store (Elasticsearch, Loki). Tracing: OpenTelemetry SDKs propagate trace context; a Jaeger or Tempo backend stores and queries. The book is unusual in explicitly stating that all three are necessary and that none replaces the others — high cardinality events are traces; aggregated rates are metrics; human-readable context is logs.
- **Security: RBAC, Pod Security, and Secrets (Ch. 18–20).** The book's security chapters align closely with this repo's existing posture: one ServiceAccount per service (not the default ServiceAccount), RBAC verbs scoped to the minimum needed, security context with non-root UID, read-only root filesystem where possible, `allowPrivilegeEscalation: false`. The secret management chapter covers the same vulnerability this repo addresses — `Secret` objects are base64-encoded, not encrypted at rest by default — and recommends the same class of solution (KMS-backed envelope encryption for etcd, or external secret operator for runtime injection).

## Actionable Techniques

- Run the exact same container image locally that CI will build — use `kind` (or `minikube`) to run a real Kubernetes cluster locally; avoid per-developer "docker-compose" environments that behave differently from the cluster the image will actually run on.
- Set memory limits tight (within 20% of observed peak usage) and leave CPU limits absent or very loose for latency-sensitive services — CPU throttling at the limit is silent and produces hard-to-diagnose latency spikes, while memory OOM is observable and fast.
- After every Helm upgrade (whether CI-pushed or GitOps-applied), run `kubectl rollout status deployment/<name> --timeout=120s` followed by an HTTP smoke test against the service's health endpoint before declaring the deploy complete; if either fails, `helm rollback` immediately.
- Use one `ServiceAccount` per service with the minimum RBAC verbs needed; never use the `default` ServiceAccount; never bind a `ClusterRole` when a namespace-scoped `Role` will do.
- Write all logs to stdout as structured JSON from day one — retrofitting log structure onto a service after it is in production is significantly harder than designing for it during `go-project-structure`.
- Use `kubectl top pods` and `kubectl describe node` weekly during the initial deployment of a new service to calibrate resource requests to actual observed usage, then lock the requests into the `values.yaml`; do not leave requests at defaults.

## Key Terminology

Worth adding to `skills/glossary-management/`'s Ubiquitous Language:

- **kind (Kubernetes IN Docker)** — a tool for running multi-node Kubernetes clusters inside Docker containers; used for local development and CI testing environments that must behave identically to a cloud cluster.
- **Twelve-Factor Application** — a methodology for building cloud-native applications that explicitly comply with the Kubernetes scheduling contract: config from env vars, logs to stdout, stateless processes, backing services as attached resources.
- **CPU Throttling** — the Kubernetes mechanism that enforces CPU limits by throttling (slowing) a container without killing it; distinct from memory OOM killing; produces silent latency degradation rather than an observable crash.
- **Deploy-then-Verify** — the post-deploy verification pattern: after every Helm upgrade or GitOps reconciliation, a scripted health check confirms the new version is serving traffic before the deploy is declared complete; on failure, automatic rollback fires.

## Caveats

- **The book's second edition (2022) covers Kubernetes 1.23; several APIs have changed since.** `PodSecurityPolicy` (deprecated in 1.21, removed in 1.25) is referenced in the security chapters; its replacement (`Pod Security Admission` with labeled namespace modes) is the current control. Check chapter 19's security guidance against the current Kubernetes version's actual API before copying patterns into `kubernetes-manifest`.
- **The book is cloud-agnostic (EKS, GKE, AKS examples throughout) but this repo defaults to on-cluster (kind-local) and self-managed clusters.** The `LoadBalancer` service type discussion assumes a cloud provider's LB controller; this repo's ingress pattern uses Kubernetes-native Ingress + a controller (Nginx or Traefik), not cloud LBs — the book's cloud-LB examples are not directly applicable but the Ingress pattern it describes is.
- **The Prometheus/Grafana/ELK observability stack the book covers maps closely to this repo's OpenTelemetry + Prometheus + Tempo + Grafana stack, with Loki as the preferred log aggregator over Elasticsearch.** Treat the book's observability chapters as confirming the direction rather than specifying tooling — this repo's own `opentelemetry-instrumentation`, `prometheus-metrics-design`, and `distributed-tracing-design` skills own the specific instrumentation choices.
