# Kubernetes Patterns: Reusable Elements for Designing Cloud-Native Applications
**Authors:** Bilgin Ibryam, Roland Huß
**Domain:** DevOps & Delivery — Kubernetes Workload Design Patterns

## Core Concepts

- **Pattern Language for Kubernetes Workloads (Preface, Ch. 1).** The book adapts the Gang of Four pattern language to Kubernetes: each pattern names a recurring problem in cloud-native application design, gives it a canonical solution, and names the specific Kubernetes primitives that implement it. The organizing principle is that applications and the platform they run on have a *contract* — the application signals its operational state (probes, resource requests, graceful shutdown signals), and the platform uses those signals to make scheduling, routing, and restart decisions. Patterns are the vocabulary of that contract.
- **Foundational Patterns — The Platform Contract (Part I, Ch. 2–6).** Four patterns define the minimum viable contract every workload must honour: (1) **Predictable Demands** — a container declares its resource requests (what it needs to be scheduled) and limits (what it is allowed to use), so the scheduler can bin-pack correctly and the OOM killer doesn't fire arbitrarily; (2) **Declarative Deployment** — `Deployment` rollout strategy (`RollingUpdate` parameters: `maxSurge`, `maxUnavailable`) declaratively governs how the scheduler replaces pods; (3) **Health Probe** — three distinct probes (`livenessProbe`, `readinessProbe`, `startupProbe`) each answer a different question (is this container worth restarting? is this pod ready to receive traffic? has the container finished starting?); (4) **Managed Lifecycle** — the container handles `SIGTERM` gracefully and the pod spec sets `terminationGracePeriodSeconds` to match, so in-flight requests drain before eviction.
- **Structural Patterns — Multi-Container Pod Composition (Part II, Ch. 7–12).** Five patterns extend a single-container pod into a multi-container cooperation: (1) **Init Container** — one or more containers that run to completion before any app container starts; use cases include pulling secrets from Vault, running database migrations, pre-populating a cache volume, or waiting for a dependency to become available; (2) **Sidecar** — a second container in the same pod that enhances the main container's network or storage capabilities without the main container being aware of it (Linkerd's proxy, Envoy, Fluent Bit log forwarder, OTel Collector — all are sidecars); (3) **Adapter** — a sidecar that transforms the main container's output interface into a standard interface the platform expects (e.g., a container that reads a legacy log format and converts it to structured JSON for a log aggregator); (4) **Ambassador** — a sidecar that proxies outbound requests from the main container to an external service, handling retries, circuit breaking, and protocol translation; (5) **Multi-Container Pod** as a design decision criterion: containers belong in the same pod if and only if they share a lifecycle and cannot run independently — not because they are logically related.
- **Behavioral Patterns — Workload Scheduling and Lifecycle Types (Part III, Ch. 13–19).** Kubernetes has distinct workload controllers for distinct operational lifetimes: **Batch Job** (`Job`) for one-time, run-to-completion work; **Periodic Job** (`CronJob`) for scheduled, run-to-completion work; **Daemon Service** (`DaemonSet`) for one-pod-per-node infrastructure agents (log forwarders, monitoring agents, CNI plugins); **Singleton Service** (`StatefulSet` with 1 replica or leader-election) for services that must have exactly one active instance (schedulers, coordinators); **Stateful Service** (`StatefulSet`) for services with identity-stable storage (databases, message brokers, Zookeeper); **Service Discovery** (Kubernetes `Service` DNS conventions, headless services for `StatefulSet` per-pod DNS, ExternalDNS for external registration); **Elastic Scale** (`HorizontalPodAutoscaler`, `VerticalPodAutoscaler`, KEDA for event-driven scaling beyond CPU/memory).
- **Configuration Patterns — How Configuration Reaches Containers (Part IV, Ch. 20–23).** Four patterns govern the configuration contract: (1) **EnvVar Configuration** — environment variables for simple key-value configuration that is container-scoped, process-visible, and immutable after pod start; (2) **Immutable Configuration** — a `ConfigMap` or `Secret` backed by a Git-committed source, mounted as a volume or consumed as an env var, whose changes trigger a pod rollout rather than a live update; (3) **Projected Volume** — a single volume mount that combines a `ConfigMap`, `Secret`, `serviceAccountToken`, and `downwardAPI` into one filesystem path, reducing the number of volume mounts and their associated RBAC grants; (4) **Configuration Template** — an Init Container that reads a template plus a `ConfigMap` of substitution values and writes the final config file to a shared volume, enabling configuration rendering that is too complex for environment variable substitution but doesn't justify a sidecar.
- **Advanced Patterns — Extending Kubernetes (Part V, Ch. 24–28).** Three patterns extend Kubernetes itself: (1) **Controller** — a reconciliation loop that watches a Kubernetes resource (standard or custom) and drives actual state toward desired state by making Kubernetes API calls; (2) **Operator** — a Controller paired with one or more Custom Resource Definitions (CRDs) that encode domain-specific operational knowledge as automation (an Argo CD `Application` controller, a Postgres Operator, a Prometheus Operator are all Operators); (3) **Elastic Scale** via KEDA (Kubernetes Event-Driven Autoscaler) — scales a `Deployment` or `Job` based on external metrics beyond CPU/memory: queue depth, Kafka consumer lag, Redpanda consumer group lag, cron schedule, HTTP request rate.
- **Self Awareness — Downward API (Ch. 6).** Containers that need to know their own pod name, namespace, node name, resource limits, or labels at runtime use the **Downward API** — a Kubernetes mechanism that projects these facts into environment variables or a volume file at pod start. The canonical use: a service that includes its own pod name and namespace in every log line, without calling the Kubernetes API, because the Downward API injects those values before the container's entrypoint runs.

## Actionable Techniques

- Every new Kubernetes workload starts from a checklist of the four Foundational Patterns: resource requests/limits set (Predictable Demands), rollout strategy configured (Declarative Deployment), all three probes wired to real endpoints (Health Probe), SIGTERM handler implemented and `terminationGracePeriodSeconds` set (Managed Lifecycle). Absent any of these four, the workload is not platform-conformant.
- Use Init Containers for any one-time per-pod setup that must complete before the main container starts: pulling a Vault secret into a shared volume, running `go-migration`'s migrate command, or waiting for a dependency's health endpoint to respond — not a shell hack in the main container's entrypoint.
- Use a DaemonSet for any platform-infrastructure agent (OTel Collector, Fluent Bit, node exporter) that must run on every node — not a Deployment with high replica count, because a Deployment does not guarantee one-replica-per-node.
- Use KEDA's Redpanda/Kafka scaler for any consumer service (`go-event-consumer`) that should scale to zero when its consumer group has zero lag and scale up proportionally to lag — CPU-based HPA will not detect a backlog that hasn't yet started processing.
- When a `StatefulSet` service needs per-pod DNS-resolvable hostnames (Redpanda brokers, Zookeeper nodes), use a headless `Service` (ClusterIP: None) — pods get `<pod-name>.<service-name>.<namespace>.svc.cluster.local` automatically, without requiring a separate DNS registration step.
- Avoid putting two services into the same pod because they are "related" — they must share a lifecycle (one cannot run without the other) and be unable to operate independently. Loose coupling via the Service Discovery pattern almost always belongs to separate pods on separate `Service` resources.

## Key Terminology

Worth adding to `skills/glossary-management/`'s Ubiquitous Language:

- **Init Container** — a container that runs to completion before any app container in a pod starts; used for setup work that must precede the main workload (schema migration, secret retrieval, dependency wait).
- **Sidecar** — a container co-located in the same pod as the main application container, enhancing it with network, storage, or observability capabilities without modifying the main container.
- **DaemonSet** — a Kubernetes workload controller that schedules exactly one pod per node (or per selected node subset); the correct controller for node-scoped infrastructure agents.
- **Operator** — a Kubernetes controller paired with one or more Custom Resource Definitions that encodes domain-specific operational knowledge as automated reconciliation; the mechanism by which complex stateful systems (databases, message brokers) are managed declaratively.
- **KEDA (Kubernetes Event-Driven Autoscaler)** — a Kubernetes add-on that extends HorizontalPodAutoscaler to scale workloads based on external event sources (queue depth, consumer group lag, cron) rather than only CPU/memory utilisation.
- **Predictable Demands** — the Kubernetes pattern requiring every container to declare resource requests (scheduling signal) and limits (enforcement ceiling); absence of resource requests makes the scheduler unable to bin-pack and enables resource starvation.
- **Managed Lifecycle** — the Kubernetes pattern requiring containers to handle SIGTERM gracefully, with `terminationGracePeriodSeconds` ≥ the application's drain timeout, so in-flight requests complete before pod eviction.

## Caveats

- **The book's second edition (2023) is the authoritative version.** The first edition (2019) pre-dates several patterns (KEDA, Argo Rollouts, full Sidecar formalisation in the beta Sidecar container API). Cite the second edition for the Configuration Template and multi-container Sidecar patterns — the first edition's Sidecar relies on init-container-as-sidecar hacks that the second edition supersedes.
- **Kubernetes 1.29+ has native Sidecar Container support (KEP-753).** The book's second edition covers this: a container declared with `initContainers` and `restartPolicy: Always` is treated by Kubernetes as a native sidecar (starts first, doesn't block pod readiness on its own readiness, stays running while app containers run). This supersedes the hack of using a long-running Init Container; update `kubernetes-manifest` to reflect the native API when cluster version ≥ 1.29.
- **The Operator pattern is expensive to build correctly.** Writing a production-quality Operator requires understanding the Kubernetes reconciliation model, controller-runtime, event queue mechanics, and status subresource design — a non-trivial engineering investment. The pattern is worth it when the operational domain is genuinely complex and an existing, well-maintained Operator does not exist; not as a default for any service with custom resources.
- **KEDA requires its own installation on the cluster.** It is not part of core Kubernetes; it is a CNCF project that installs via a Helm chart and adds CRDs. Including it in `kubernetes-manifest`'s or `helm-chart`'s standards requires a deliberate `opentofu-module` provisioning decision, not just a YAML pattern.
