# Concourse CI: The Cloud Native CI/CD System
**Source:** Official Concourse Documentation (concourse-ci.org), community-authored guides, and pipeline examples
**Domain:** DevOps & Delivery — CI/CD Tooling (Alternative to GitHub Actions)

> **Source note:** This file synthesises the official Concourse documentation (concourse-ci.org/docs), the Concourse Tutorials (Stark & Wayne), community blog posts, and reference pipeline examples. Concourse does not have a single canonical book; this file is grounded in the authoritative official docs and widely-cited community practice rather than a single text. Claims are attributed to the Concourse documentation section that defines them, not to community opinion.

## Core Concepts

- **Four Primitives: Tasks, Resources, Jobs, and Pipelines (Concourse Docs: Concepts).** Concourse's entire model is built from four things: (1) **Tasks** — the unit of computation: a container image, a set of inputs (directories), a set of outputs (directories), and a script to run inside the container; tasks are stateless, disposable, and reproducible; (2) **Resources** — the unit of versioned external state: a Git repository, a Docker image, an S3 bucket, a GitHub release, a time trigger; resources implement a three-step interface (`check` for new versions, `get` to fetch a version, `put` to publish a version); (3) **Jobs** — a sequence or graph of `get`, `put`, and `task` steps with explicit dependency wiring; (4) **Pipelines** — a named collection of resources and jobs, declaratively configured in YAML, stateless except for the resource versions it tracks.
- **Everything Runs in Containers — No Shared State (Concourse Docs: Architecture).** Every task runs in a fresh container, launched from the image specified in the task config. There is no shared filesystem between tasks except through explicitly declared input/output bindings. The worker machine is not a build agent in the Jenkins/CircleCI sense — it is a container host; no tool installation is shared between tasks or between builds. If a task needs Go, it uses a Go image; if a task needs Helm, it uses a Helm image. This makes Concourse tasks inherently reproducible: the same task definition run on any worker produces the same result because the container image is the environment.
- **Resources Define the Interface with the Outside World (Concourse Docs: Resources).** A resource type is a Docker image that implements three scripts: `/opt/resource/check` (emit JSON array of new versions since the last-seen version), `/opt/resource/in` (fetch a specific version into a directory), `/opt/resource/out` (push a version from a directory to the external system). The built-in resource types cover the common cases: `git` (Git repository), `docker-image` (Docker Hub/registry image), `s3` (S3-compatible object), `time` (cron-style time trigger), `github-release` (GitHub release assets). Custom resource types extend the model to any external system — a Redpanda topic, a Kubernetes resource version, a Vault secret — by publishing a Docker image implementing the three scripts.
- **Dependency Graph, Not a Script (Concourse Docs: Jobs, Dependencies).** A Concourse job's steps are a graph of `get` (resource fetch, marks the resource as "passed through this job"), `put` (resource push), and `task` steps connected by `passed:` constraints. A `get` step with `passed: [unit-tests]` only runs if the fetched version of that resource has passed through the named job — this is the mechanism for pipeline ordering: the acceptance-test job only runs on a commit that has already passed unit-tests, without any explicit step in the unit-test job to trigger the next job. Concourse calls this "fan-in/fan-out" — multiple jobs can pass through the same resource version, and a downstream job waits for all of them.
- **No Shared Mutable State — Pipelines Are Stateless (Concourse Docs: State Model).** Concourse workers have no persistent build directories, no `~/.gradle` caches across builds (unless a resource explicitly restores one), and no artifacts stored on the worker. All persistence is through resources: an artifact cache is an S3 resource with a version; a build output is a Docker image resource; a test report is an S3 resource. This discipline eliminates the "works on my worker" problem (a build that passed on worker A because it shared state with a previous build but fails on worker B from a clean start) — but it means every build that needs a warm cache must explicitly `get` a cache resource at the start and `put` it at the end.
- **Teams, RBAC, and the Fly CLI (Concourse Docs: Auth, Fly).** Concourse organises pipelines into teams; each team has its own RBAC (pipeline viewer, member, operator, owner). The `fly` CLI is the primary interface: `fly -t <target> set-pipeline` loads a YAML pipeline definition into the Concourse server; `fly -t <target> trigger-job` runs a job manually; `fly -t <target> watch` streams build output. There is no web UI pipeline editor — pipelines are always set from a file, making them inherently version-controllable. The `fly` CLI also allows `fly execute` — running a single task locally against a worker without defining a full pipeline, useful for developing and debugging individual task containers.
- **The Time Resource for Scheduled Builds (Concourse Docs: time resource).** Concourse has no built-in cron scheduler per se; instead, the `time` resource emits a new version on a configured interval (e.g., every 24 hours between 08:00 and 09:00 UTC). A job that `get`s the time resource with `trigger: true` runs whenever the time resource emits — this is the mechanism for nightly builds, weekly security scans, and other schedule-driven tasks. The time resource's start/stop window prevents the build from firing at exactly the same second across all pipelines in a team (natural jitter).
- **Across Step for Matrix Builds (Concourse Docs: across step, experimental).** The `across` step allows a task or set of steps to run once for each value in a variable set — a matrix build. A pipeline that tests against Go 1.22, 1.23, and 1.24 uses `across` to parameterize the Go image version without duplicating job definitions. As of the official docs, `across` is marked experimental; its behaviour is correct for simple matrix cases but has edge-case limitations with resource versioning.

## Actionable Techniques

- Model every external dependency as a Concourse resource (Git repo, image registry, S3 bucket, time trigger) rather than as a shell script that `curl`s or `git clone`s inside a task — the resource model gives Concourse version-tracking, fan-in dependency resolution, and a visual dependency graph in the UI for free.
- Cache expensive operations (Go module downloads, npm installs) by `get`-ting an S3 cache resource at the start of a job and `put`-ting the updated cache at the end; version the cache by `go.sum` or `package-lock.json` hash so a dependency change invalidates it automatically.
- Write each task as a standalone, locally-runnable shell script in the repository under `ci/tasks/` — then reference it from the pipeline YAML via `file: ci/tasks/<name>.sh`; this makes tasks testable with `fly execute` without running the full pipeline.
- Use the `passed:` constraint instead of explicit inter-job triggers — a job that `get`s a git resource with `passed: [unit-tests]` automatically runs only on commits that have cleared unit tests, without any manual trigger configuration in the upstream job.
- Treat the `fly set-pipeline` command the same way this repo treats `helm upgrade`: run it from CI (a dedicated Concourse job that applies pipeline changes) or from a version-controlled script — never apply pipeline changes ad hoc from a developer's local `fly` session in production contexts.
- Pin base images in task configs by digest (`image: golang@sha256:<digest>`) rather than by tag — Concourse tasks that reference a mutable tag (`:latest`, `:1.23`) are not reproducible across rebuilds when the tag moves.

## Key Terminology

- **Concourse Resource** — an entity that implements check/get/put against a versioned external system; the mechanism by which Concourse tracks versions and triggers jobs.
- **Concourse Task** — a containerized, stateless unit of computation with declared inputs and outputs; the only place work actually happens in a Concourse pipeline.
- **Fly CLI** — the command-line interface for interacting with a Concourse server; the only way to set, update, or delete pipelines (no web UI editor).
- **Fan-in / Fan-out** — Concourse's dependency model: a resource version that must pass through multiple upstream jobs before a downstream job consumes it (fan-in); a resource version that triggers multiple parallel downstream jobs (fan-out).
- **Passed Constraint** — the `passed:` field on a `get` step that restricts the fetched version to one that has already passed through the named job(s); the mechanism for pipeline ordering without explicit inter-job triggers.

## Caveats

- **Concourse is not this repo's default CI system.** GitHub Actions is the default per `settings.json` and `sdlc-context.json`'s tech stack. This research file captures Concourse's model so the CI/CD skills can reference it accurately as an alternative, not as a recommendation to switch. If a product using this factory runs on Concourse, the platform-engineer can configure it; the factory does not promote Concourse over GitHub Actions.
- **Concourse's UI is intentionally minimal** — it shows pipeline dependency graphs and build status; it does not show pull request statuses, branch protection rule results, or repository-level insights. Teams that rely on GitHub's pull request checks UI for workflow will find Concourse's feedback loop different (build status visible in the Concourse web UI, not natively in GitHub PRs — requires a `github-status` resource for that integration).
- **The Concourse community is smaller than GitHub Actions' marketplace ecosystem.** Custom resource types exist for most common integrations but are often community-maintained with varying update cadence. Evaluate community resource types for production use the same way this repo evaluates any open-source dependency.
- **`across` step is experimental as of documentation last reviewed.** Do not use it for production matrix builds without first verifying its stability in the current Concourse version deployed; use separate job definitions for small matrices when `across` stability is uncertain.
