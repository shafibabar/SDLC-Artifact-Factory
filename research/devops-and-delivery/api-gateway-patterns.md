# API Gateway Patterns
**Authors:** Kong official docs (Gateway, Ingress Controller, Plugin Hub); Sam Newman, *Building Microservices* (2nd ed.); Alex Xu, *System Design Interview* — synthesis
**Domain:** DevOps & Delivery — Edge / North-South Traffic Management

> Source note: This file is a synthesis across Kong's product documentation and two well-known microservices/system-design texts, not a distillation of a single canonical book. The API-gateway *role* (routing, auth offload, rate limiting, edge observability) is stable and vendor-neutral; Kong specifics (plugin model, decK, DB-less mode, Kong Ingress Controller) are drawn from Kong's public docs. No version numbers, benchmarks, or quotes are invented; where a Kong feature is named it is a documented, long-standing capability, not a claim about a specific release.

## Core Concepts

- **The gateway is the single north-south entry point.** An API gateway is the one front door through which all *client-to-cluster* (north-south) traffic passes before it reaches any service. It collapses cross-cutting edge concerns — routing/dispatch to the right upstream, authentication and authorization *offload* (validate the JWT/API key once, at the edge, so downstream services trust an already-authenticated request), rate limiting and quota enforcement, request/response transformation, and edge observability (request logs, latency, status-code metrics) — into one policy-enforcement layer instead of duplicating them in every service. Newman frames this as the antidote to smearing edge logic across N services; Xu treats it as a standard tier in any at-scale system design.
- **Gateway (north-south) vs. service mesh (east-west) — complementary, not alternatives.** This is the single most-confused distinction and the most important one for this repo. A gateway governs traffic *entering* the cluster from outside; a service mesh (Linkerd here) governs *service-to-service* (east-west) traffic already *inside* the cluster — mTLS identity, retries, per-call telemetry between pods. They solve different planes: you do not pick one *or* the other, you run both. A request typically hits the gateway first (TLS termination, authn, rate limit), then travels the mesh (mTLS, retries) between services. Conflating them leads teams either to try to do edge auth in the mesh sidecar or to try to do inter-service mTLS in the gateway — both are category errors.
- **Kong's plugin model.** Kong's core is a thin reverse proxy; all behavior is plugins attached to a Route, Service, Consumer, or globally. The three families that matter: **auth** (key-auth, jwt, oauth2, OIDC — validate credentials and set the authenticated Consumer), **traffic control** (rate-limiting, request-size-limiting, proxy-cache), and **transformations** (request-transformer / response-transformer to add/strip/rename headers and reshape bodies). A plugin is a unit of edge policy that is configured, not coded — the gateway equivalent of "declare the behavior, don't reimplement it per service."
- **Declarative config and the Kong Ingress Controller (KIC).** On Kubernetes, Kong runs as an Ingress Controller: gateway config is expressed as Kubernetes resources (Ingress / Gateway API `HTTPRoute`, plus `KongPlugin`/`KongConsumer` CRDs) and reconciled from Git — the same GitOps model this repo already uses. Off-cluster, the same declarative state is managed with **decK** (diff/sync a YAML file of the whole config against a running Kong). Either way the gateway's entire routing-and-policy surface is a reviewed file in version control, not clicks in an admin UI.
- **DB-less mode.** Kong can run without its Postgres/Cassandra control-plane database, loading its full config from a declarative YAML file at boot (and via decK). DB-less is the natural fit for a GitOps, immutable-infrastructure shop: no stateful gateway datastore to back up or run per tenant, config is the manifest, and a gateway pod is disposable and reproducible. It removes an entire stateful dependency from the edge tier.
- **Gateway vs. BFF (Backend-for-Frontend).** A gateway is *generic* edge policy shared by all clients; a **BFF** is a *per-client-experience* service (one for the web app, one for mobile) that aggregates and reshapes multiple downstream calls into exactly what that one frontend needs. Newman's rule of thumb: put cross-cutting, client-agnostic concerns (authn, rate limit, TLS) in the gateway; put client-specific aggregation and payload shaping in a BFF behind it. Overloading the gateway with client-specific response shaping recreates a monolithic, hard-to-change edge — the anti-pattern of the "smart gateway."
- **Where the gateway sits relative to Ingress + mesh.** In a Kubernetes + Linkerd topology the gateway *is* the ingress: it terminates TLS, applies edge policy (authn, rate limit, transform), and only then hands traffic into the mesh — where Linkerd re-encrypts with mTLS and manages east-west calls. The gateway is the outermost trust-boundary crossing; the mesh is the internal identity fabric. Edge policy belongs at the gateway; service identity belongs in the mesh; neither substitutes for the other.

## Actionable Techniques

- **Draw the two planes explicitly on the Container Diagram.** Mark exactly one north-south arrow (client → gateway/ingress) and treat every in-cluster arrow as east-west (mesh). If an "edge" concern (authn, rate limit, TLS termination) appears on an east-west arrow, or an "internal" concern (inter-service mTLS, retries) appears on the north-south arrow, that is a misplacement to fix before shipping.
- **Offload authn at the edge, keep authz in the app.** Use a Kong auth plugin (jwt/OIDC) to *validate* the token and reject anonymous traffic at the gateway, then forward the verified claims (e.g., as trusted headers) downstream. Do **not** move ABAC/tenant authorization decisions into the gateway — those stay in application code (this repo's `access-control-model`/`zero-trust-design` position: the edge proves *who*, the app decides *what they may do*). The gateway thins the attack surface; it is not the authorization authority.
- **Rate-limit per Consumer, per tenant.** Model each tenant (or API key) as a Kong Consumer and attach a rate-limiting plugin scoped to it, so one tenant cannot exhaust shared edge capacity. With this repo's physical per-tenant isolation the gateway limit is a second, edge-layer quota complementing per-namespace resource limits — defense in depth at the front door.
- **Keep gateway config declarative and in Git.** Express routes and plugins as KIC CRDs (in-cluster) or a decK YAML (out-of-cluster) reconciled the same way Helm/OpenTofu state is. Run DB-less so a gateway pod carries no state a restore plan must cover. A new route or a changed rate limit is a reviewed PR diff, never a live admin-API mutation.
- **Reserve the gateway for client-agnostic policy; push client-shaping to a BFF.** When the React app needs a composed payload that stitches several services, build a small BFF service behind the gateway rather than encoding that aggregation as gateway response-transformer rules. Keep the gateway's plugin set small and generic.
- **Emit edge telemetry into the existing observability stack.** Turn on Kong's request logging/metrics and export to Prometheus (and traces to Tempo via OpenTelemetry) so edge latency, 4xx/5xx rates, and per-Consumer throughput land in the same Grafana the mesh and services already use — one pane, edge plus interior.

## Key Terminology

- **North-South traffic** — client-to-cluster traffic crossing the outer boundary; the gateway's domain. Contrast **East-West traffic** — service-to-service traffic inside the cluster; the mesh's (Linkerd's) domain. Worth adding to `glossary-management` since the two-plane distinction is the load-bearing concept and this repo's ubiquitous language already carries `Service Mesh`.
- **Authentication offload** — validating credentials once at the gateway so downstream services receive already-authenticated requests; distinct from **authorization**, which (per this repo's stance) stays in application code.
- **Backend-for-Frontend (BFF)** — a per-client-experience service that aggregates/reshapes downstream calls for one frontend; distinct from the client-agnostic gateway in front of it.
- **DB-less mode** — running Kong with no control-plane database, config loaded declaratively; the stateless-edge fit for GitOps.
- **Kong plugin / Consumer** — a plugin is a unit of edge policy attached to a Route/Service/Consumer/globally; a Consumer is the identity (API key, tenant) a plugin like rate-limiting is scoped to.

## Caveats

- **This is a docs-plus-books synthesis, not one canonical text.** The gateway *role* and the gateway-vs-mesh and gateway-vs-BFF distinctions are drawn from Newman and Xu (widely-cited, stable framings); the Kong specifics (plugin families, decK, KIC CRDs, DB-less) are from Kong's official documentation. Treat chapter-level attributions as absent by design — no single book grounds all of this.
- **Kong is one implementation, named because the issue named it.** The role generalizes to any gateway (Envoy/Contour, Traefik, NGINX Ingress, Gateway-API implementations). Nothing above commits this repo to Kong; if a lighter gateway meets the same edge-policy and declarative-config needs, the frugality rule applies. The value here is the *pattern*, with Kong as the concrete illustration.
- **No version numbers, benchmarks, or quotes are invented.** Named Kong features (plugin model, DB-less, decK, Kong Ingress Controller) are long-standing documented capabilities; this file makes no claim about which release introduced any of them and cites no performance figures.
- **The gateway does not replace the mesh, and vice-versa — the most important honesty here.** Any reading that treats "we have Linkerd" as a reason to skip a gateway (or "we have a gateway" as a reason to skip the mesh) is the exact category error this file exists to prevent. They are complementary planes.
- **Gateway edge-authz is deliberately out of scope.** The gateway validates *who*; it must not become this repo's authorization authority. ABAC/tenant decisions stay in the application (`access-control-model`, `zero-trust-design`). Pushing authz into gateway plugins would recreate the "smart gateway" anti-pattern and split the authorization model across two layers.
