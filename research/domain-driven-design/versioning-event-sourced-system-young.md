# Versioning in an Event Sourced System
**Authors:** Greg Young (*Versioning in an Event Sourced System*, Leanpub, 2017)
**Domain:** Domain-Driven Design — event schema evolution (event-sourced stores and published events)

This file grounds the event versioning rule that the Wave 2 audit found split between `domain-event-catalog` (`.v1` suffix, semver major bump) and `event-schema-design` (suffix banned, new event type) (W2-3, W2-4). Decision D047-1 settles the house rule: CloudEvents 1.0 with extensions, a breaking change is a new event type and never a `.vN` suffix, and `event-schema-design` owns the rule while `domain-event-catalog` points to it. D047-2 gives serialization and the schema registry to the data-architect, and D047-10 moves Go code out of design skills. This file does not repeat Kleppmann's backward/forward compatibility and Avro reader/writer schemas (`research/software-architecture/designing-data-intensive-applications-kleppmann.md`, Ch. 4) or Khononov's case for event sourcing, internal vs integration events and upcasting as a technique (`research/domain-driven-design/learning-ddd-khononov.md:20-21`). It adds Young's full set of options, when each fits, and his line between a new version and a new event.

## Core Concepts

- **Events are facts that are never updated, so versioning them is harder than versioning an API.** An API version can be retired once callers move. A stored event stays in the stream forever and must stay readable by today's code, by replays and by new projections built years later. Young starts from why an event cannot simply be updated: the event is the record: changing it rewrites history that consumers, projections and auditors already acted on.
- **A new version must be convertible from the old one; if it isn't, it's a new event.** This is Young's central rule, paraphrased. If every field of the new shape can be derived from the old one (a default, a rename, a split field), it is a new version of the same event. If the meaning changed (what happened in the business is different), no conversion exists, and it is a different event with its own name. A change in semantics is never a version bump.
- **Basic type-based versioning: the new version is a new type, and the old handler stays.** Young's simplest approach adds a new type for the new shape (his examples, as recalled, number it in the name, along the lines of `ItemDeactivated_v2`). Code must handle every type ever written. To keep the domain from growing a handler per version, old types are converted to the newest one as they are read, so the domain only sees the latest.
- **Upcasting converts old events to the current shape on read.** The stored bytes never change; a chain of small converters (v1 to v2, v2 to v3) runs at load time. This only works because of the convertibility rule above. Khononov's file already covers the technique; Young places it as the companion to type-based versioning, not a separate discipline.
- **Weak schema: map, don't deserialize strictly.** With a weak (tolerant) schema, such as JSON read by name-based mapping, the reader takes the fields it knows, ignores the rest and fills missing fields with defaults. The rules that keep it safe: only add fields, never rename, never change a field's type or meaning, and give every new field a default that is correct for old events. Many changes then need no new type at all. Young also describes a hybrid: weak schema for additions plus a type change for the rare breaking change.
- **Serialization choice decides which approach is cheap.** Strict binary formats bound to code types make every change a new type. JSON with mapping gives weak schema almost for free. Avro and Protobuf sit between: field numbers or reader/writer schemas allow additions safely, and a schema registry can enforce the add-only rules mechanically. The choice belongs with whoever owns serialization, before the first event is stored.
- **Negotiation: a consumer asks for the version it understands.** Like content negotiation over HTTP or a feed, a consumer of published events states which version it can read, and the producer side converts (upcasts or downcasts) to that shape. This keeps old consumers working without the producer emitting every version on every write. It suits published events with many consumers; it is overkill inside one service.
- **Internal and published events have different tolerance.** Private events inside one event-sourced service can change more freely: one team owns every reader, and upcasting or a stream rewrite is a local decision. Published (integration) events are a contract with consumers you don't control, so they need the strict end: add-only weak schema, a new type for breaking changes, a deprecation period, and ideally coarser events that hide internal detail. Young warns against publishing internal events directly.
- **Copy-and-replace rewrites a stream into a new one; the old stream is left alone.** When a stream's shape or boundary is wrong (it should be split, joined, or many old versions have piled up), read the old stream, transform each event, write a new stream, then switch readers over. Young also describes copy-transform of a whole store as part of a release: build a migrated copy, run old and new side by side, then cut over. Starting fresh from the latest shape when versions have piled up is what he calls declaring versioning bankruptcy (name recalled with less confidence).
- **In-place transformation is dangerous.** Editing stored events directly destroys the audit trail, breaks anything that already read or cached the old event, cannot be undone if the transform has a bug, and fails partway on large stores. Young treats it as a last resort, and copy-and-replace as the safe form of the same goal.
- **Mistakes are fixed with new events, not edits.** An event recorded wrongly is corrected the way an accountant corrects a ledger: append a correcting or compensating event. The original stays as evidence of what the system believed at the time.
- **A version number in the type name is one form of type-based versioning, not a mistake Young warns against.** Young uses numbered type names for convertible versions and upcasts them away. D047-1's "new event type, never a `.vN` suffix" agrees with him on semantic changes (a new event with a new name) and is **narrower** on shape changes: where Young would accept `_v2` plus an upcaster, the house rule asks for a descriptive new name for published events. That is a house choice for consumer clarity, not something Young requires.

## Actionable Techniques

- **Classify every change with Young's test first.** Additive with a correct default: evolve in place under weak schema. Same meaning, different shape, fully convertible: a new type plus a converter. Different meaning: a new event with a new business name, no converter.
- **Pick the approach by where the event lives.** Internal, stored: weak schema for additions, upcasting for convertible changes, copy-and-replace for stream-boundary changes. Published: weak schema for additions, a new type with dual publication and a deprecation date for breaking changes, negotiation only when there are many consumers.
- **Write the default for every added field and check it is true for old events.** A default that misstates history (for example, "zero" for an unknown amount) is a silent data error; prefer an explicit "unknown".
- **Never edit stored events.** Use a correcting event for bad data, upcasting for shape, and copy-and-replace for structure. Record the choice in an ADR when a stream is rewritten.
- **Keep converters small, chained and tested on real old events.** Store sample events of every historical type as test fixtures so a converter change can't silently break a replay.
- **Decide serialization and the registry before the first stored event.** The format fixes which of the above stays cheap. Lean products can run JSON weak schema with contract tests and no registry; products with many consumers add a registry in an add-only mode.

## Key Terminology

- **Type-based versioning** — each new event shape is a new type; old types stay readable.
- **Weak schema** — reading by field-name mapping with defaults and ignored extras; add-only changes.
- **Upcasting** — converting an old stored event to the current shape at read time; stored bytes unchanged.
- **Negotiation** — a consumer asks for the version it can read; the producer side converts.
- **Copy-and-replace / copy-transform** — writing a transformed copy of a stream (or store) and switching readers to it.
- **Versioning bankruptcy** — collapsing accumulated versions by rewriting to the latest shape (via copy-and-replace).
- **Correcting (compensating) event** — a new event that fixes a wrongly recorded fact without editing it.
- **Internal vs published event** — a private event-sourcing event vs a contract event other contexts consume.

## Caveats

- **Recalled with confidence:** events are never updated; the convertibility rule (if it can't be converted from the old event, it is a new event); type-based versioning with old handlers kept; weak schema and its add-only rules; serialization format deciding the cost; internal vs published events; copy-and-replace as the safe alternative to editing; in-place edits as dangerous; correcting events.
- **Recalled with less confidence:** exact chapter names and order (no chapter numbers are given for that reason); whether "versioning bankruptcy", "copy-transform" and "negotiation" are Young's chapter titles or my labels for his ideas; the exact form of his numbered type names (`_v2` vs `V2`). "Upcasting" is widely used in the community (Axon and others) and may predate or differ from Young's wording. "Tolerant reader" is Fowler's term (see Newman's file), and "consumer-driven contract" is Robinson's; neither is claimed for Young.
- **No quotations or page numbers.** The book is short and sold only on Leanpub; everything here is paraphrase from working knowledge, not a fresh re-read.
- **D047-1 is narrower than Young.** Young does not ban version numbers in type names. The house ban is a deliberate choice for published-event clarity and should be cited as D047-1, not as Young's rule.
