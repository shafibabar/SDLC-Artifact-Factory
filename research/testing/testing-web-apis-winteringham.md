# Testing Web APIs
**Authors:** Mark Winteringham
**Domain:** Testing

## Core Concepts

- **API testing is treated as its own discipline with its own map of test types, not a subset of UI testing or a synonym for contract testing.** Winteringham's organizing move is a "web API testing map" that separates the different jobs testing does against an API — functional correctness (does the request/response behave as documented), integration (does the API behave correctly against its real upstream/downstream dependencies), non-functional concerns (security, performance, usability of the API itself), and workflow/state correctness (does a multi-call sequence leave the system in the right state) — and argues teams collapse these into one undifferentiated bucket ("we have API tests") when they need deliberately different techniques and different owners. This repo currently names two of these jobs precisely (`go-contract-test` for schema/shape agreement, `go-integration-test` for real-dependency correctness) but has no named place for the other two — see Applies To.
- **Risk-based test planning: testing effort should be allocated by where the API can actually hurt you, not spread evenly across every endpoint.** The book's planning technique — informally called "risk storming" in Winteringham's wider writing and taught in the book as a collaborative exercise — has whoever knows the API (not just the tester) rate each capability or endpoint on likely impact and likelihood of failure, then concentrates deeper testing (exploratory sessions, non-functional checks, workflow tests) on the highest-scoring areas rather than treating a payment-idempotency endpoint and a static reference-data lookup as equally deserving of the same test depth. This is a planning technique this repo's `test-pyramid` does not have: it names *layers* (unit/contract/integration/e2e) and *proportions*, but nothing that decides which specific endpoints deserve extra investment within a layer.
- **Exploratory testing applied specifically to the HTTP surface of an API — a different activity from Hendrickson's product-level exploratory testing already in this repo's research.** Where `explore-it-hendrickson.md` (and this repo's own `uat-plan` exploratory-session component, built from it) is about a human exploring a **product workflow** through its UI during Customer Validation, Winteringham's API exploration targets the **protocol-level surface** directly and earlier — during Implement/Quality, before or alongside writing automated tests: sending an unexpected HTTP verb at a resource, omitting a required header, sending a wrong `Content-Type`, adding unrecognized fields to a payload, sending a boundary-sized or malformed body, or replaying a request with a stale auth token — using a tool like Postman/Insomnia to probe the API by hand and build a mental model of its real behavior before locking that behavior into automated assertions. It is charter-shaped in spirit (aim the exploration, then follow what you find) but the "product" being explored is the wire contract itself, not a user journey.
- **Testing the request and testing the response are treated as distinct, deliberate checks — not implied by "call the endpoint and assert 200."** The book pushes testers to separately verify: that a request is validated correctly (wrong types, missing required fields, extra unknown fields, wrong verb) and that a response is checked in full — not just the status code and a happy-path field, but every documented header, the error envelope shape on every failure branch (not just one sampled 400), and the exact boundary conditions the API contract promises (pagination edges, rate-limit thresholds, idempotency replay).
- **Testing workflows: multi-step, stateful sequences where each call's correctness depends on the ones before it.** A single request/response test proves one call works in isolation; a workflow test proves that a realistic sequence (create → read the created resource back → update it → observe the update reflected) holds together — including sequences that legitimately span more than one service call, which is where state bugs (a field that updates in storage but not in the read model, a cursor that becomes unstable mid-sequence) actually surface. This sits at a different grain than this repo's `go-e2e-test` (full user journey through the whole stack) — a workflow test can be pure API-to-API, no UI, no browser, exercising a business-relevant sequence of calls that never shows up as a single "user journey."
- **Non-functional concerns are tested as part of the API's own contract, not left entirely to a separate discipline.** The book treats security (authentication/authorization enforcement, security headers, injection resistance), performance, and usability (is the API actually easy and unambiguous to consume — clear errors, predictable pagination, sane defaults) as things the API-level test suite itself should assert on, in addition to — not instead of — dedicated security and performance testing. Concretely: does every response actually carry the documented security headers; does exceeding the documented rate limit actually return `429` with the right headers; does calling a deprecated version actually emit the promised deprecation signal — these are functional assertions about a non-functional promise, and the book treats "we designed it that way" and "we tested that it happens" as two different, both-necessary claims.
- **A layered automation architecture keeps API test suites maintainable as they grow: separate the HTTP mechanics from the test's business intent.** The book's automation guidance is to build (or adopt) a thin abstraction layer — request builders, response parsers/matchers, and reusable test-data builders — so an individual test reads as "create a data asset, classify it, assert it appears Restricted" rather than raw HTTP calls repeated with copy-pasted headers and manual JSON assembly in every test file. This is presented as a maintainability discipline specifically for the volume and churn API test suites accumulate, distinct from (and not a repeat of) unit-test patterns.
- **Testing asynchronous and eventually-consistent APIs requires deliberate polling and correlation, never a fixed sleep.** Where an API's effect isn't immediately visible in its own response (a `202 Accepted` whose outcome arrives later, a webhook callback, a read model that catches up after a write), the book's guidance is to poll with a bounded deadline and back off, and to use a correlation id threaded through the async path so a failed wait can be traced to exactly where it stalled — treating "wait and see" as a designed technique, not a workaround.

## Actionable Techniques

- **Risk-rate each endpoint/capability before deciding test depth**, using a simple two-axis pass (impact if it breaks × likelihood of failure) done by whoever knows the domain, not just the person writing tests — then route the highest-scoring endpoints to deeper coverage (exploratory pass, non-functional checks, workflow tests) and let low-scoring, low-change endpoints rely on schema/contract coverage alone. This repo's domain: a `/data-assets/{id}/classification` `PATCH` (business-critical, compliance-sensitive) and a `/healthz` `GET` do not deserve equal test investment, but nothing in `test-pyramid` currently says so explicitly.
- **Before automating a new endpoint, spend a short, time-boxed exploratory pass against its raw HTTP surface** — wrong verb, missing/extra headers, malformed and boundary-sized bodies, stale/expired auth, unexpected `Content-Type` — using a manual HTTP client, and only then write the automated assertions the pass revealed were worth locking in. This is a lightweight, protocol-level echo of Hendrickson's charter discipline, aimed at the wire contract rather than a product workflow.
- **Test every documented response header and every documented error branch, not just the happy-path shape.** For each endpoint, enumerate the response headers `api-contract-design` promises (security headers, `Idempotency-Key` echo, `Deprecation`) and every status code its own table lists (`400`/`401`/`403`/`404`/`409`/`422`/`429`/`500`), and assert each one is actually reachable and correctly shaped — a schema validator that only ever sees a sampled `200` and one `400` has not verified the contract, it has sampled it.
- **Write at least one workflow test per business-relevant multi-call sequence**, distinct from both a single-endpoint contract test and a full-stack e2e journey: call create, then read the same resource back, then mutate it, then read again — asserting state is consistent across the sequence, at the API layer only, with no browser or frontend involved.
- **For idempotency, rate limiting, and versioning specifically, write a test that proves the behavior, not just a test that proves the shape.** Replay a request with the same `Idempotency-Key` and assert the stored result is returned unchanged; exceed the documented rate limit in a test and assert `429` with the correct headers; call a version past its announced sunset window's start and assert the `Deprecation` header is actually present — each of these is a specific, cheap, currently-unwritten test given what `api-contract-design` already promises.
- **Poll with a bounded deadline and a correlation id for any API effect that isn't synchronous**, exactly as `go-integration-test`'s `awaitEvent`-style pattern already does for the outbox/consumer round trip — this book's guidance confirms that pattern rather than adding a new one; the actionable item is applying it consistently to *every* async API path (webhooks, `202`-then-poll endpoints), not only the event-pipeline case already covered.

## Candidate New Skills/Agents

- **One conservative candidate: a new `api-behavior-test` skill, owned by `test-strategist`, sitting alongside `go-contract-test` and `go-integration-test` in the Implement/Quality phases.** The gap this closes is specific and real, not speculative: `api-contract-design` (main) already promises five testable behaviors — `Idempotency-Key` replay, cursor pagination stability, `429` rate-limit enforcement, `Deprecation`-header versioning, and the standard `ErrorResponse` envelope on every documented failure branch — and as things stand today, none of the four skills read for this document tests any of them as behavior. `go-contract-test` proves shape; `go-integration-test` proves real-dependency correctness of the module/event path; `security-implementation` proves the control exists in code; nothing proves the control actually fires when exercised through the real HTTP surface. A new skill scoped narrowly to these cross-cutting, contract-promised *behaviors* (not schema, not full integration, not security-control implementation) would close the gap without overlapping any of the three. It should also carry the risk-based endpoint-prioritization technique (rate impact × likelihood, concentrate deeper coverage accordingly) since nothing in `test-pyramid` currently owns that planning step, and the API-surface exploratory technique (protocol-level probing before automating), since it is genuinely distinct from `uat-plan`'s human/product-level exploratory session and has no other home.
- **Deliberately not proposing this now** — per this repo's "conservative new-skill proposals" standard and the two-wave discovery/implementation process, this finding should surface as a discovery-sub-issue candidate for review rather than be built speculatively. An acceptable lighter alternative, if a full new skill is judged too heavy for the size of the gap: fold the five behavioral checks directly into `go-contract-test` as a new "Behavioral Contract Checks" section (it already owns the OpenAPI-conformance test file and is the natural place to add `TestProvider_IdempotencyKey_Replays` alongside `TestProvider_ConformsToOpenAPI`) rather than standing up a fourth test skill — this would keep the skill count frugal at the cost of a slightly broader `go-contract-test` scope. Either path is defensible; which one is chosen is a decision for the actual build session, not this research pass.
- **No agent-level gap.** `test-strategist` already owns every relevant skill in this cluster (`test-pyramid`, `go-contract-test`, `go-integration-test`, `go-e2e-test`); whichever of the two options above is chosen, it adds a skill (or a section) under an agent that already exists and already reasons about exactly this territory.

## Key Terminology

Candidates worth checking against `skills/glossary-management/` if the gap above is acted on:

- **Web API Testing Map** — Winteringham's framing of API testing as several distinct jobs (functional, integration, non-functional, workflow) rather than one undifferentiated "API tests" bucket. Useful primarily as an organizing concept for scoping a new skill correctly, not as a term this repo's artifacts need to surface directly.
- **Risk Storming** — the collaborative impact × likelihood rating technique for deciding where to invest deeper API test coverage. Not present anywhere in this repo's testing vocabulary today (`test-pyramid` and `risk-register` both use "risk" but neither has an endpoint-level prioritization technique); worth naming precisely if the risk-based prioritization step above is adopted, so it isn't confused with the general project-risk sense already used in `risk-register`.
- **Workflow Test** — a multi-call, stateful sequence tested purely at the API layer (no UI), distinct from both a single-endpoint contract test and a full-stack `go-e2e-test` journey. Not currently named in this repo; the closest existing concept is `go-integration-test`'s outbox+consumer round trip, which is a workflow test in spirit but scoped to one module's async path rather than a general technique.
- **Behavioral Contract Check** (candidate term, not from the book) — a proposed name, used above in the Candidate New Skills section, for the missing middle between schema conformance and full integration testing: a test that proves a contract-promised *behavior* (idempotency replay, rate-limit enforcement, deprecation signaling) actually occurs. Flagged as a naming candidate only, to be settled if and when the gap is actually built.

## Caveats

- **This document's citations are conceptual, not chapter-and-verse.** Unlike some of this cluster's other research files, no specific chapter numbers are asserted here — the book's content is described from its well-documented structure and publicly discussed technique names (the testing map, risk storming, request/response/workflow testing, non-functional API testing, automation-layer architecture), not verified line-by-line against a copy of the text during this pass. Treat the *shape* of the findings (risk-based planning exists as a named technique; API-level exploratory testing is protocol-level and distinct from product-level exploratory testing; non-functional concerns are tested as functional assertions) as reliable, and any implied precision about which exact chapter a technique appears in as unverified.
- **This is a genuine, if narrow, gap — not a case of the repo lacking API testing.** `go-contract-test` and `go-integration-test` are both mature, well-reasoned skills that correctly cover their stated scope (schema agreement; real-dependency correctness). The gap is specifically the handful of cross-cutting *behavioral* promises `api-contract-design` makes that fall outside both skills' declared boundaries — idempotency replay, rate-limit enforcement, deprecation signaling, pagination stability under concurrent writes, and full error-branch coverage. Don't overstate this as "this repo doesn't test its APIs" — it does, thoroughly, at the layers those two skills own.
- **Test data management, as the book treats it, is a narrower concern for this repo than for the book's general audience.** Winteringham's test-data guidance is partly aimed at testers working against black-box APIs they don't own (no direct database access, must provision and tear down state entirely through the API itself). This repo's actual model is white-box — `go-integration-test` and `test-fixture-design` already seed and clean up directly against a real, Testcontainers-provisioned database per test. That part of the book does not reveal a gap here; it describes a harder problem (black-box test data) this repo doesn't currently have, since every service under test is one this repo's own agents build and own.
- **The automation-architecture guidance (layered request builders/response parsers, separating HTTP mechanics from test intent) is already substantively practiced, not absent.** `go-integration-test`'s helper functions (`startPostgres`, `awaitEvent`, `freshTenant`) and `go-contract-test`'s (`loadOpenAPI`, `validateAgainstSchema`) are exactly this kind of abstraction layer. This book confirms the existing pattern is sound rather than prescribing a new one — cited here only to be explicit that this part of the book is a "no gap" finding, not overlooked.
- **Do not conflate this book's API-surface exploratory testing with `explore-it-hendrickson.md`'s product-level exploratory testing.** They share a family resemblance (unscripted, aimed at what wasn't specified) but differ in who does it (engineer/tester vs. a human UAT participant), when (Implement/Quality vs. Customer Validation), and what's being explored (raw HTTP requests/responses vs. a user-facing workflow). If the candidate skill above is ever built, it should cite this book for its exploratory technique and explicitly state it is not an extension of `uat-plan`'s exploratory-session component, to avoid two different practices accreting under one name.
