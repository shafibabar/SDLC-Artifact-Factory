# Python Testing with pytest
**Authors:** Brian Okken
**Domain:** Testing — pytest mechanics for Python

> Source note: synthesized from Brian Okken's *Python Testing with pytest* (2nd ed., Pragmatic Bookshelf, 2022) from working knowledge of the text. pytest's mechanics described here are stable, publicly-documented API; no direct quotations are reproduced. Chapter attributions are approximate signposts, not verified page citations.

## Core Concepts

- **Zero-ceremony test discovery and naming (Ch. 1–2).** pytest finds tests by convention, not registration: files matching `test_*.py`/`*_test.py`, functions prefixed `test_`, classes prefixed `Test` (with no `__init__`). There is no test-suite object to assemble, no base class to inherit — a bare module of `test_` functions is a runnable suite. This convention-over-configuration stance is the reason the same command (`pytest`) works identically on one file or a whole repo, and why test layout mirrors package layout without wiring.
- **Plain `assert` with rich introspection (Ch. 2).** Unlike `unittest`'s `assertEqual`/`assertTrue` vocabulary, pytest uses Python's bare `assert`. Its assertion-rewriting introspection unpacks a failed `assert a == b` into a diff of the two operands' actual values — including recursive dict/list/set diffs — so the failure message is generated from the expression itself, with no custom message required. This removes an entire memorized API surface and is the single biggest ergonomic difference from `unittest`.
- **Fixtures as dependency injection, scoped by lifetime (Ch. 3–4).** A `@pytest.fixture` function's return (or `yield`) value is injected into any test that names it as a parameter. `scope=` controls how often the fixture's setup runs: `function` (default, per test), `class`, `module`, `session` (once per whole run) — the lever that turns an expensive resource (a database container, an async engine) from per-test cost into per-session cost. Fixtures are pytest's answer to xUnit `setUp`/`tearDown`, but composable and explicitly requested rather than implicitly inherited.
- **`yield`-based setup/teardown and `conftest.py` sharing (Ch. 3–4).** A fixture that `yield`s a value runs everything before the `yield` as setup and everything after as teardown — teardown is guaranteed even when the test fails. Fixtures placed in `conftest.py` are auto-discovered by every test file in that directory tree with no import, giving a directory-scoped shared-fixture namespace; nested `conftest.py` files layer, so package-wide and subpackage-specific fixtures coexist.
- **Factory fixtures and fixture composition (Ch. 4).** When a test needs *many* configured instances, a fixture returns a *factory* — an inner function the test calls with parameters (`make_data_asset(tenant="acme", sensitivity="restricted")`) — instead of a single fixed object. Fixtures also depend on other fixtures by naming them as parameters, so a `session`-scoped `db_engine` composes into a `function`-scoped `db_session` that rolls back per test: a dependency graph of resources assembled by request, not a monolithic setup method.
- **Parametrize: test cases as data (Ch. 5).** `@pytest.mark.parametrize` turns one test function into N independent test cases, each a row of input/expected data — every row reported as its own pass/fail with its own id. This is *Specification by Example* in code: the example table lives beside the assertion, and adding a case is adding a data row, not copy-pasting a test. Fixtures themselves can be parametrized (`params=` on the fixture) to run the entire dependent suite across variants (e.g. multiple tenant configurations).
- **Markers: skip, xfail, and custom subset selection (Ch. 6).** `@pytest.mark.skip`/`skipif` drop a test (conditionally, e.g. on a missing dependency); `@pytest.mark.xfail` records a test *expected* to fail (a known bug or unimplemented spec) without reddening the run, and flags it loudly if it unexpectedly passes (`XPASS`). Custom markers (`@pytest.mark.integration`, registered in config) plus `-m "integration"`/`-m "not slow"` and keyword/nodeid selection (`-k`, `path::test`) carve arbitrary subsets — the mechanism that keeps the Test Pyramid's fast unit layer runnable in isolation from slow integration tests.
- **The plugin ecosystem (Ch. 12–15).** pytest's behavior extends through hooks and plugins: **pytest-cov** wraps coverage.py for `--cov` line/branch reports (a lagging signal, per Khorikov, never a target); **pytest-mock** exposes patching as a `mocker` fixture with automatic per-test teardown (no nested `with patch(...)` stacks); **pytest-asyncio** lets `async def test_` coroutines run under an event loop with async fixtures, essential for a FastAPI + asyncpg + aiokafka stack whose code is async end to end.
- **Real dependencies via testcontainers-python (integration layer).** For integration tests that must exercise the actual database/broker rather than a fake, `testcontainers-python` spins up a throwaway Postgres or Redpanda container per session, yields its connection URL through a `session`-scoped fixture, and tears it down after. This is the concrete tool behind Khorikov's rule that *managed* dependencies (your own DB) are verified through real end-state, not mocked — and behind cosmic-python's "test against the real thing at the edges" discipline.
- **Fakes over mocks, and the pyramid as a consequence (cross-book alignment).** Okken shows the mechanics of both `pytest-mock` and fixture-based fakes, but the *discipline* comes from the books already in `research/`: prefer a state-based fake (an in-memory repository fixture) for managed dependencies and reserve mocks for unmanaged, externally-observable ones (Khorikov); let the pyramid's shape fall out of a well-isolated domain model (cosmic-python's ports/adapters), not out of a target ratio.

## Actionable Techniques

- **Layer `conftest.py` deliberately.** Put session-scoped expensive resources (async engine, testcontainer) in the top-level `tests/conftest.py`; put per-test transactional wrappers and domain factories in subpackage `conftest.py` files. Never import a fixture — if a test can't see it, it's in the wrong `conftest.py`.
- **Make the per-test DB fixture roll back, not recreate.** Compose a `function`-scoped `db_session` on a `session`-scoped engine that opens a transaction and rolls it back in teardown — fast isolation without rebuilding schema per test.
- **Push example tables into `parametrize`.** Any test whose body would be copy-pasted with a different input becomes a parametrize row instead; give each row an `id` so failures name the case, not `test[0-1-2]`.
- **Use a factory fixture for domain objects with a tenant/sensitivity axis.** `make_data_asset(tenant=…, sensitivity=…)` returning valid `DataAsset` instances keeps per-tenant-isolation tests readable and prevents each test from re-specifying the full object.
- **Register custom markers in config and select with `-m`.** Mark integration/slow tests, register the marker in `pyproject.toml` (so unknown-marker warnings stay meaningful), and run `-m "not integration"` for the fast inner loop, `-m integration` in CI's slower stage.
- **Gate async correctly.** Set `asyncio_mode = "auto"` (or mark tests) so `async def` tests and async fixtures run without per-test boilerplate; ensure async engine/session fixtures are async generators (`async def … yield`).
- **Reserve mocks for the unmanaged edge.** Use `mocker` only for aiokafka publishes / third-party HTTP — the observable interactions; use an in-memory fake repository fixture for the owned Postgres path, and an integration test with testcontainers for the real end-state check.
- **Report coverage, don't chase it.** Wire `--cov` for a gap *signal*, but never accept a coverage number as evidence a suite is good — an assertion-free test inflates it while catching nothing.

## Key Terminology

- **Fixture** — a `@pytest.fixture`-decorated provider injected by name into tests; the composable replacement for xUnit `setUp`/`tearDown`. Already in the glossary as `Test Fixture`; pytest gives it a scope lifetime (`function`/`class`/`module`/`session`) worth noting there.
- **Parametrization** — one test function expanded into N data-driven cases via `@pytest.mark.parametrize`; the code-level realization of `Specification by Example` / example tables already in the glossary.
- **`conftest.py`** — the directory-scoped, auto-discovered fixture (and hook/plugin) namespace; nested files layer package-wide and subpackage fixtures without imports.
- **xfail / xpass** — a test marked expected-to-fail (known bug or unimplemented spec) that stays green as `XFAIL`, and loudly flags `XPASS` if it starts passing — distinct from `skip`, which runs nothing.
- **Testcontainer** — a throwaway real dependency (Postgres/Redpanda) started for the duration of a fixture's scope; the tool behind integration tests against real managed dependencies.

## Caveats

- **Confidence:** high on pytest's mechanics (discovery, assert rewriting, fixtures, scopes, parametrize, markers, the named plugins) — stable, widely-used public API. Chapter numbers are approximate signposts, not verified citations.
- **The three python-* testing skills do not yet exist** at the time of writing — this file is source material *for building them*, mapping the book's mechanics onto Tier 2 targets whose Go siblings (`go-unit-test`/`go-integration-test`/`go-contract-test`) are the built reference shape. Do not read the Applies To rows as describing current skill content.
- **testcontainers-python and the pytest plugins are additional dependencies** — each must justify itself against the repo's frugality constraint. testcontainers needs a container runtime available in CI; the frugal contract default deliberately avoids a Pact broker, matching `go-contract-test`.
- **Okken's book is mechanics, not test-design philosophy.** It shows *how* to mock, parametrize, and fixture; it does not adjudicate *when* to mock vs. fake or how to shape the pyramid. That judgment is owned by `unit-testing-khorikov.md` (four pillars, managed vs. unmanaged dependencies, never-assert-on-a-stub) and `architecture-patterns-with-python-percival-gregory.md` (ports/adapters, fakes at the edges) — this file defers to them on discipline and supplies only the pytest execution layer.
- **Async is the default here, not an afterthought.** The target stack (FastAPI + asyncpg + aiokafka) is async end to end, so `pytest-asyncio` and async fixtures are load-bearing, not optional — a sync-only reading of the book undersells what the python-* skills need.
