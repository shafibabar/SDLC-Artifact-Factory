# Specification by Example: How Successful Teams Deliver the Right Software
**Authors:** Gojko Adzic
**Domain:** Testing

## Core Concepts

- **"Living Documentation" has a precise, load-bearing definition — not just "docs that don't rot."** Adzic's claim is stronger than "specs stay current because they're tested." A specification becomes *living documentation* only when it is (a) automatically validated against the real system on a regular cadence, and (b) the validated result is itself surfaced back to the team as readable documentation — typically an auto-generated report or website built from the executed specs (his own examples come from tools like Pickles, Cucumber's HTML/JSON reporters, and similar "spec-to-doc" generators used by the case-study teams in the book). The point isn't merely that a stale scenario fails the build (a necessary but not sufficient condition) — it's that the *documentation artifact itself* is derived mechanically from the passing suite, so there is never a hand-maintained document that can drift from what was actually verified. A team that keeps `.feature` files in version control and runs them in CI has satisfied half of Adzic's definition (current-because-tested); the other half — deriving a browsable, single-source-of-truth documentation artifact from the execution results, readable by both business and technical audiences without opening a code editor — is a distinct practice the book treats as the actual payoff of doing all this work in the first place.
- **Specification Workshops are Adzic's own named practice for deriving examples collaboratively, before Gherkin is written.** The book (building directly on Chris Matts' and Dan North's earlier BDD thinking, and converging independently with Ken Pugh's ATDD "triad") describes a short, structured, facilitated session where business, development, and testing perspectives work out concrete examples for a feature together — the same three-perspective shape later literature calls the "Three Amigos." Adzic's book is a major popularizer of that collaborative-authorship expectation but is not the coiner of the exact phrase "Three Amigos" — that workshop-format name is most closely associated with George Dinwiddie, with Adzic (and, separately, Matt Wynne's Example Mapping) doing much of the work of spreading the practice into mainstream BDD adoption. Attribute the *phrase* carefully; attribute the *practice* (deriving examples collaboratively, before automation, from all three perspectives) to Adzic confidently.
- **A concrete "definition of ready" for a specification, not just "get people in a room."** Beyond naming the collaborative expectation, Adzic gives procedural texture: keep workshops short and focused on one feature or a small handful of scenarios at a time; the facilitator's job is to keep the conversation on concrete examples and away from abstract rule debates (functionally the same discipline Example Mapping enforces with its red/blue/green cards); and a specification is workshop-ready to automate once the examples are expressed in **business language with no UI or technical mechanics**, each example is **traceable to a single rule** it illustrates, and the team present has **explicitly agreed** it represents the intended behaviour (not merely that someone wrote it down). This is a slightly sharper, more procedural version of the same "who's in the room" gap already found by `agile-testing-crispin-gregory.md` for `bdd-feature-file` — it doesn't introduce a new procedure so much as it makes the missing step nameable and checkable.
- **Key Examples: the discipline of the minimum sufficient example set, not exhaustive coverage.** One of the book's most concrete techniques: a good specification illustrates a business rule with the *smallest* set of examples that fully pins the rule down — not one example per plausible input combination. Adzic's worked guidance is to actively prune examples that don't add new information (an example that could be deleted without changing what the rule specifies is a redundant example and should go), and to treat a growing pile of near-identical rows in a scenario outline as a smell — either the rule is over-specified, or several *different* rules are being conflated into one table. This is explicitly an economy/minimality principle, not a completeness principle — it sits philosophically opposite Jorgensen's decision-table completeness (`2^n` rule enumeration, already routed to `go-unit-test`/`test-pyramid` by the `software-testing-craftsman-jorgensen.md` file, correctly out of scope here): Jorgensen asks "have we enumerated every combination," Adzic asks "have we kept only the combinations that actually teach the reader something new."
- **Refactoring specifications as a first-class, ongoing practice, not a one-time authoring event.** The book treats a specification suite the way disciplined teams treat production code: as it grows, duplicated setup gets extracted, overlapping scenarios get merged or deleted, step definitions get consolidated, and scenarios that no longer reflect a live business rule get retired rather than left to accumulate as dead weight that erodes trust in the whole suite ("if some of the specs are known-stale, nobody trusts any of them"). This maintenance discipline is explicitly framed as protecting the "living" property over time — a spec suite that was living documentation at launch but was never refactored degrades into exactly the kind of untrustworthy artifact the whole practice exists to prevent.
- **Given/When/Then as a structure for illustrating business rules, not a script for driving the UI** — Adzic's framing here (inherited from and popularizing Chris Matts' and Dan North's earlier articulation) is that a scenario's job is to make a business rule concrete and checkable, with the automation underneath it as an implementation detail the business reader never needs to see. This is the same declarative-not-imperative stance Ken Pugh independently argues for from the ATDD side (already confirmed fully implemented in this repo per `lean-agile-atdd-pugh.md`), and it is consistent with — not different from — how this repo's `bdd-feature-file/SKILL.md` already frames the relationship ("the acceptance criteria *are* the test, in the business's language"). No daylight found between Adzic's framing and this repo's existing framing on this specific point.

## Actionable Techniques

- **Generate a documentation artifact from the executed suite, not just run the suite in CI.** After scenarios pass, produce a browsable report (HTML/site) grouping scenarios by feature, showing pass/fail status and the last-verified date, so a non-engineer can browse *what the system currently does, proven* without reading `.feature` files in a repo browser.
- **Run a short, focused specification workshop per feature (or small scenario batch) before Gherkin is finalized** — timebox it, keep the conversation anchored to concrete examples, and treat "we can't produce a real example" as a signal the feature isn't ready to specify yet (the same readiness signal Example Mapping and Pugh's ATDD both already use).
- **Apply a "does this example teach something new" prune test to every Scenario Outline.** Before adding a row to an Examples table, ask whether removing it would change what the rule is proven to do; if not, don't add it. Periodically re-run this prune test on existing tables as rules evolve.
- **Schedule specification refactoring alongside code refactoring**, not as an afterthought — when step definitions are consolidated or scenarios merged, treat it as maintenance work with the same seriousness as a production-code refactor, not busywork to skip under time pressure.
- **Treat "ready to automate" as a checkable definition-of-ready**, not a vibe: business language only, one rule per example, team-agreed. This mirrors work `acceptance-criteria/SKILL.md` already does in its "Criteria That Fail the Testability Check" table — Adzic's version is workshop-facing (is this example ready to hand to automation) rather than criterion-facing (is this criterion testable), a modest but real distinction in *when* the check applies.

## Caveats

- **The "auto-generated documentation site" practice assumes tooling this repo hasn't evaluated.** Adzic's case-study teams used tools like Pickles or Cucumber's own reporters to turn executed `.feature` files into browsable HTML. This repo already has `godog` named as its Go BDD runner in `bdd-feature-file/SKILL.md`; whether godog's own reporting output (or a lightweight equivalent) is sufficient to satisfy Adzic's "generated documentation artifact" bar, versus requiring an additional tool, is a build-time decision for whoever implements the gap above — not something this research file can resolve without checking godog's actual reporter capabilities, which is out of scope for a book-research pass.
- **This book predates this repo's specific stack** (godog, Playwright e2e binding, Redpanda-based event assertions) by well over a decade — cite it for the *conceptual* content (living documentation's precise definition, specification workshops, key examples, spec refactoring) not for any tooling recommendation; the book's own tooling examples (Fitnesse-adjacent and early Cucumber-era) are dated relative to this repo's Go-native choices.
- **"Key Examples" is a minimality principle, not a completeness one — don't conflate it with Jorgensen's decision-table coverage.** `software-testing-craftsman-jorgensen.md` already found (and correctly routed elsewhere) that Gherkin is a "less formally rigorous descendant" of Decision Table testing; that finding is about *combinational completeness* (has every condition combination been enumerated). Adzic's key-examples principle is the opposite concern — has every example been *earned*, not merely enumerated. Both can be true of the same scenario outline at once (complete *and* minimal), so citing both books together on the same table is legitimate, not contradictory — just don't let one book's finding be read as invalidating the other's.
- **No standout finding here required inventing a gap.** Most of what Adzic's book covers (declarative Given/When/Then, examples-before-rules, collaborative derivation) is already either fully implemented in this repo (per this file's own checks) or already found and correctly attributed by `agile-testing-crispin-gregory.md` and `lean-agile-atdd-pugh.md`. This file's genuine, load-bearing addition is narrower than a first skim of the book's scope might suggest: the Living Documentation depth gap, the key-examples prune test, and the (optional, small) spec-maintenance anti-pattern — three targeted additions to one existing skill, not a new practice area for the repo.
