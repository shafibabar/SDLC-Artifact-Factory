# Contract Testing in Action
**Authors:** Marie Cruz and Lewis Prescott
**Domain:** Testing

## Core Concepts

- **Contract testing is not schema validation, and the difference is the book's central thesis (Ch. 1–2).** Cruz and Prescott spend their opening chapters distinguishing a *contract test* from a *schema test*: a schema check confirms a payload has the right shape and types, but says nothing about whether the specific values, combinations, and interactions a consumer actually relies on remain compatible. Their running example is a field that stays the correct `string` type across a change but flips from an enum of three known values to a free-text field — a schema validator waves it through; a contract test (built from the consumer's real expected interaction) fails immediately because the consumer's mock was generated from the exact expected values, not just the type. This is a direct, named contrast with `go-contract-test`'s own approach, which is schema-based by design (`kin-openapi` validates real responses against the OpenAPI spec's structural shape) — see Applies To below for what this means concretely, not just terminologically.
- **The consumer test runs against a mock generated *from* the contract, not a hand-written stub (Ch. 3–4).** In the Pact model the book teaches, the consumer-side test doesn't just declare which fields it reads — it defines exact request/response interactions (a specific request triggers a specific expected response), and the Pact library spins up a real local mock HTTP server built from those interactions. The consumer's actual client code runs against that mock server. The side effect of running the test is a generated **pact file** (JSON) recording every interaction — the contract is a byproduct of testing the consumer, not a document written by hand first.
- **Provider verification replays the consumer's exact recorded interactions against the real provider, using Provider States to set up fixtures (Ch. 5–6).** The Pact Verifier reads the pact file(s) and, for each interaction, issues the exact recorded request against the running provider and asserts the response matches. Because a provider's real behavior often depends on prior state ("a data asset with this ID exists and is classified Restricted"), each interaction can carry a **Provider State** — a named precondition string (`"a classified data asset exists"`) that the provider maps, on its own side, to setup code (seed a fixture, insert a row) before the verifier fires that specific request. This is the concrete mechanism that makes exact-interaction replay possible without the provider's real database always happening to be in the right state.
- **The Pact Broker is the shared source of truth for contracts, and `can-i-deploy` is the deployment safety gate (Ch. 7–9).** Consumers publish pact files to a central Broker (self-hostable, open source, Docker-deployable) tagged with a consumer app version (typically a git SHA) and an environment. Providers poll the Broker for the latest pacts to verify and publish their verification *results* back to the same Broker, tagged with the provider's version. The `pact-broker can-i-deploy --pacticipant Consumer --version <sha> --to-environment production` CLI command then queries the Broker's **compatibility matrix** — every consumer version × every provider version that has ever been verified against it — and returns pass/fail before a deploy is allowed to proceed. This answers a question schema validation structurally cannot: "is the specific consumer version I'm about to deploy actually compatible with the specific provider version currently running in production" — checked against real historical verification results, not a point-in-time CI run.
- **Pending Pacts and WIP Pacts decouple "the contract changed" from "the provider's build broke" (Ch. 8).** A naive Broker-gated pipeline means the instant a consumer adds a new expectation, the provider's next CI run turns red — even though the provider team hasn't had a chance to react yet. **Pending Pacts** mark a newly published (never-yet-verified-successfully) contract as non-blocking: the provider's verification step runs it, reports the result, but does not fail the build on a first failure. **WIP Pacts** extend this to pacts still tagged to an in-progress consumer branch that hasn't reached main. Both mechanisms let contract evolution happen incrementally, visibly, without an automatic build break the moment a consumer team starts iterating.
- **Contract versioning is tied to deployable artifact versions (git SHA), not semantic contract version numbers (Ch. 7, 9).** The book is explicit that Pact does not ask teams to hand-manage a contract version number; instead every published pact and every verification result is tagged with the actual application version (commit SHA) that produced it, plus the environment it's deployed to. Compatibility is then a lookup against real deployed versions, which is what makes `can-i-deploy` meaningful across independently-deployable services — it is asking about *what is actually running*, not about the latest contract in the repo.
- **Consumer-driven vs. bi-directional contract testing (Ch. 10).** The book covers Pact's own newer, commercially-hosted alternative (via PactFlow) — bi-directional contract testing — where the consumer publishes its expectations and the provider independently publishes an OpenAPI spec, and PactFlow's SaaS compares the two without requiring the provider to run the Pact Verifier against real consumer interactions. The book presents this as a lighter-weight option for organizations that cannot get provider teams to adopt Pact Verifier directly, at the cost of losing the exact-interaction-replay guarantee of true CDC. It is explicitly a commercial, hosted capability (PactFlow), not part of the open-source Pact Broker.
- **Message/event contract testing follows the same consumer-driven shape, adapted for async (Ch. 11).** For queue- or topic-based integration, the "consumer" test still defines an expected message shape and the "provider" (publisher) verifies its emitted messages satisfy every consumer's expectation — but there is no live request/response to replay, so verification is a message-handler function invoked with the recorded message body rather than an HTTP call. Provider States apply the same way (set up context, then assert the publisher's message-building code produces a matching message).
- **Contract tests occupy a distinct layer in the test pyramid — smaller and faster than integration tests, but still consumer/provider-pair-specific (Ch. 1, 12).** The book positions contract tests as running in each side's own CI pipeline (no network call to the real counterpart at test time — everything is mocked from or replayed against the contract), placing them below full integration/E2E tests in cost and above pure unit tests in the confidence they provide about cross-service compatibility — a scope argument, not a replacement for either layer.

## Actionable Techniques

- When a boundary genuinely graduates to Pact per `go-contract-test`'s existing escalation rule ("stay schema-based... until there's a genuine multi-party, multi-repo integration... adopt `pact-go`... record it as an ADR"), write the consumer test as an exact-interaction Pact test (request → specific expected response, run against the Pact-generated mock, not a schema assertion) rather than reusing the schema-validation style used for the frugal default — the two are mechanically different tests, not the same test pointed at a different library.
- Name **Provider States** explicitly as the fixture-setup mechanism whenever a `pact-go` provider verification is adopted — each interaction that depends on prior data (an existing record, a specific status) needs a named state string mapped to setup code on the provider side, or verification will flake against whatever data happens to already exist.
- Adopt **Pending Pacts** (and WIP Pacts for in-progress consumer branches) as the default mode for any provider's Pact Broker-gated CI the moment more than one consumer team can publish contracts independently — this is what keeps `go-contract-test`'s existing "provider CI runs... every consumer expectation" loop from turning red the instant a consumer iterates, without disabling the check entirely.
- When `go-contract-test`'s ADR for adopting `pact-go` is written, name `can-i-deploy` (queried against a self-hosted, open-source Pact Broker) as the specific deployment gate replacing the skill's current "frugal, file-based answer" (pinning each consumer's expectation files to its deployed version and verifying HEAD + deployed) — the Broker's compatibility matrix is the same idea (verify against what's actually deployed, not just HEAD) implemented as a queryable service instead of committed files, and is the concrete mechanism the skill's own text gestures at without naming.
- If message/event contracts ever need the same escalation as HTTP contracts (multi-party, multi-repo Redpanda topic ownership), apply the same consumer-driven mechanics `event-schema-design`/`go-contract-test` already use for schema compatibility, replacing "validate against the registered schema" with "replay the consumer's recorded expected message against the publisher's message-building function" for the specific boundary that has outgrown schema-only checks.
- If PactFlow's bi-directional contract testing is ever considered as a lighter alternative to full Pact Verifier adoption, flag it explicitly against `CLAUDE.md`'s frugality constraint ("Open-source over paid tooling... No external paid APIs added without explicit approval") before adopting — it is a commercial SaaS product, unlike the self-hostable, open-source Pact Broker and Verifier.

## Key Terminology

Worth considering for `skills/glossary-management/`'s Ubiquitous Language:

- **Provider State** — a named precondition (e.g., "a classified data asset exists") that a provider maps to setup code before verifying a specific recorded interaction. Not currently named anywhere in the repo; directly actionable only once `go-contract-test`'s Pact escalation path is taken for a real boundary — don't add speculatively before then.
- **Pact Broker** and **`can-i-deploy`** — the shared contract repository and its deployment-safety CLI gate. `go-contract-test` already implements the *concept* `can-i-deploy` answers (verify against the deployed consumer version, not just HEAD) as a file-pinning workaround, but never uses either term. Worth adding once the skill names the Broker as the tooled replacement for that workaround.
- **Pending Pact / WIP Pact** — the mechanism that lets a newly published consumer contract avoid immediately failing the provider's build. Distinct from this repo's existing `event-schema-design` BACKWARD-compatibility check (which gates schema *evolution*, not a specific unverified consumer expectation) — worth its own term if the Pact escalation path is adopted, to avoid conflating the two.
- **Contract Test vs. Schema Test** — the book's own named distinction between structural validation (type/shape) and exact-interaction validation (the specific values and combinations a consumer's mock was built from). Worth a precise glossary distinction if `go-contract-test` adds the caveat recommended above, so "contract test" isn't used loosely to mean "schema check" going forward.
- **Bi-Directional Contract Testing** — PactFlow's commercial alternative to consumer-driven verification (provider publishes OpenAPI, consumer publishes expectations, a third party diffs them). Flag as a commercial/SaaS term if ever discussed — do not adopt into glossary as a recommended technique without the frugality caveat attached, since it is a paid product distinct from the open-source Pact Broker.

## Caveats

- **The book's premise is multi-team, multi-repo scale by default — this repo's actual operating model is solo, single-repo.** Every chapter assumes a consumer team and a provider team that don't share a codebase, communicate asynchronously, and need a Broker to coordinate deploys they don't otherwise see. `go-contract-test` already reaches this conclusion correctly and independently ("Because we're solo and the services share one repo/contract, this loop is a CI job, not cross-team broker choreography — frugal by design," line 98) — this book validates that reasoning rather than contradicting it. Treat this book's mechanics as dormant capability for a future multi-party engagement, not a retrofit the current product needs.
- **This is confirmed a depth gap, not a contradiction.** `go-contract-test`'s schema-based default is a legitimate, working design for this repo's current scale — it is not "wrong" relative to this book. The genuine gap is narrower and more honest than "the skill is missing CDC": the skill already names Pact as the correct escalation and already has a workaround (file-pinning) standing in for `can-i-deploy` — this book supplies the mechanical detail (Provider States, Pending/WIP Pacts, the Broker, the actual `can-i-deploy` command) that the skill's existing prose gestures at but doesn't specify. Don't overstate this as "the repo lacks contract testing" — it doesn't.
- **The book's tooling (Pact, PactFlow, the Broker) is largely language-agnostic in its examples (primarily JavaScript/Ruby in the book's own code samples), not Go-specific.** `pact-go` exists as the Go client library and is already the tool `go-contract-test` names for its escalation path, but this book does not itself demonstrate Go usage — treat it as a source of CDC mechanics and vocabulary, not of Go-idiomatic implementation detail (that extrapolation, if the escalation is ever taken, belongs in `go-contract-test` itself, consistent with how the `go-*` skills already handle other book-sourced concepts).
- **PactFlow's bi-directional contract testing is a paid, hosted product and must be flagged against `CLAUDE.md`'s frugality constraint if ever raised as an option** — unlike the self-hostable, open-source Pact Broker and Pact Verifier, which fit the "open-source over paid tooling" default without needing explicit approval.
- **The book is current (2023) and does not require any "supersedes an existing, more rigorous source" check** — unlike some other research findings in this cluster (e.g., Newman's service-sizing heuristics being subsumed by *Software Architecture: The Hard Parts*), no other source in this repo's research tree covers Pact-specific mechanics at this level of detail; `building-microservices-newman.md`'s Consumer-Driven Contracts finding is explicitly architecture-conceptual only and defers exactly this mechanical depth, which is what this document supplies.
