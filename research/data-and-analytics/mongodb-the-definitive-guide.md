# MongoDB: The Definitive Guide
**Authors:** Shannon Bradshaw, Eoin Brazil, Kristina Chodorow
**Domain:** Data & Analytics — Document Data Modeling and the Official Go Driver

> Source note: synthesized from the book and the stable, public MongoDB data model, query, aggregation, and `mongo-go-driver` APIs. No version numbers, benchmarks, or quotes are invented; where a mechanism is named (aggregation stage names, read/write concern levels, replica-set/sharding concepts) it reflects the widely-documented, long-stable MongoDB contract.

## Core Concepts

- **The document is the unit of storage, and it is a whole aggregate (Ch. 1–3).** A MongoDB document is a BSON object — a typed superset of JSON with `ObjectId`, dates, decimals, and binary — and the book's central shift from relational thinking is that one document should hold the data an application reads and writes *together*. This maps almost exactly onto the DDD Aggregate boundary: an Aggregate root and everything inside its consistency boundary is a natural document, because a single-document write is atomic. The design question is no longer "how do I normalize this across tables" but "what is the aggregate that gets loaded and saved as one unit."
- **Embed vs. reference is the one modeling decision that matters most (Ch. 8).** Embed when the child data is owned by, bounded in size with, and read alongside the parent (one-to-few, contained lifecycle) — a `Report` embedding its `sections`. Reference (store an `ObjectId`/key and read separately) when the related set is unbounded or large (one-to-many/many, would blow the 16MB document cap), when it is shared across parents, or when it is written on a different cadence than the parent. The book frames this as a read-pattern decision, not a purity decision: model for the queries you actually run.
- **Denormalization is a deliberate, owned tradeoff (Ch. 8).** Because there are no joins in the write path, the document model duplicates data on purpose — a `tenantName` copied into each `DataAsset` so a listing needs one query, not a lookup. The book is explicit that this trades write-time fan-out and a consistency obligation (you must update every copy, or accept staleness) for read simplicity and locality. This is the inverse of the repo's default 3NF Postgres posture, and the choice must be made with eyes open.
- **Schemaless still needs a schema — and a schema *version* (Ch. 9).** MongoDB does not enforce structure by default, but the book is emphatic that a collection still has an implicit application-level schema, and that letting it drift silently is the failure mode. The durable technique is a `schemaVersion` field on every document plus handle-on-read migration (the app upgrades a document's shape when it loads it) or a background migrator — no `ALTER TABLE`, so evolution is code, not DDL. Optional JSON-Schema validators can be attached to a collection to make the contract enforceable at the server.
- **Indexes decide whether a query is viable (Ch. 5).** The book treats indexing as the difference between a working system and a collection scan. Types: single-field; **compound** (order matters — the ESR rule: Equality, then Sort, then Range fields); **multikey** (automatic over array fields, indexing each element); **text**; **TTL** (auto-expires documents after a time — the native fit for ephemeral scan results or audit windows); plus partial and unique indexes. A query that isn't covered by an index is a design defect, not a tuning afterthought.
- **The aggregation pipeline is the query language for analytics (Ch. 7).** A pipeline is an ordered list of stages, each transforming the stream: `$match` (filter early, ideally on an index), `$group` (aggregate — counts, sums, `$push`), `$lookup` (a left-outer join into another collection), `$project`/`$addFields` (reshape), `$sort`, `$unwind` (flatten arrays), `$facet` (multiple sub-pipelines). This is where document stores answer the reporting questions that would otherwise force a relational model — but `$lookup` is deliberately the exception, not the norm; heavy join-shaped work is the signal you may want Postgres.
- **Multi-document ACID transactions exist, but they cost (Ch. 8, driver docs).** Single-document writes are always atomic — the model's whole point. Since MongoDB 4.x, multi-document transactions across collections/shards are supported with snapshot isolation, but the book's stance (and MongoDB's own guidance) is that needing them frequently means the documents are drawn wrong: reach for a transaction as a targeted tool, not a default, because it adds latency, lock contention, and a 60-second default runtime limit.
- **Replica sets and sharding are the availability and scale story (Ch. 10–14).** A **replica set** is a primary plus secondaries with automatic failover — the durability/HA unit. **Sharding** horizontally partitions a collection across shards by a **shard key**, which is the highest-stakes physical decision (it dictates write distribution and whether a query is targeted or scatter-gather, and is very hard to change). For this repo's per-tenant physical isolation, `tenantId` is a natural shard-key/partition axis conceptually.
- **Read and write concerns are tunable consistency (Ch. 11).** **Write concern** (`w:1`, `w:"majority"`, plus `j:true` for journal durability) trades latency for durability guarantees; **read concern** (`local`, `majority`, `snapshot`) trades freshness for consistency; **read preference** routes reads to primary or secondaries. These are per-operation dials, not global settings — the book's point is that "consistency" is a spectrum you choose per call, unlike Postgres's single strong default.

## Actionable Techniques

- **Model from the query, then validate the embed/reference call against three tests:** Is the child set bounded (won't approach 16MB)? Is it read with the parent every time? Is it owned by exactly one parent? Three yeses → embed. Any no → reference. Record the decision in the data model artifact like an ER choice.
- **Put `schemaVersion` on every document from day one**, and write the load path as a small upgrade switch (read v1 → return v2 in memory), so schema evolution never requires a migration window. Attach a `$jsonSchema` collection validator once the shape stabilizes.
- **Index to the ESR rule and add a TTL index for anything ephemeral** (scan results, cached extractions, expiring audit rows) so cleanup is the database's job, not a cron. Verify every hot query with `explain()` and refuse collection scans in review.
- **Aggregation from Go:** build a `mongo.Pipeline` as `bson.D` stages, `$match` first on an indexed field, decode with `cursor.All(ctx, &out)`. Keep pipelines in the repository, returning domain Read Models — never leak `bson.M` upward.
- **Go driver repository shape:** depend on a `Collection`-narrow interface, not `*mongo.Client`, so it is swappable and testable; use `InsertOne`/`FindOne`/`UpdateOne` with `bson` struct tags on the domain document; wrap `mongo.ErrNoDocuments` into a domain not-found error at the package edge, exactly as `go-repository-pattern` wraps `pgx.ErrNoRows`.
- **Scope every operation by tenant:** put `tenantId` in every filter (`bson.D{{"tenantId", tid}}`) as an application-layer defense-in-depth check even under physical isolation, and make it the leading field of compound indexes and the conceptual shard key.

## Key Terminology

- **Document / BSON** — the storage unit: a typed (ObjectId, date, decimal, binary) JSON superset, capped at 16MB, modeling one Aggregate. Worth a `glossary-management` entry alongside `Aggregate`, since the two concepts deliberately align.
- **Embedding vs. Referencing** — the two ways to represent a relationship in a document model (nested sub-document vs. stored key read separately); the core modeling decision, distinct from relational normalization.
- **Aggregation Pipeline** — MongoDB's staged (`$match`/`$group`/`$lookup`/`$project`/`$unwind`) query-and-transform language; the document-store equivalent of analytical SQL.
- **Shard Key** — the field partitioning a collection across shards; the highest-stakes, hardest-to-change physical decision, and the natural home of `tenantId` in this repo.
- **Read/Write Concern** — per-operation consistency and durability dials (`w:"majority"`, read concern `snapshot`, etc.), distinct from Postgres's single strong default.

## Caveats

- **Confidence is high on the model, driver surface, and headline concepts** (document model, embed/reference, aggregation stages, index types, replica sets, sharding, read/write concerns, multi-document transactions) — these are long-stable, publicly documented MongoDB contracts. Exact chapter numbers are approximate signposts to the book's structure, not verified page citations.
- **This repo's default is PostgreSQL + pgx, deliberately.** These research targets are about giving the factory a *reasoned* document-store option for the narrow cases where it fits (aggregate-shaped, schema-evolving, read-together data), not about displacing Postgres. The document-vs-relational decision guide should bias toward Postgres and require justification for Mongo, matching the frugality and default-stack posture in CLAUDE.md.
- **Physical multi-tenancy changes the emphasis, not the rule.** Per-tenant isolation already separates data, so `tenantId`-in-every-filter is defense-in-depth (as `access-control-model` already frames its own tenant check), not the sole barrier — read it as a second independent layer, consistent with how the repo treats the equivalent Postgres check.
- **The book predates this repo's stack;** none of its examples are Go-against-this-architecture. Every Go/`mongo-go-driver`, `bson`-tag, tenant-scoping, and shard-key application above is this document's extrapolation of the book's language-agnostic model onto the repo's stack, not text lifted from the book. Multi-document transactions and `$lookup` are supported but are signals to re-examine the document boundaries, not defaults to lean on.
