# The Go Programming Language
**Authors:** Alan A. A. Donovan and Brian W. Kernighan
**Domain:** Software Architecture & Implementation (Go language reference — foundational/canonical)

## Core Concepts

- **Interfaces are implicit, structural contracts, satisfied by possession of methods — never declared.** A type need not name the interface it implements; the compiler checks structurally, at the call site, whether the type's method set covers the interface's method set. This is the single largest design fork between Go and Java/C#-style nominal typing, and it is what makes "accept interfaces, return structs" a coherent idiom rather than a slogan: a function that takes an interface parameter can be satisfied by any concrete type, present or future, without either side importing the other's package. The book builds this idea concretely through `io.Reader`/`io.Writer` — small, one-method interfaces satisfied by dozens of unrelated concrete types across the standard library — and generalizes it into the advice that interfaces should be small and defined close to where they are consumed, since "the bigger the interface, the weaker the abstraction" (a formulation the book attributes to Rob Pike and demonstrates repeatedly).
- **Goroutines and channels implement CSP-style concurrency: "don't communicate by sharing memory; share memory by communicating."** The book teaches this as a design philosophy, not a strict rule — channels are the tool for coordinating independently-executing goroutines (pipelines, fan-out/fan-in, cancellation via a closed "done" channel, multiplexing with `select`), while the `sync` package (`Mutex`, `RWMutex`, `Once`) is presented as the correct, idiomatic tool for protecting a small, in-process critical section of shared mutable state. The book is explicit that both are legitimate; the choice is about which one makes the *particular* piece of coordination clearer, not doctrinal purity.
- **Errors are ordinary values, returned as the last result, never exceptions.** The book's error chapter (5.4) establishes the pattern this whole plugin's `go-error-handling` is built on: a function that can fail returns `(T, error)`, the caller checks `if err != nil` explicitly, and there is no `try/catch`. The book teaches building richer errors by defining types that implement the `error` interface (e.g., `*PathError`-style structs) and inspecting them with type assertions/type switches — the direct ancestor of the `errors.As` pattern the standard library formalized four years after publication (Go 1.13, 2019). Error *wrapping* with `%w` and `errors.Is`/`errors.As` postdate the book; they are the standard library's later formalization of exactly the problem the book identifies (how does a caller inspect a specific failure inside a chain of added context) — see Caveats.
- **Package design: small, focused, well-named, with a clean exported/internal boundary.** The book's guidance on naming is specific and mechanical: package names are short, lower-case, single words with no underscores or mixedCaps; an exported identifier should not repeat its package name (`bytes.Buffer`, not `bytes.BytesBuffer` — "stutter"); a package's doc comment begins `// Package foo ...` and is the package's front door. The `internal/` directory convention (importable only by code rooted at its parent) is treated as a first-class tool for controlling what a module exposes to consumers outside itself.
- **`defer`, `panic`, and `recover` have a narrow, disciplined relationship.** `defer` schedules a call to run when the surrounding function returns, in LIFO order relative to other deferred calls in the same function — the book's running examples are exactly resource cleanup (closing a file, unlocking a mutex) and, notably, using deferred, recovered panics to convert an internal invariant violation into a returned error at a package boundary. The book is explicit that `panic` is for programmer errors and truly unrecoverable situations (an out-of-bounds index, a nil dereference) — not a substitute for an `error` return — and that `recover` is only useful inside a deferred function, and only sensibly used at a boundary (a server's per-request handler, so one bad request doesn't take down the process), never as routine control flow.
- **`net/http`'s actual design is a `Handler` interface plus function-wrapping middleware.** The book (ch. 7.7, building a working web server) demonstrates that `http.Handler` is a one-method interface (`ServeHTTP(w, r)`), that `http.HandlerFunc` adapts a plain function to that interface, and that cross-cutting behavior (the book's example is request counting/logging) is added by writing a function of the shape `func(http.Handler) http.Handler` that closes over the next handler and returns a new one — exactly the pattern chi's and this plugin's middleware chains build on. `http.ServeMux`, the standard library's own router, is shown as basic (prefix and exact-path matching, no path-parameter extraction) — the book does not claim it's sufficient for everything, which is the same gap chi is chosen to close in this plugin.
- **Struct (and interface) embedding is Go's mechanism for composition, and it is explicitly distinguished from inheritance.** The book is careful on this point: embedding promotes an embedded type's methods and fields to the outer type, which *looks* like inheritance syntactically, but there is no dynamic dispatch, no `super`, and no is-a relationship — it is composition with field/method promotion as syntactic sugar. The book's own examples embed for two distinct reasons: reusing an implementation's fields/behavior (embedding `bytes.Buffer` to gain its methods) and building a wider interface out of narrower ones by embedding interfaces inside an interface definition (`io.ReadWriter` embedding `io.Reader` and `io.Writer`). Embedding a concrete type purely to shortcut a decorator (embed to delegate, override a subset of methods) is a third, related use the book also demonstrates.
- **Testing idioms: table-driven tests, `testing.T`/`testing.B`, and `httptest`.** This book is one of the works most credited with cementing the table-driven test as *the* idiomatic Go test structure — a struct literal slice of `{input, want}` cases run in a loop, each reported individually. Chapter 11 covers this pattern directly, alongside benchmark functions (`func BenchmarkX(b *testing.B)`, the `for i := 0; i < b.N; i++` loop) and `httptest.NewServer`/`httptest.NewRecorder` for testing HTTP handlers without binding a real socket.
- **Slices, maps, and their well-known gotchas.** The book spends a full chapter (4) on the reference semantics of slices (a slice header pointing at a shared backing array; `append` may or may not reallocate, and code that assumes in-place mutation propagates across aliases is a classic bug source), the difference between a `nil` slice and an empty (`[]T{}`) one (both have length zero and are safe to range over and append to, but a `nil` slice marshals to JSON `null` while `[]T{}` marshals to `[]` — a frequent API-contract surprise), and maps' explicitly unspecified iteration order (`for k := range m` is intentionally randomized per run so code never accidentally depends on it) plus the rule that writing to a `nil` map panics while reading from one returns the zero value.

## Actionable Techniques

- **Add a compile-time interface-satisfaction assertion at every place a consumer-defined port is implemented.** The book demonstrates forcing a structural-satisfaction check at compile time (`var _ Interface = (*ConcreteType)(nil)`) rather than discovering a missed method only when the code that uses the interface fails to compile somewhere else. `go-repository-pattern`'s `DataAssetRepo` (`internal/infrastructure/postgres/dataasset_repo.go`, lines 33–41) satisfies `domain.DataAssetRepository` purely by having the right methods and is never checked against it directly in the file that implements it — a one-line `var _ domain.DataAssetRepository = (*DataAssetRepo)(nil)` next to the struct definition would catch a signature drift (e.g., a renamed or re-typed method) at the exact file that broke it, rather than at every call site across the application layer. The same applies to every other port implementation in the roster (`OutboxRelay`, `Consumer`, `AccessPolicy` implementations).
- **Preallocate the `records`/`ids` slices in `go-event-publisher`'s `drainOnce`, since the capacity bound is already in hand.** `internal/infrastructure/messaging/outbox_relay.go`'s `drainOnce` (as taught in `go-event-publisher`, lines 87–97) declares `var records []*kgo.Record` and `var ids []uuid.UUID`, then `append`s to both inside a loop bounded by `LIMIT $1` (`r.batch`) — the exact upper bound is already a field on the struct at the point the loop starts. This is precisely the "BAD" pattern `go-performance-optimization`'s own Preallocate Slices and Maps section (lines 102–109) warns against and shows the fix for (`make([]*kgo.Record, 0, len(rows))`) — the fix here is `make([]*kgo.Record, 0, r.batch)` / `make([]uuid.UUID, 0, r.batch)`. This is not a correctness bug (both slices work fine as nil-then-appended), but it is a concrete instance of the plugin's own stated allocation-awareness standard not being applied to a loop where the size hint costs nothing to use — the kind of finding the book's slice-growth chapter (4.2.1, on `append`'s reallocation behavior) exists to make visible.
- **Name the standard library's function-wrapping middleware pattern explicitly in `go-middleware`'s Purpose or Ordering section**, citing it as the same shape `net/http` itself uses (not just a chi convention) — currently the skill correctly *implements* `func(http.Handler) http.Handler` middleware but never states that this is the standard library's own idiom (the book's ch. 7.7 logging-middleware example is the direct ancestor), which would strengthen the skill's authority independent of chi as a specific router choice.
- **Add a one-line package doc comment convention (`// Package postgres implements...`) to `go-project-structure`'s package-naming guidance.** The skill's naming table (lines 90–99) and Output Format both reference `doc.go` files as an artifact but the skill body never states the book's convention that a package's doc comment is a complete sentence beginning `// Package <name>` and is the package's front door for `go doc`/pkg.go.dev-style discovery — a small, mechanical addition consistent with the rest of the naming table.
- **State explicitly, in `go-error-handling`, that `%w`/`errors.Is`/`errors.As` are Go 1.13 additions that formalize (rather than originate) the book's error-inspection guidance** — useful context for anyone using this book as a reference alongside the skill, so the two are read as consistent rather than as the skill silently diverging from "the" canonical Go text.
- **Reference "table-driven test" as the named pattern it is** (it already appears as a heading in `go-unit-test`, but citing that this exact structure is the one the language's own reference book popularized would strengthen the skill's grounding when read against this source).

## Key Terminology

Checked against `skills/glossary-management/references/ubiquitous-language.md` in full before proposing anything:

- **Table-Driven Test** — a single test function driving a table (slice of struct literals) of `{input, want}` cases through a loop, each run as a named subtest. Not currently a glossary entry, despite the Testing and Quality section already carrying granular, parallel-structured entries (`Given/When/Then`, `Scenario`, `Feature File`, `Unit Testing`). This pattern is explicitly named as a section heading in `go-unit-test` and is the default shape of nearly every unit test example across the Go skill roster — a real, consistently-used term with no existing near-synonym in the glossary. **Proposed as a genuine addition** given both its absence and its consistent, repeated use.
- **Structural Typing / Implicit Interface Satisfaction** — the property that a Go type satisfies an interface by possessing its methods, with no explicit declaration of intent (no `implements` keyword). Considered but **not proposed**: this is a language-mechanics term rather than a cross-artifact business or architecture term of the kind the rest of the glossary's Design Principles section carries (`SOLID`, `Separation of Concerns`), and the concept is already fully explained in prose wherever it matters (`go-project-structure`'s Minimalist Interfaces section). Worth reconsidering only if a future skill needs to reference the concept by name outside a Go-specific context.
- **Escape Analysis** — the compiler's determination of whether a value can be stack-allocated or must be heap-allocated, based on whether a reference to it outlives the function that created it. Already used as a tag and section heading in `go-domain-model` and `go-performance-optimization`; considered but **not proposed** for the same reason as structural typing — a Go-compiler-internals term, not a term this repo's artifacts (vision statements, ADRs, feature files) would ever need to use outside the two Go skills that already define it in-line.

## Caveats

- **This book is temporally bounded in ways that matter and are worth stating plainly, not treated as silent gaps.** Published in 2015, it predates: generics (Go 1.18, 2022 — so it has nothing to say about `go-project-structure`'s "Where Generics Belong" section, which is correctly informed by later Go idiom rather than this book); error wrapping and `errors.Is`/`errors.As` (Go 1.13, 2019 — the book's error-inspection guidance is type assertions/switches on custom error types, which `go-error-handling` correctly supersedes rather than contradicts); and per-iteration `for`-loop variable semantics (Go 1.22, 2024 — the book's original closures-over-loop-variables gotcha, and the `tt := tt` workaround it implies, is exactly what `go-concurrency-patterns` and `go-unit-test` correctly flag as now-obsolete). None of these are defects in the skills; they are places the skills have correctly moved past what this book, however authoritative, could have said in 2015.
- **Despite those boundaries, the book is authoritative and largely unchanged where it matters most for this roster: interfaces, `defer`/`panic`/`recover`, slices/maps, the `testing` package's core shape, and `net/http`'s fundamental `Handler` design.** These are the parts of the language that have not changed since 1.0, and they are exactly the parts this cluster's 24-skill Go roster gets right — the majority of findings in this pass are confirmations (interfaces correctly small and consumer-defined, `defer` LIFO correctly relied on for shutdown ordering, the nil-slice/JSON-`omitempty` interaction correctly avoided, table-driven tests correctly structured) rather than gaps.
- **The two genuinely concrete, non-citation findings are narrow and low-risk, not systemic.** The missing compile-time interface assertions and the un-preallocated batch slices in `go-event-publisher` are both small, mechanical fixes with no design implications — unlike, for example, a missing methodology (DDD, Event Storming) would be. Treat them as worth a small edit each, not as evidence the Go skill set needs deeper rework.
- **This book has nothing to say about the architecture-level concerns most of this roster's depth actually comes from** — DDD Aggregates, CQRS, the Transactional Outbox, idempotent consumers, multi-tenancy, ABAC — because those are patterns layered on top of the language, not language features. Where this book is silent, that silence is expected and correct: it is a language reference, not a distributed-systems or DDD text, and the 24 skills' depth in those areas comes from elsewhere in this research cluster and from the architecture/DDD skill domains directly.
- **Calibration note, consistent with this cluster's other research files:** most individual findings here are confirmations of already-correct idiom, precisely because this book covers language fundamentals a mature, production-grade Go skill set should already have gotten right — and, per the read of all 24 skills, mostly has. The value of this pass is in the handful of concrete, checkable items above, not in a broad rewrite.
