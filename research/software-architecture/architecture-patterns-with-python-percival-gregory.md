# Architecture Patterns with Python
**Authors:** Harry Percival & Bob Gregory
**Domain:** Software Architecture — DDD, TDD, and application patterns in Python ('Cosmic Python')

> Source note: synthesized from working knowledge of the book (widely known as *Cosmic Python*), not from the physical text. The patterns it teaches — Domain Model, Repository, Unit of Work, Service Layer, dependency inversion / ports-and-adapters, domain events + message bus — are stable, well-documented public content and the book's running example (an allocation/order-line domain) is its own canonical illustration. Chapter groupings below are approximate signposts, not verified citations; no quotes or page numbers are invented.

## Core Concepts

- **The Domain Model comes first, and stays free of infrastructure (Part I).** The book's opening move is to build a rich domain model — entities with identity and mutable state, immutable value objects, and an *Aggregate* that owns a consistency boundary — in plain Python objects with **no** imports from the database, the web framework, or any I/O. In the running example a `Product` Aggregate owns its `Batch` entities and enforces the allocation invariant across them; the Aggregate is the only object outside code allowed to mutate, and its root method (`allocate`) is where the invariant lives. Value objects are modeled as frozen dataclasses (`@dataclass(frozen=True)`, equality by value); entities are ordinary classes with identity-based equality. This "domain model is a plain-object island" stance is the book's foundation for everything that follows.

- **The Aggregate is the transactional consistency boundary — one Aggregate, one lock, one version (Ch. 7).** The book is explicit that Aggregates exist to answer "what set of objects must be consistent with each other, and therefore change together inside one transaction?" It pairs this with an optimistic-concurrency `version_number` bumped on every state change, so two concurrent transactions touching the same Aggregate collide instead of silently interleaving — the Python-side twin of the CAS-on-`version` discipline this repo's `go-repository-pattern` already mandates.

- **Repository abstracts persistence — and its real payoff is a fake for tests (Ch. 2).** The Repository is an object that pretends to be an in-memory collection of Aggregates (`.add()`, `.get()`), hiding SQL/ORM behind an abstract interface (an `abc.ABC` in the book; a `typing.Protocol` is the more structural, Go-interface-like alternative). The book's most-cited justification is *testing leverage*: because the port is an abstraction, a `FakeRepository` backed by a `set` is a three-line drop-in, so the service and domain layers get fast, database-free unit tests, while the real SQLAlchemy/`asyncpg` repository is exercised only by a small number of integration tests. The abstraction earns its keep at the test seam, not just as decoupling for its own sake.

- **Unit of Work wraps repositories in one atomic boundary, exposed as a context manager (Ch. 6).** The Unit of Work (UoW) is the book's answer to "who owns the transaction?" It is a context manager (`with uow:` / `async with uow:`) that opens a session/transaction on enter, exposes the repositories inside it, and **rolls back by default on exit unless the caller explicitly `commit()`s**. This makes the atomic consistency boundary a first-class, visible object rather than a transaction scattered across the code — and gives tests a `FakeUnitOfWork` just as easily as a fake repository.

- **The Service Layer holds use-case orchestration; handlers stay thin (Ch. 4).** A service-layer function is one use case ("allocate this order line"): it takes primitives/DTOs, opens the UoW, loads the Aggregate through the repository, calls a domain method, commits, and returns. The web framework (Flask in the book; FastAPI here) does nothing but parse the request, call the service function, and serialize the result — Percival & Gregory show the same allocation flow driven identically from an HTTP handler, a CLI, and a test, precisely because none of the logic lives in the handler. This is the direct Python analog of this repo's `go-service-layer` five-step discipline (idempotency → load → authorise → domain call → save).

- **Dependency inversion / ports-and-adapters: abstractions in the domain, implementations at the edge (Part II).** The book frames the whole architecture as the Dependency Inversion Principle applied at module scale: the domain and service layers depend only on *abstractions* (Repository, UoW, and later a message bus), and concrete adapters (SQLAlchemy, Redis/Kafka, Flask) depend inward on those abstractions — never the reverse. Dependencies are supplied by explicit injection (a composition-root `bootstrap` function wiring real adapters, or fakes in tests) rather than imported directly by the code that uses them. Ports are expressed as `abc.ABC` or `typing.Protocol`; the book leans toward duck-typed/Protocol satisfaction over deep inheritance trees.

- **Domain events + a message bus decouple side effects; commands and events are different (Part II, Ch. 8–11).** The domain model raises **events** (`Allocated`, `OutOfStock`) as plain dataclasses recorded on the Aggregate; a **message bus** dispatches each event to one or more handlers. The book draws a sharp distinction: a **Command** is an imperative sent to exactly one handler and *may* fail loudly (the caller wants the outcome); an **Event** is a statement of fact broadcast to zero-or-more handlers, each of which fails independently without breaking the caller. This is the internal, in-process cousin of this repo's Redpanda outbox/consumer story — the same command-vs-event semantics, one process earlier.

- **Testing philosophy: prefer fakes over mocks, and test at the highest gear you can (throughout).** The book argues against mock-heavy tests that assert on *how* code calls its collaborators (brittle, coupled to implementation) in favor of **fakes** — real, simple in-memory implementations of the same port — asserting on *state and outcomes*. It advocates "edge-to-edge" / "high-gear" tests that drive a whole use case through the service layer against fakes, dropping into low-gear per-object unit tests only where the logic is genuinely intricate, and reserving slow integration tests for the adapters themselves — a concrete Test Pyramid the fake-based ports make cheap to build.

## Actionable Techniques

- **Model the Aggregate root as the only mutation entry point.** Give the root the invariant-enforcing method (`Product.allocate(line)`), keep child entities and value objects reachable only through it, and carry a `version_number` bumped inside that method so optimistic concurrency has something to collide on.

- **Define every port as a `typing.Protocol` in the domain/service layer, implement it at the edge.** Structural typing means the `asyncpg` repository never imports or subclasses the port — it just matches its shape — which is the closest Python gets to Go's implicit interface satisfaction and keeps the dependency arrow pointing inward. Reserve `abc.ABC` for when you want an explicit base with shared helper code.

- **Make the Unit of Work an async context manager that defaults to rollback.** `__aexit__` rolls back unless `commit()` was called; the service function's happy path ends in an explicit `await uow.commit()`. This turns "did we forget to commit?" and "did an exception leave a half-written transaction?" into structurally-answered questions.

- **Write a `FakeRepository` (set-backed) and `FakeUnitOfWork` (no-op commit) first.** Drive the service layer's unit tests entirely through them so the domain/service tests never touch Postgres; let `testcontainers` integration tests cover only the real adapter. This is the book's single biggest day-to-day payoff and the reason the ports exist.

- **Collect events on the Aggregate, drain them through the message bus after commit.** The Aggregate appends events to a `self.events` list; the UoW/service collects them post-commit and hands them to the bus, which routes each to its handler(s). Keep the handler map explicit (`{Allocated: [publish_to_external, ...]}`) so the wiring is readable, not magical.

- **Raise domain-specific exceptions inside the model and translate them once, at the transport boundary.** `class OutOfStock(DomainError)` raised deep in the Aggregate; a single FastAPI `@app.exception_handler(DomainError)` maps the domain exception family to HTTP status codes — the handlers themselves never build error responses. `raise ... from cause` preserves the chain (`__cause__`), Python's analog of Go's `%w` wrapping.

## Key Terminology

- **Aggregate** — a cluster of domain objects with a single root, treated as one unit for consistency and persistence; the transactional boundary. (Already canonical in this repo's Ubiquitous Language — the book grounds the Python-side modeling of it.)
- **Unit of Work** — an object owning a single atomic transaction, exposing repositories inside it and committing/rolling back as one; here a context manager that defaults to rollback. Candidate glossary addition — it is the named seam `python-service-layer` will reference directly.
- **Service Layer** — the use-case orchestration layer between the transport edge and the domain model; one function per application use case.
- **Message Bus** — an in-process dispatcher routing commands (one handler) and events (zero-or-more handlers) to their handlers, decoupling side effects from the code that triggers them.
- **Fake (vs. Mock)** — a real, simple in-memory implementation of a port used in tests, asserted against by state/outcome, as opposed to a mock asserted against by call expectations. Worth distinguishing in the testing glossary cluster from `Test Fixture`.

## Caveats

- **Confidence, overall:** high on the book's headline patterns (Domain Model, Repository, Unit of Work, Service Layer, dependency inversion / ports-and-adapters, domain events + message bus, fakes-over-mocks, high-gear testing) — these are the book's well-known, widely cited contributions and are stable public content. Lower confidence on exact chapter numbers and topic ordering; the chapter references above are approximate signposts, not verified against the physical text.

- **Python's encapsulation is weaker than Go's, and the book is honest about it — but does not fully solve it.** Go enforces private fields at compile time (unexported = unreachable from another package); Python offers only `_single_underscore` (pure convention, unenforced) and `__double_underscore` name-mangling (weakly enforced, trivially bypassed). So an Aggregate that in Go *cannot* have its invariant bypassed by external mutation can, in Python, always be reached around by a determined caller. The book leans on frozen dataclasses for value objects (genuine immutability) but for entity/Aggregate encapsulation it relies on discipline and code review, not the compiler. Every `python-domain-model` artifact should state this gap plainly rather than imply parity with `go-domain-model`.

- **Duck typing / `Protocol` satisfaction is structural but unchecked at runtime.** A `typing.Protocol` port is only verified if `mypy`/`pyright` runs — nothing at runtime stops a wrong-shaped object from being injected, unlike Go where interface satisfaction is a compile error. This makes the static type-check step a *required* part of the toolchain for these skills (as the Halstead file already argues for the roster generally), not an optional nicety; the ports-and-adapters guarantee is only as real as CI's type gate.

- **The book uses Flask + SQLAlchemy synchronously; this repo's stack is FastAPI + `asyncpg`, async and ORM-free.** The patterns are framework- and sync/async-agnostic — Repository, UoW, Service Layer, and the message bus all translate directly — but the *code* must be adapted: UoW and repository become `async with`/`await`, the SQLAlchemy Session becomes an `asyncpg` connection/transaction (this repo deliberately avoids the ORM — see the Halstead file's Actionable Techniques), and the book's synchronous message bus becomes async dispatch. Treat every book code snippet as pattern illustration, not a copy-paste source.

- **The book's message bus is in-process; this repo also has a real cross-service broker (Redpanda).** Cosmic Python's events/commands live inside one Python process. This repo's outbox/consumer story (`go-event-publisher`/`go-event-consumer` and their `python-*` mirrors) is the *cross-process* layer. The two are complementary — in-process events can trigger an outbox write that a broker later delivers — but the book only covers the in-process half, and conflating the two would blur a real architectural boundary.

- **Not a multi-tenant or security text.** The book's allocation example is single-tenant with no authorization concern. Per-tenant isolation, ABAC, and the `tenant_id`-in-every-query rule this product requires are additions from this repo's own security skills, not content the book provides — its patterns are the *carrier* for those concerns (tenant scoping lives in the repository; authorization in the service layer), but the concerns themselves come from elsewhere.
