# 100 Go Mistakes and How to Avoid Them
**Authors:** Teiva Harsanyi
**Domain:** Software Architecture & Implementation (Go, anti-pattern catalog / practitioner level)

## Core Concepts

The book's premise is structural, not narrative: twelve chapters, each a category of real-world Go pitfall (code/project organization, data types, control structures, strings, functions and methods, error management, concurrency foundations, concurrency in practice, the standard library, testing, and optimization), with each mistake given a wrong/right code pair and a short rule of thumb. That shape is unusually well suited to checking against this repo's 24 Go skills, since every one of them already carries its own `## Anti-Patterns` section in the same wrong-thing/why-it's-wrong register. The check below goes category by category, citing exact lines read.

- **Interface pollution (ch. 2).** Harsanyi's core claim: define interfaces on the consumer side, keep them small, and don't produce an interface "just in case." `go-project-structure` (`skills/go-project-structure/SKILL.md:103-131`) states this almost verbatim as "Minimalist Interfaces (consumer-defined)" — interfaces live in `internal/domain/ports.go` (the consumer/application side), the `postgres` implementation "does NOT declare the interface; it just satisfies it structurally" (line 122), and the rule of thumb is lifted straight from the Go proverb Harsanyi also cites: "the bigger the interface, the weaker the abstraction" (line 105). This is confirmed as an already-correct, already-cited pattern — not a gap.
- **Returning interfaces, accepting interfaces (ch. 6, "functions and methods").** A related mistake Harsanyi calls out separately: a constructor should return a concrete type, and a function should accept the narrowest interface it needs. `go-repository-pattern`'s `NewDataAssetRepo` returns `*DataAssetRepo` (a concrete pointer), and `go-service-layer`'s `NewClassifyDataAssetHandler` accepts `domain.DataAssetRepository`, `domain.AccessPolicy`, `IdempotencyStore` — all consumer-defined interfaces, none producer-defined. Both halves of this mistake are already handled correctly and consistently across every constructor read.
- **Slice/array copy semantics and `append`'s capacity-sharing gotcha (ch. 3, data types).** Harsanyi's canonical trap: appending to a re-sliced sub-slice (`s := full[2:4]; s = append(s, x)`) can silently overwrite `full`'s backing array because the sub-slice shares capacity with its parent. No skill's worked examples exhibit this shape — every `append` call read (`go-event-publisher`'s `records = append(records, r.toRecord(ctx, m))`, `go-performance-optimization`'s preallocation example, `go-chi-handler`'s validation-error accumulation) grows a freshly declared `nil` or `make`d slice, never a re-slice of an existing one. One example is worth confirming explicitly as *correct on the exact axis this mistake concerns*: `go-domain-model`'s `PullEvents` (`skills/go-domain-model/SKILL.md:69-73`) does `e := a.events; a.events = nil; return e`. Setting `a.events` to `nil` — not `a.events[:0]` — means the next `recordEvent` call allocates an entirely new backing array; it does not silently corrupt the slice of events the repository is mid-draining into the outbox. Had this been written `a.events = a.events[:0]`, it would be a textbook instance of Harsanyi's mistake. It wasn't. This is a genuine, checkable non-gap, not just an absence.
- **Loop variable capture in goroutine closures (ch. 8/9, concurrency).** Pre-Go-1.22, `for _, v := range xs { go func(){ use(v) }() }` captures one shared `v` across every goroutine — Harsanyi's most-cited mistake, and probably the single most common real-world Go bug of the pre-1.22 era. This repo has already retired it explicitly, twice: `go-concurrency-patterns` anti-patterns (`skills/go-concurrency-patterns/SKILL.md:195`) — *"`tt := tt` / `it := it` loop-variable copies — dead weight on Go 1.22+, where loop variables are per-iteration. Their presence signals an unported pre-1.22 habit"* — and `go-unit-test` (`skills/go-unit-test/SKILL.md:70`, and again at line 186) states the identical rule for table-driven subtests. Cross-checked against `go-dockerfile`'s pinned build image, `golang:1.23-bookworm` (`skills/go-dockerfile/SKILL.md:35`) — one minor version past the fix (1.22) — the mistake is confirmed **not a live risk** for this codebase, and the skills correctly say so rather than silently omitting a now-irrelevant warning or, worse, still including the `tt := tt` workaround as if it were still needed.
- **`context.Context` propagation and storage (ch. 2/8).** Harsanyi's rule: `ctx` is always the first parameter, never stored on a struct. Checked across every layer read — `go-chi-handler` passes `r.Context()` explicitly (never `context.Background()`, called out as an anti-pattern at line 217); `go-service-layer`'s `Handle(ctx context.Context, cmd ...)`; `go-repository-pattern`'s every method `(ctx context.Context, ...)`; `go-event-consumer`'s `Run(ctx context.Context)` and `handleRecord(ctx context.Context, rec *kgo.Record)`; `go-event-publisher`'s `OutboxRelay.Run(ctx context.Context)`. No struct in any of the 24 skills — not `OutboxRelay`, not `Consumer`, not any handler — carries a `ctx` field. This is uniform and correct throughout; a genuine non-gap.
- **Improper error wrapping (ch. 7, error management — the book's largest single chapter).** Harsanyi's specific mistakes here: losing the chain via `%v` or `errors.New(err.Error())` instead of `%w`; comparing with `==` instead of `errors.Is`; leaking an internal error type across a boundary; over-wrapping until the message is noise. `go-error-handling` addresses every one of these by name: `%w` exactly once per wrap (`skills/go-error-handling/SKILL.md:52-56`), `err == ErrNotFound` listed as an anti-pattern (line 196), boundary translation of `pgx.ErrNoRows` → `domain.ErrNotFound` demonstrated concretely in `go-repository-pattern` and cited back in `go-error-handling` (lines 118-121), and "wrapping with no added context" listed as its own anti-pattern (line 198) with the exact noisy-chain example Harsanyi uses (`"error: error: error: connection reset"`). There is no sibling research file for *The Go Programming Language* (Donovan/Kernighan) in this cluster to cross-reference against, but on its own terms this is the deepest, most complete non-gap in the check — the skill is arguably more rigorous than the book's chapter, since it also formalizes `errors.Join` for combining independent operational failures (`skills/go-error-handling/SKILL.md:139-143`), a Go 1.20 addition that shipped after the book's 2022 print date.
- **Nil concrete type stored in a non-nil `error` interface (ch. 7's most famous single mistake).** This is Harsanyi's headline example: a function that declares `var e *MyError` and does `return e` at the end returns a non-nil `error` interface (because the interface's type word is set, even though the value word is nil) — `if err != nil` is true even though `e` itself was never assigned. **This mistake is not named anywhere across the 24 skills** — not in `go-error-handling`'s Anti-Patterns, Quality Criteria, or the sentinel/typed-error sections; not in `go-service-layer`'s `Handle(...) error` return convention; not in `go-repository-pattern`'s error-returning methods. No worked example actually *exhibits* the bug — every error-returning function read constructs its error inline with `fmt.Errorf` or returns a pre-declared package-level sentinel, never a locally-typed pointer left nil on some path — so this is not a live code defect. But it is a genuine, checkable documentation absence for one of the two or three most-cited Go footguns in the language, in a skill file whose entire purpose is to be "the cross-cutting standard every other backend skill follows" (`skills/go-error-handling/SKILL.md:9`). See Applies To below.
- **Goroutine leaks (ch. 8/9).** Harsanyi's chapter frames this as "a goroutine with no exit is a leak, and a leak is a slow outage" — nearly the exact sentence `go-concurrency-patterns` opens with (`skills/go-concurrency-patterns/SKILL.md:22`: *"A goroutine with no owner and no exit is a leak; a leak is a slow outage"*). The skill's three-question ownership check (who owns it / when does it exit / how do errors propagate, lines 30-34), its dedicated Leak Prevention Checklist (lines 167-174), and its explicit "Orphan goroutines" anti-pattern all match the book's treatment point for point, and the worked `errgroup`/worker-pool examples are leak-proof by construction (every `g.Go` closure selects on `gctx.Done()` or a closed channel). Confirmed non-gap, and arguably more systematic than the book's scattered per-example treatment.
- **Non-deterministic resource cleanup — missing/mis-placed `defer Close()` (ch. 6/7).** Harsanyi warns specifically about `defer` inside a loop (each iteration's deferred call doesn't run until the *function* returns, not the loop iteration, so N iterations pile up N open resources). Checked `go-repository-pattern`'s `Save` (named return `(err error)` + a single `defer tx.Rollback(ctx)` outside any loop, `skills/go-repository-pattern/SKILL.md:82-92`) and `go-event-publisher`'s `drainOnce` (`skills/go-event-publisher/SKILL.md:69-113`): the latter explicitly does **not** defer `rows.Close()` — it calls it manually on the early-return error path inside the loop (line 92-93) and again after the loop ends (line 98), which is the *correct* avoidance of exactly the defer-in-a-loop trap, not an accidental omission. This is worth flagging as a subtle, correct pattern rather than a bug at first glance. The named-return-plus-deferred-rollback idiom in `Save` is also precisely the one case Harsanyi endorses named result parameters for (he otherwise warns against them for ordinary functions) — a second point of confirmation, not just an absence of the mistake.
- **Table-driven tests and `t.Parallel()` (ch. 11, testing).** `go-unit-test` matches the book's table-driven shape exactly (name/inputs/want struct slice, `t.Run` per case) and goes further than the book on one subtlety Harsanyi does not cover: a parent test's `defer` fires *before* its `t.Parallel()` subtests actually run (the parent returns immediately once it spawns them), so shared teardown must use `t.Cleanup` instead (`skills/go-unit-test/SKILL.md:148`). This is a real, non-trivial Go testing gotcha the skill documents that the book itself doesn't reach. Confirmed non-gap, exceeding the source.
- **Optimization mistakes (ch. 12).** Harsanyi's chapter: don't optimize without a benchmark, prefer `strings.Builder` over loop concatenation, preallocate when size is knowable, watch allocations via `-benchmem`, use `sync.Pool` only for profiled hot paths. `go-performance-optimization` reproduces this chapter's structure almost section-for-section: the "measure first" workflow (lines 21-24, 159-166), `strings.Builder` with `b.Grow` (lines 114-123), slice/map preallocation with the exact bad/good pair style the book uses (lines 98-112), `sync.Pool` gated on profile justification with the reset-before-put/no-retain-after-put rules (lines 125-145), and `unsafe` gated behind a benchmark-and-review requirement the book doesn't go as far as (lines 153-155). `go-performance-test` extends this into CI-gated regression tracking with `benchstat`, a concern the book raises only in passing. Confirmed non-gap; this pairing is the most thoroughly covered category in the whole check.
- **Standard-library timer leak — `time.After` inside a loop (ch. 10, standard library).** A narrower, less commonly cited Harsanyi mistake worth surfacing: calling `time.After(d)` inside a `for`/`select` loop allocates a fresh `time.Timer` on every iteration, and pre-1.23 that timer is not eligible for garbage collection until it actually fires — so a loop that keeps returning via the other `select` branch (e.g., `ctx.Done()`) leaks a live timer per iteration until each one's `d` elapses. `go-event-consumer`'s `withRetry` (`skills/go-event-consumer/SKILL.md:147-163`) does exactly this: `select { case <-ctx.Done(): ...; case <-time.After(sleep): }` inside a `for` retry loop. Under Harsanyi's 2022-vintage Go (~1.18/1.19), this would be flagged as a real, if minor, leak risk. But Go 1.23's runtime change — timers become collectible as soon as they're unreachable, independent of whether `Stop` was called — closes exactly this gap, and this repo's `go-dockerfile` pins `golang:1.23-bookworm`. This is the second instance (after loop-variable capture) of a book-documented Go mistake whose severity is version-gated rather than fixed by the skill's own code, and the pattern is legitimate practice at 1.23+ even though it would not have been in the book's own Go version. Worth a one-line acknowledgment, not a rewrite.

## Actionable Techniques

- Add one sentence and one anti-pattern bullet to `go-error-handling` naming the nil-concrete-in-interface footgun explicitly, with the canonical counter-example: a function declaring `var e *ValidationError` (or any locally-typed pointer) and returning it as the function's `error` result is non-nil even when `e` was never assigned, because the interface's type word is set independent of its value word. The fix this repo's own conventions already imply (return `nil` explicitly for the no-error path; never a naked typed-nil variable) should be stated as a rule, not left implicit. This is a one-paragraph addition to a skill that already exists — not a new skill.
- Add a short note to `go-domain-model`'s `PullEvents` explaining *why* `a.events = nil` (not `a.events[:0]`) is written the way it is — currently the code is correct but silent about the hazard it's avoiding. One sentence turns an accidental correctness into a documented decision, and gives future contributors editing this method the context to not "simplify" it into the capacity-sharing bug.
- Add a one-line comment to `go-event-consumer`'s `withRetry` acknowledging that `time.After` inside the retry loop is safe specifically because the pin to Go 1.23+ (`go-dockerfile`) makes per-iteration timers GC-eligible without `Stop` — mirroring the precedent `go-unit-test` and `go-concurrency-patterns` already set for the loop-variable-capture fix (state *why* a historically-flagged pattern is fine now, rather than leaving future readers to wonder if it was missed).
- No change needed to `go-project-structure`, `go-repository-pattern`, `go-concurrency-patterns`, `go-error-handling`'s wrapping/translation content, `go-unit-test`'s table-driven/parallel content, or `go-performance-optimization` — cite these as confirmed-correct against the book's corresponding chapters rather than editing them.

## Caveats

- **This check found exactly one real, unaddressed documentation gap of consequence — the nil-interface footgun in `go-error-handling` — and no code defects.** Every worked example read across all 24 skills was checked line-by-line against the book's ten most-cited mistakes (the eight the task named plus two more surfaced in the process — the return-concrete-accept-interface half of interface pollution, and the `time.After`-in-loop timer question). None of them exhibit the bug the mistake describes. This is a strong, honest result for a 24-skill, production-grade Go implementation — it should not be read as "the book found nothing," but as "the book's headline mistakes are already systematically avoided, and the one gap found is a documentation absence in the standard-setting skill, not a bug anyone shipped."
- **Two findings are explicitly version-gated, and the skills already handle one of the two correctly.** Go 1.22 retired the loop-variable-capture bug, and `go-concurrency-patterns`/`go-unit-test` both say so explicitly with the correct version number, rather than either silently dropping a stale warning or silently keeping an unneeded `tt := tt` workaround. Go 1.23 (the version this repo's `go-dockerfile` actually pins) additionally made unreachable timers GC-eligible without an explicit `Stop`, which quietly closes the `time.After`-in-a-retry-loop concern in `go-event-consumer` — but nothing in that skill says so. The asymmetry between these two cases (one explicitly justified, one silently safe-by-luck) is itself the actionable finding, not the underlying mistake.
- **No skill in this roster explicitly states the `go.mod` `go` directive version.** The Go 1.23 signal used throughout this document comes entirely from `go-dockerfile`'s pinned build image (`golang:1.23-bookworm`) — `go-project-structure` and `go-makefile`, the two skills that would be the natural home for a `go.mod`/toolchain version statement, don't mention one. This is a minor observation, not a defect worth its own remediation row: the inferred version is consistent everywhere it matters (both version-gated findings above check out against 1.23), but a future skill update that changes the Dockerfile's pinned Go version without a corresponding audit of these two version-dependent notes would silently invalidate them.
- **The book's own age (2022, Go ~1.18/1.19) is itself the interesting variable.** A meaningful fraction of what would have been findings against an older Go codebase are not findings here specifically *because* the runtime and language moved past the mistake in the intervening four Go releases (1.20's `errors.Join`, 1.22's per-iteration loop variables, 1.23's timer GC) — and this repo's skills already reflect that later state rather than the book's. Treat every "confirmed non-gap" in this document as time-qualified: correct against Go 1.23 as pinned today, not a permanent property of the pattern.
- **Interface pollution and the return-concrete/accept-interface convention are the strongest, most explicit non-gaps in the whole check** — both are not just absent-of-the-mistake but positively, explicitly stated in `go-project-structure` using close to the book's own vocabulary. This is worth reading as confirmation that the skill's author(s) already internalized this specific book's central chapter, whether or not this book was consulted directly when the skill was written.
