# API Design Patterns
**Authors:** JJ Geewax
**Domain:** API Design (REST/resource-oriented API contracts)

## Core Concepts

- **Resource-oriented design with a fixed set of standard methods (Part 2, Ch. 6-11).** The book's central organizing idea is that an API should be modeled as a set of *resources* (nouns) manipulated by a small, closed set of *standard methods*: List, Get, Create, Update, Delete (plus a few others like Undelete). This is the same resource-over-verb philosophy `skills/api-contract-design/SKILL.md` already states in its Resource Naming section ("Resources are named after domain concepts... not after database tables or implementation concepts") and its HTTP-Method-to-Command/Query mapping table (`POST`→Create/Command, `PUT`/`PATCH`→Update/Command, `DELETE`→Delete/Command, `GET`→List-or-Get/Query). The two frameworks line up closely: the skill's mapping table is effectively Geewax's standard-methods list expressed as an HTTP-verb table instead of a named-method list.
- **Custom methods for state transitions that don't fit clean CRUD (Ch. 11).** Geewax's standard methods deliberately do not cover every operation an API needs — actions like "cancel an order," "publish a document," or (in this repo's domain) "classify a data asset" are not create/read/update/delete in any honest sense. His answer is a *custom method*: a resource-scoped action expressed as `POST /{resource}:customVerb` (colon-suffixed verb on a resource or collection, e.g. `POST /documents/123:publish`), explicitly reserved for the (hopefully rare) case where forcing the action into a standard method or into a field update on the resource would be a worse contortion than naming a verb. Critically, Geewax's guidance is not "avoid verbs" — it is "prefer standard methods and only reach for a custom method when the operation genuinely isn't a resource-state update," and even then the custom method is still resource-scoped (`resource:verb`), never a bare free-floating RPC endpoint.
- **Long-running operations as a first-class `Operation` resource (Ch. 13, "Standard fields," and the LRO chapter).** For any request whose work cannot complete within a normal synchronous request/response cycle, Geewax specifies a standard `Operation` resource pattern: the triggering call returns immediately with an `Operation` object carrying (at minimum) a unique operation name/ID, a `done: boolean` field, and — once `done` is true — either a `response` field (the actual result, shaped like the resource that would have been returned synchronously) or an `error` field (a structured error, same shape as the book's standard error model). Clients poll `GET /operations/{id}` until `done` is true. This is a fully specified, reusable resource shape — not just "return 202 and a Location header."
- **A single standard error model modeled on `google.rpc.Status` (Ch. 15, "Errors").** Geewax specifies one canonical error shape for every error response: a machine-readable `code` (drawn from a small, fixed enum of canonical error categories — e.g. `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `FAILED_PRECONDITION`, `RESOURCE_EXHAUSTED`, `INTERNAL`, `UNAVAILABLE` — the `google.rpc.Code` enum this book's error chapter is explicitly aligned with), a human-readable `message`, and a repeated `details` field holding structured, typed error-detail objects (e.g., a `BadRequest` detail listing per-field violations, a `QuotaFailure` detail, a `RetryInfo` detail with a suggested backoff). The `code` in Geewax's model is a small fixed enum shared across every API and every error, not a free-form per-endpoint string.
- **Versioning as a last resort, with a strong bias toward additive, backward-compatible evolution (Ch. 2, "Versioning").** Geewax's default posture is that a major-version bump is an expensive, disruptive event to be avoided wherever possible: prefer adding new optional fields, new resources, and new custom methods over breaking existing ones, and treat "unknown fields are ignored by well-behaved clients" as the working assumption that makes most schema growth non-breaking. When a version bump is genuinely unavoidable, he discusses both path-based (`/v1/`, `/v2/`) and header-based approaches, and leans toward keeping the *whole API* on one version identifier (bumped rarely, for the API as a whole) rather than per-resource or per-field versioning — but does not prescribe one transport mechanism (path vs. header) as uniquely correct; he treats it as a project-level convention choice as long as it's applied consistently and the API commits to a real deprecation runway once a version is cut.
- **Resource revisions / ETags for optimistic concurrency (Ch. 13, "Resource revisions").** For resources that can be concurrently modified by multiple clients, Geewax specifies a standard pattern: the server returns a revision identifier (an `etag` field or equivalent) with every resource representation; a client wishing to perform a safe conditional update sends that revision back (`If-Match` header, or an `etag` field in the update request) and the server rejects the update with a conflict if the resource has changed since the client last read it. This is distinct from ordinary `409 Conflict` business-rule violations — it's specifically about detecting lost updates from concurrent writers.
- **Field masks for partial updates and partial responses (Ch. 13, "Partial updates" / "Partial responses").** Geewax specifies a `updateMask` (or `fieldMask`) parameter on Update requests — a list of field paths the client intends to change — as the standard mechanism for expressing "update only these fields" precisely, distinct from `PATCH`'s ambiguity about whether an omitted field means "leave unchanged" or "set to the zero value." A parallel `readMask`/response field mask lets `GET`/`List` callers request only a subset of fields on large resources.
- **Singleton sub-resources for one-per-parent settings-like resources (Ch. 8-9).** For a resource that always has exactly one instance per parent (e.g., a "config" or "settings" object hanging off a parent resource, with no independent create/delete lifecycle), Geewax names this the singleton sub-resource pattern: no List, no Create, no Delete — only Get and Update, addressed at a fixed path under the parent (e.g. `/data-assets/{id}/classification` if classification were modeled as a singleton rather than a state field). This is a narrower, more specific pattern than a general "sub-resource."
- **List semantics: page tokens, not raw cursors as a general term; filter as a single expression string, not one query param per field (Ch. 7, "List").** Geewax's List pattern uses `pageToken`/`nextPageToken` (opaque, server-issued, analogous in spirit to this skill's `cursor`/`nextCursor`) and a `pageSize` parameter. For filtering, his default is a single `filter` query parameter holding a small filter-expression-language string (e.g. `filter=state=ACTIVE AND createTime>2021-01-01`) rather than one query parameter per filterable field — a materially different shape from a named-query-parameter-per-field convention. Sorting uses a single `orderBy` parameter with a comma-separated list of `field [asc|desc]` clauses.

## Actionable Techniques

- Add a "Custom Methods" subsection to `skills/api-contract-design/SKILL.md`'s Resource Naming section, explicit that a true custom method is `POST /{resource}:verb` (colon-suffixed, resource-scoped) reserved for actions that are genuinely not a create/read/update/delete on the resource — and cross-reference the existing "Verb endpoints" anti-pattern row so a future reader understands the anti-pattern is about *free-floating* verb endpoints (`POST /v1/classifyDataAsset`), not custom methods generally. Keep the skill's own correction (`PATCH /v1/data-assets/{id}/classification`) as the preferred default for state transitions that map cleanly onto a resource field, and add the custom-method form only as the named fallback for the cases that genuinely don't (e.g., a one-shot, non-idempotent action with no natural resource-field equivalent, such as `POST /v1/estate-scans/{id}:cancel`).
- Extend the skill's `202 Accepted` row in Standard Response Shapes with a concrete, named response body shape for the status-check endpoint it currently only gestures at ("a status URL") — an `Operation`-style object with `name`/`id`, `done: boolean`, and (once done) either `response` or an `error` field using the skill's existing `ErrorResponse` shape. This closes a real gap: the skill currently specifies what the *initial* 202 response contains (resource ID + status URL) but never specifies what `GET`ing that status URL actually returns.
- Add an explicit note to the ErrorResponse section that the skill's `code` field is a free-form, domain-specific SCREAMING_SNAKE_CASE string (`DATA_ASSET_NOT_FOUND`) by design — appropriate for this repo's per-domain error vocabulary — while considering whether the status-code-to-error-code-pattern table would benefit from also naming the small set of canonical *category* codes (a la `google.rpc.Code`) that the domain-specific codes nest under, purely as an optional cross-reference; do not force full replacement of the existing scheme, which is already coherent and works for this repo's needs.
- Add a "Resource Revisions (Optimistic Concurrency)" section to the skill covering `etag`/`If-Match` for resources with realistic concurrent-writer risk (the Data Asset and Compliance Gap resources named throughout the skill's own examples are plausible candidates — multiple scanners or reviewers could race on the same record) — this is a genuine, currently-absent mechanism distinct from the skill's existing `409 Conflict` row (which covers Aggregate invariant violations, not lost-update detection).
- Add a brief "Field Masks" note to the skill for partial updates on resources with many optional fields, cross-referencing the existing `PATCH` row in the HTTP-Method-to-Command/Query table — this clarifies the currently-unstated question of what an omitted field in a `PATCH` body means (leave unchanged, per Geewax's convention) versus explicit `null` (clear the field).
- When a future resource in this repo's domain is genuinely a one-per-parent settings-like object (a configuration or preference resource with no independent lifecycle), name it explicitly as a singleton sub-resource (Get/Update only, no List/Create/Delete) rather than defaulting to the skill's general "nest only one level deep" sub-resource rule without further qualification.

## Candidate New Skills/Agents

- **No new skill or agent is proposed.** Every genuinely new technique this book contributes — custom methods, the LRO `Operation` status-check shape, resource revisions/`etag`, field masks, singleton sub-resources — is a content addition that fits inside `skills/api-contract-design/SKILL.md`'s existing scope (it already owns resource naming, response shapes, and collection conventions for this repo's single API-contract skill). None of these techniques is large or independent enough to justify its own `SKILL.md`, and splitting them out would fragment a single OpenAPI-contract-authoring skill into pieces an agent would have to remember to load together. This mirrors the established pattern in the `building-microservices-newman.md` and `fundamentals-of-software-architecture-richards-ford.md` findings in this same cluster: genuine gaps that are additions to an existing skill's scope are proposed as such, not manufactured into new components.
- **Explicitly not proposed: a general "google-aip-style" API-design skill.** The book (and the AIPs it grew from) covers substantially more ground than this repo's REST-only, OpenAPI-based contract model needs — gRPC-specific conventions, Protocol Buffers field numbering, `google.rpc.Status`-as-literal-wire-format, and AIP-numbered governance process are all out of scope for a plugin whose stack default is Go/`net/http`/`chi` REST APIs described in OpenAPI 3.1. Only the REST-applicable subset (custom methods, LRO resource shape, error model philosophy, revisions, field masks) is relevant, and that subset is small enough to live as sections within the existing skill rather than a new one.

## Key Terminology

Worth considering for `skills/glossary-management/`'s Ubiquitous Language:

- **Custom Method** — Geewax's precise term for a resource-scoped, colon-suffixed action endpoint (`resource:verb`) reserved for operations that don't fit the standard Create/Get/List/Update/Delete set. `api-contract-design`'s "Verb endpoints" anti-pattern already forbids the undisciplined version of this (`POST /v1/classifyDataAsset`) but has no name for the disciplined, narrowly-scoped version that is sometimes legitimate — adopting the term would let the skill distinguish "never do this" from "do this, but only when a resource-field update genuinely doesn't fit."
- **Standard Methods** — the book's fixed vocabulary for List/Get/Create/Update/Delete (and Undelete). This repo's HTTP-Method-to-Command/Query table already implements the concept without naming it; adopting the term is optional and low-value since the skill's own table is already precise enough.
- **Operation (Long-Running Operation resource)** — a standard resource shape (`name`, `done`, `response`/`error`) for tracking async work, pollable via `GET`. Not currently named anywhere in this repo; the skill's `202 Accepted` row references "a status URL" without specifying what that URL returns — this term and its shape would fill that gap precisely.
- **Resource Revision / ETag** — a server-issued opaque identifier of a resource's current state, used with `If-Match` to detect and reject updates based on stale reads (optimistic concurrency). Not currently named or mechanized anywhere in this repo; distinct from the skill's existing `409 Conflict` (Aggregate guard failure) row, which is about business-rule violations, not concurrent-writer collision.
- **Field Mask** — a list of field paths identifying which fields a partial update (or partial response) should touch. Not currently named in this repo; would clarify the currently-unstated `PATCH` semantics in `api-contract-design`'s HTTP-Method table.
- **Singleton Sub-resource** — a sub-resource with exactly one instance per parent and no independent create/delete lifecycle (Get/Update only). Not currently distinguished from a general sub-resource in this repo's Resource Naming section.

## Caveats

- **The skill's per-field-query-parameter filtering convention is a defensible, deliberate divergence from the book, not a gap to close.** Geewax's single `filter` expression-string parameter (`?filter=state=ACTIVE AND createTime>2021-01-01`) is more expressive but requires the API to implement (or adopt) a filter-expression parser/grammar — real implementation cost this repo's frugality principle (`CLAUDE.md`, "Budget and Frugality") would weigh against unless a concrete need for compound/boolean filter expressions actually arises. The skill's existing convention (named query parameter per canonical field, each explicitly declared in the spec) is simpler to implement, simpler to validate against undocumented filters ("every filterable field is declared in the spec"), and simpler for a non-programmer PM to review in an OpenAPI spec. Do not propose migrating to a `filter` string parameter as a "fix" — only reach for it if a specific product's filtering needs genuinely outgrow named parameters (e.g., needing OR logic across fields, which named parameters cannot express).
- **This book is a REST/HTTP-transport-agnostic distillation of Google's internal AIP (API Improvement Proposal) corpus, and several of its patterns assume a Google-style API ecosystem (Protocol Buffers, gRPC, `google.rpc.Status` as a literal wire type) that this repo does not use.** Where this document describes the error model as "closely aligned with `google.rpc.Status`," that alignment is conceptual (code/message/details as three top-level concerns) — this repo's OpenAPI/JSON `ErrorResponse` envelope is a REST-native realization of the same idea, not a literal implementation of the protobuf type, and no change is needed to make it "more aligned."
- **Versioning: the book's bias toward avoiding major-version bumps does not conflict with the skill's existing path-based versioning policy — it reinforces the skill's own Versioning Strategy table.** Re-read closely, `api-contract-design`'s existing table already treats new fields and new endpoints as additive/no-bump-required and reserves the major-version bump for genuinely breaking changes (removed fields, changed types, removed endpoints) — this is the same "prefer additive evolution, reserve versioning as a last resort" posture Geewax argues for, just expressed as a table instead of prose. The book does not reveal a meaningful gap here; it confirms the skill's existing policy is already the right default. The skill's specific 6-month sunset window and `Deprecation` header mechanics are also already covered as non-gaps by this same research cluster's `building-microservices-newman.md` finding — this document does not re-propose them.
- **Do not treat "Google's API style" as this repo's target house style.** The AIP corpus this book distills was written for a large, multi-team organization publishing many long-lived public/partner APIs under central governance — a different context from this repo's single-PM, single-agent-driven, product-by-product model. Adopt the specific, narrow techniques named above (custom methods, LRO shape, revisions, field masks) because they close concrete gaps in `api-contract-design`, not because "Google does it this way" is itself a reason.
