# Microservices Patterns
**Authors:** Chris Richardson
**Domain:** Software Architecture — Microservice Data Management, Sagas, Query Patterns

> Source note: synthesized from my knowledge of the book (no PDF). Chapter references are approximate signposts, not verified page citations. Netflix Conductor task types and semantics are folded in from that project's stable public model, not from Richardson's book (which uses Eventuate/Axon for its examples) — the mapping from Richardson's orchestration pattern to Conductor is this document's own construction for this repo's stack.

## Core Concepts

- **The Saga pattern replaces distributed transactions (Ch. 4).** Because each microservice owns its own database, a business operation spanning services cannot be one ACID transaction — 2PC across service databases is rejected as a coupling-and-availability sink. A **Saga** is a sequence of **local transactions**, each in one service, coordinated by asynchronous messaging: each local transaction publishes an event or message that triggers the next. The Saga gives ACD (atomicity via compensation, consistency, durability) but sacrifices **I** — isolation. This repo's `event-driven-patterns` skill already mandates exactly this ("No distributed transactions... a Saga's compensations replace the cross-service rollback 2PC would have given"), so the book is confirmatory, not novel, on the headline — its value is in the *mechanics* below.
- **Choreography vs. orchestration — the explicit tradeoff (Ch. 4).** Richardson frames these as the two ways to coordinate a Saga. **Choreography**: no central coordinator; each service subscribes to the others' events and reacts — decentralized, but the flow logic is smeared across participants and every service becomes coupled *to the events* (and, insidiously, to the implicit ordering between them). **Orchestration**: a central **Saga orchestrator** (a persistent state machine) tells participants what to do by sending Command messages and consuming reply messages. Orchestration centralizes the flow logic, makes complex/branching flows far easier to reason about and to observe ("where is this process right now?" is one query), and avoids cyclic event dependencies — at the cost of a **central component every participant depends on**. Richardson's guidance: choreography for simple Sagas (2–4 steps), orchestration once the flow is complex, has branches/loops, or needs a queryable central view.
- **Compensating transactions and the three step classes (Ch. 4).** A Saga cannot roll back — a committed local transaction is visible immediately. Instead, failure triggers **compensating transactions** that semantically undo prior steps, executed in reverse. Richardson classifies every Saga step as **compensatable** (can be undone by a compensating tx), **pivot** (the point of no return — the step that, once it commits, means the Saga will run forward to completion, never backward), or **retriable** (comes after the pivot, must eventually succeed, so it is retried rather than compensated). Designing a Saga *is* deciding where the pivot sits; `event-driven-patterns`' Quality Criteria already demands "a class (compensatable/pivot/retryable)" per step — this is that vocabulary's source.
- **Countermeasures for the missing isolation — semantic locks (Ch. 4).** Because Sagas lack isolation, other transactions can read the intermediate, not-yet-committed-across-the-whole-flow state (anomalies: lost updates, dirty reads, fuzzy reads). The primary countermeasure is the **semantic lock**: an application-level flag (e.g. an order in `PENDING`/`APPROVAL_PENDING` state) set by the first compensatable step and cleared by a later retriable step, signaling "this record is mid-Saga, treat it with care." Other countermeasures: **commutative updates** (order-independent), **pessimistic view** (reorder steps so the riskiest run last), **reread value** (optimistic-lock re-check before write), and **by-value** (route high-risk requests to a stricter path). This is the concept most missing from this repo's current Saga material.
- **The orchestrator is a persistent state machine / process manager (Ch. 4).** A Saga orchestrator is modeled as a state machine: states, transitions on reply messages, and per-state Command dispatch. It **must be persisted** (its state written in the same local transaction as the message it consumes, via the Outbox) so a crash mid-Saga resumes rather than loses the flow. This is the classic "Process Manager" pattern (Hohpe) applied to Sagas — the orchestrator holds the flow state that choreography scatters.
- **Queries that span services — API Composition vs. CQRS (Ch. 7).** Once each service owns its data, a query needing data from several services can no longer be one join. Two patterns: **API Composition** — an in-memory join by a composer (a gateway or a dedicated service) that calls each owning service and stitches results; simple, but bad for large datasets and high fan-out. **CQRS** — maintain a separate **Read Model** (query-optimized view) fed by subscribing to the source services' Domain Events; handles complex queries and diverse access patterns at the cost of eventual consistency and the replication machinery. Richardson's rule: API Composition first; reach for CQRS when the join is expensive, the query shapes are diverse, or the composition fan-out is too wide. This repo already has a `cqrs-pattern` skill; the book supplies the *decision boundary between the two*.
- **The Transactional Outbox is the reliable-messaging foundation (Ch. 3).** Richardson's "reliably send messages as part of a transaction" is exactly the **Transactional Outbox** this repo already standardizes on: write the business row and the outbox row in one local transaction, then a relay (polling publisher or transaction-log tailing / CDC) publishes them. Every Saga message and every CQRS event depends on this to be atomic-with-the-write. **Idempotent consumers** (dedup on message id) are its mandatory partner because the relay guarantees at-least-once.

## Actionable Techniques

- **Classify every Saga step before coding it.** For each step record: its **class** (compensatable / pivot / retriable), its **compensating transaction** (for compensatable steps only), and the **semantic-lock state** it sets or clears. A Saga with no identified pivot, or a "compensatable" step whose compensation isn't written, is an incomplete design — fail it in review.
- **Choose coordination by a written rule, not by habit.** Choreography when the Saga is ≤3–4 steps of independent reactions with no branching and no "where is it now?" requirement. Orchestration (a persisted state-machine coordinator) the moment the flow branches, loops, has compensations across 4+ services, or a human/dashboard needs central visibility. Position orchestration as this repo's **deliberate exception** to its choreography+Saga default, invoked for complex, long-running, visibility-critical flows.
- **Map an orchestration Saga to a Netflix Conductor workflow.** Model the flow as a **JSON DAG** of tasks. Task types: **SIMPLE** (work done by an external worker), **FORK_JOIN** + **JOIN** (parallel fan-out and barrier), **DECISION**/**SWITCH** (branch on an expression), **SUB_WORKFLOW** (compose a child workflow), **WAIT** (block until an external signal/duration — the async human-approval or external-event step), **HTTP** (call a REST endpoint inline). Each SIMPLE task is executed by an **external task worker** that polls Conductor, does the work, and posts the result — so business logic stays in your Go services, and Conductor holds only the flow state.
- **Encode retry, timeout, and compensation as workflow policy, not ad-hoc code.** Per task, set `retryCount`, `retryLogic` (FIXED / EXPONENTIAL_BACKOFF), `retryDelaySeconds`, `timeoutSeconds`, `responseTimeoutSeconds`, and `timeoutPolicy` (RETRY / TIME_OUT_WF / ALERT_ONLY). Model **compensation as an explicit failure path**: set `failureWorkflow` on the definition so that when the Saga fails past a compensatable step, Conductor launches a dedicated compensation workflow that runs the undo tasks in reverse. This makes "what happens on failure" a reviewable artifact, not buried in a catch block.
- **Persist orchestrator state transactionally.** Whether the coordinator is Conductor or a hand-rolled Go state machine, its state transition and the command/event it emits must be written in **one local transaction** via the Transactional Outbox, so a crash resumes the Saga at the right state rather than double-sending or losing it. Make every task worker **idempotent** (dedup on task/message id) because Conductor and Redpanda both redeliver.
- **Default queries to API Composition; graduate to CQRS on a named trigger.** Start a cross-service query as an API-Composition join in a gateway/composer. Move it to a CQRS Read Model — fed by subscribing to the owning contexts' Domain Events off Redpanda — when the composition fans out too wide, the join is over large data, or the same data must answer many differently-shaped queries. Name the trigger in the design; don't build a Read Model speculatively.

## Key Terminology

- **Saga** — a sequence of local transactions coordinated by messaging, providing atomicity-via-compensation across services in place of a distributed transaction. Already in this repo's Ubiquitous Language; the book is its canonical source.
- **Compensating transaction** — a local transaction that semantically undoes a prior compensatable Saga step (there is no rollback — the prior commit is already visible).
- **Semantic lock** — an application-level countermeasure for the Saga's lack of isolation: a flag/state (e.g. `PENDING`) marking a record as mid-Saga so concurrent transactions treat it with care. Strong glossary candidate — it is the concept most absent from the repo's current Saga vocabulary.
- **Pivot transaction** — the Saga step that, once committed, guarantees the Saga runs forward to completion; steps before it are compensatable, steps after it are retriable.
- **Saga orchestrator / process manager** — a persisted state machine that drives a Saga by issuing Commands and consuming replies, holding the flow state choreography would scatter.
- **API Composition** — answering a cross-service query by an in-memory join over calls to each owning service. Contrast with **CQRS**, which pre-builds a Read Model from Domain Events.

## Caveats

- **Confidence:** high on the book's headline patterns (Saga, choreography vs. orchestration, compensating transactions, the three step classes, semantic locks, API Composition vs. CQRS, Transactional Outbox) — these are the book's well-known, widely-cited contributions. Chapter numbers above are approximate signposts, not verified citations.
- **Conductor specifics are not from Richardson's book.** The book's orchestration examples use Eventuate Tram / a hand-built orchestrator, not Netflix Conductor. Conductor's task-type names (SIMPLE, FORK_JOIN, JOIN, DECISION, SUB_WORKFLOW, WAIT, HTTP) and policy fields (`retryLogic`, `timeoutPolicy`, `failureWorkflow`) are folded in from Conductor's own stable public model, and the Richardson-to-Conductor mapping is this document's construction for this repo's stack. Conductor's exact task-type roster and field names have evolved across versions — treat the list as the stable core, and confirm against the pinned Conductor version before generating manifests.
- **This repo defaults to choreography+Saga on Redpanda; orchestration is the exception, and Conductor is an added dependency.** Introducing a central orchestrator (Netflix Conductor, or a hand-rolled Go state machine) adds an operational component every participant depends on — the exact "central dependency" cost Richardson names. Against this repo's frugality constraint, prefer a hand-rolled persisted-state-machine Saga coordinator (Go + pgx + Outbox, deployed per-tenant like everything else) for a single complex flow; justify pulling in Conductor as an open-source engine only when the number and complexity of orchestrated flows outgrows hand-rolled coordinators and central visibility across many workflows becomes the point.
- **Physical per-tenant isolation shapes deployment.** Any orchestrator here inherits this repo's per-tenant physical isolation — a Conductor deployment or a Go coordinator runs within the tenant's boundary (Kubernetes namespace / Helm release), not as a shared multi-tenant control plane, so a Saga never spans tenants and the orchestrator's Read/query view stays tenant-scoped.
