## Core Concepts

- **The AMQP 0-9-1 object model is the whole point (Ch. 1–4).** A *Connection* is a single TCP socket to the broker; *Channels* are lightweight logical sessions multiplexed over one Connection so an application does not open a socket per thread of work. Producers never publish to a queue — they publish to an *Exchange* with a *routing key*; the Exchange, via *Bindings*, decides which *Queues* (if any) receive a copy. This producer/exchange/binding/queue indirection is the structural difference from a system where you address a topic-partition directly: the routing topology is broker-side configuration, not caller-side addressing.
- **Exchange types are the routing algebra (Ch. 4).** *direct* — exact routing-key match (point-to-point, work queues). *topic* — routing key is a dotted path matched against binding patterns with `*` (one word) and `#` (zero-or-more words), e.g. `scan.gdrive.completed` bound by `scan.#`. *fanout* — ignores routing key, copies to every bound queue (broadcast). *headers* — matches on message header attributes instead of the routing key. Choosing the exchange type *is* choosing the delivery semantics; it is a design decision, not a config detail.
- **Publisher confirms + the mandatory flag are how a producer knows a message was accepted (Ch. 5).** Plain `basic.publish` is fire-and-forget — the broker may drop it silently. *Publisher confirms* (`confirm.select`) make the broker return `basic.ack` once the message is safely enqueued (or persisted, for durable queues), giving at-least-once producer guarantees. The *mandatory* flag additionally makes the broker return the message (`basic.return`) if it routed to **zero** queues, catching the silent-drop-into-the-void failure where a routing key matches no binding.
- **Consumer acknowledgements govern redelivery (Ch. 5–6).** With `autoAck=false`, a message is held "unacknowledged" until the consumer sends `basic.ack`; if the consumer dies first, the broker requeues it — at-least-once delivery. `basic.nack`/`basic.reject` explicitly refuse a message; `requeue=true` puts it back, `requeue=false` discards it (or routes it to a DLX if configured). Auto-ack trades this safety for throughput and means a crash loses in-flight work.
- **Dead-letter exchanges + TTL turn poison messages and delays into topology (Ch. 6, 8).** A queue configured with `x-dead-letter-exchange` republishes messages that are rejected (`requeue=false`), that expire via message/queue TTL (`x-message-ttl`), or that exceed `x-max-length` — to a designated DLX. This is how RabbitMQ expresses retry-with-backoff and poison-message quarantine: there is no built-in replay, so delayed retry is *built* from a TTL queue that dead-letters back to the work exchange.
- **Prefetch/QoS is the fair-dispatch and back-pressure knob (Ch. 6).** `basic.qos(prefetch_count=N)` caps how many unacknowledged messages the broker pushes to one consumer channel before waiting for acks. `prefetch=1` gives fair dispatch (a slow consumer is not handed a backlog while a fast one starves); a higher prefetch trades fairness for throughput. This is the single most important tuning parameter for a *Competing Consumers* pool sharing one queue.
- **THE central contrast for this repo: queue-based (RabbitMQ) vs. log-based (Kafka/Redpanda).** RabbitMQ is a **smart broker / dumb consumer** queue: a message is **removed on ack** — once consumed it is gone, there is **no retention window, no offset, no rewind, and no replay** for a late-arriving or newly-deployed consumer. Ordering is **per-queue** (and only guaranteed to a single consumer without requeues), not per-partition. There is **no consumer-group offset** concept — parallelism comes from multiple consumers *competing* on one queue, which by design **destroys ordering** across the pool. Redpanda (Kafka API), which this repo standardizes on, is the inverse: a **dumb broker / smart consumer** durable log where messages are **retained** for a configured window, every consumer group tracks its own **offset**, ordering is **per-partition**, and any consumer can **rewind and replay** history. Fan-out in RabbitMQ needs one queue per consumer bound to a fanout exchange; in Kafka every group independently reads the same retained partitions. Neither is "better" — they answer different questions, and picking the wrong one is a costly architecture mistake.

## Actionable Techniques

- **Choose the broker on the replay question first.** If a consumer must be able to reprocess history (new read model, reindex, bug-fix reprocessing, event sourcing, audit) → log-based (Redpanda). If the workload is transient task dispatch where a consumed message is genuinely done (RPC-style work queues, per-tenant job fan-out with complex routing) → a queue broker like RabbitMQ is a legitimate fit. State this as an explicit selection criterion, not a default.
- **Model retry/backoff explicitly in RabbitMQ topology** because there is no offset to "leave and come back to": a work queue dead-letters (`requeue=false`) to a *retry* queue with `x-message-ttl` set to the backoff delay and its own DLX pointing back at the work exchange; after N cycles (tracked via an `x-death` header count) route to a terminal *parked*/DLQ queue. Contrast with Redpanda where retry is often just "don't advance the offset."
- **Always enable publisher confirms + the mandatory flag for any message that matters**, and treat a `basic.return` (unroutable) as a hard configuration error surfaced in telemetry — it means a routing key matched no binding, the silent-loss failure mode.
- **Size prefetch to the work, not to a default.** Start `prefetch=1` for long/uneven task handlers (fair dispatch); raise it only when handler latency is low and uniform and throughput is the constraint. Measure unacked-message depth to tune.
- **Emit the queue-model semantics as OpenTelemetry attributes** so a data-estate/compliance operator can see them: delivery-tag, redelivered flag, exchange, routing key, and (for a Redpanda comparison skill) the deliberate absence of an offset. Make the "no replay" property observable, not folklore.

## Key Terminology

- **Exchange / Binding / Routing Key** — the broker-side routing triple that decides queue delivery; the AMQP concept with no direct Kafka equivalent (Kafka addresses topic-partitions directly). Candidate glossary additions alongside the existing platform terms.
- **Publisher Confirm / Mandatory flag** — the producer-side at-least-once mechanism (`basic.ack` on accept) and the zero-route detector (`basic.return`).
- **Dead-Letter Exchange (DLX)** — reuses the repo's existing `Dead Letter Queue` glossary term but names the *routing* mechanism (an exchange messages are re-published to on reject/TTL/overflow), which is how RabbitMQ realizes a DLQ.
- **Prefetch / QoS (`basic.qos`)** — the unacked-message window per consumer channel; the fair-dispatch and back-pressure control.
- **Removed-on-ack vs. retained log** — the one-line statement of the queue-vs-log divide worth adding to the glossary so `Competing Consumers` (already a repo term) is understood as *ordering-destroying by design* in the queue model.

## Caveats

- **Confidence is high on the AMQP 0-9-1 model and RabbitMQ's headline mechanics** (exchanges, bindings, exchange types, publisher confirms, the mandatory flag, manual ack/nack/reject, DLX, TTL, prefetch/QoS) — these are the published protocol spec the book teaches, not the author's private invention. Chapter numbers are approximate signposts, not verified citations.
- **This repo does not run RabbitMQ** — it standardizes on Redpanda (Kafka API). This file exists to make `message-broker-selection` able to teach the *contrast* and to justify that standardization deliberately, and to seed two AMQP skills only if a future workload (e.g. per-tenant RPC-style task dispatch) genuinely warrants a queue broker. Do not read it as a recommendation to introduce RabbitMQ.
- **The queue-vs-log framing is a model, not a verdict.** RabbitMQ has streams (a log-like feature) and Kafka can emulate work queues; the clean "removed-on-ack vs. retained" contrast above describes the *classic* queue model AMQP 0-9-1 exposes, which is the correct teaching baseline for selection, but a real design should check current feature sets before treating either as absolute.
- **All Go application shapes above are extrapolations onto this repo's stack** (Go, `amqp091-go`-style clients, OpenTelemetry, per-tenant isolation) — the book's examples are primarily Python. The mapping of AMQP semantics onto this repo's chi/pgx/Redpanda-standardized architecture is this document's synthesis, not content literally in the book.
