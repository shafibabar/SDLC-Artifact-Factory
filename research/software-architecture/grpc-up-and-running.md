## Core Concepts

- **Contract-first with Protocol Buffers (Ch. 2–3).** A gRPC API begins as a `.proto` file: `service` blocks declare RPC methods, `message` blocks declare request/response types. The proto *is* the contract — the single source of truth from which both server stubs and client stubs are generated. This inverts the repo's REST default, where the OpenAPI 3.1 spec is authored as the contract but handlers and clients are hand-written against it. With gRPC the strongly-typed client/server code cannot drift from the schema because it is generated from it. protobuf3 (`syntax = "proto3";`) is the current language version; the wire format is compact binary, not JSON.
- **Field numbers are the wire contract, not the field names (Ch. 3).** Every message field carries an integer tag (`string tenant_id = 2;`). That number — never the name — is what the binary encoding uses. The compatibility rules follow directly: never reuse a number, never renumber an existing field, and never change a field's type in an incompatible way. To drop a field, delete it and add its number (and optionally its name) to a `reserved` clause so no future edit silently re-homes it. Unknown fields are preserved on the wire, giving forward compatibility; new fields are added with fresh numbers, giving backward compatibility. proto3 makes scalar fields non-presence-tracking by default; `optional` restores explicit presence (has-a-value vs zero-value), and `repeated` denotes a list. This is the discipline that lets a producer and consumer evolve independently — the gRPC analog of additive-only OpenAPI evolution.
- **Four communication patterns (Ch. 4).** gRPC exposes exactly four method shapes over one HTTP/2 stream: **unary** (one request → one response, the REST-like default); **server streaming** (one request → a stream of responses, e.g. paginating or tailing a large scan result); **client streaming** (a stream of requests → one response, e.g. uploading a large document in chunks); and **bidirectional streaming** (independent read and write streams over one connection, e.g. a live progress channel). Streaming is a first-class capability the repo's REST edge cannot express without bolting on SSE/WebSockets. The pattern is chosen per method in the proto (`stream` keyword on the request and/or response type).
- **Interceptors are the middleware analog (Ch. 5).** gRPC has server and client interceptors in two flavors matching the method shapes: **unary interceptors** wrap a single request/response; **stream interceptors** wrap a streaming call. They are where cross-cutting concerns live — auth-token validation, tenant extraction, logging, metrics, tracing propagation, panic recovery — exactly the role chi middleware plays at the repo's REST edge. Interceptors chain, and the streaming variant must wrap the `ServerStream` to observe individual messages.
- **The status-code model is gRPC's own, not HTTP's (Ch. 5).** Every call completes with a gRPC status **code** (an enum: `OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `FAILED_PRECONDITION`, `RESOURCE_EXHAUSTED`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `INTERNAL`, …) plus a message and optional structured details. These are transport-independent and richer for RPC semantics than HTTP status codes — `INVALID_ARGUMENT` vs `FAILED_PRECONDITION` vs `OUT_OF_RANGE` distinguish failures that all collapse to `400` in REST. Servers must map domain errors to these codes deliberately, the same discipline `go-chi-handler` applies mapping domain errors to HTTP status.
- **Deadlines, cancellation, and metadata are built into the call (Ch. 5).** Every gRPC call carries a **deadline** (an absolute time, propagated to the server, which sees `DEADLINE_EXCEEDED` and should stop work) — not an ad-hoc client timeout. Cancellation propagates through the `context.Context`: when a client cancels or its deadline passes, the server's context is cancelled and downstream calls should unwind. **Metadata** is the key/value header/trailer channel (the analog of HTTP headers) carrying auth tokens, tenant IDs, and trace context — read and written via context, and the natural place OpenTelemetry trace propagation and the tenant claim ride.
- **Code generation is a build step, not a runtime library (Ch. 2–3).** `protoc` (with `protoc-gen-go` and `protoc-gen-go-grpc`) compiles `.proto` into Go types and the client/server interface stubs; the server implements the generated service interface, the client calls the generated client. This is genuinely contract-first: the generated code is checked in or built in CI, and a proto change that breaks compatibility surfaces as a compile break, not a production 400.

## Actionable Techniques

- **Write the proto first, review it like an OpenAPI spec.** Define `service` + `message`, assign field numbers deliberately, and treat the numbering as permanent from the first review. Adopt a house rule: field numbers 1–15 (one wire byte) for the hot, frequently-set fields; leave gaps intentionally.
- **Codify the compatibility rules as a checklist for every proto edit:** (1) am I reusing or renumbering an existing field number? — forbidden; (2) did I `reserved` the number (and name) of anything I removed? — required; (3) am I changing a field's type? — only within the wire-compatible set; (4) is a new field additive with a fresh number and a sane zero-value default? Run a schema-diff/breaking-change linter (e.g. Buf) in CI so this is enforced, not remembered.
- **Choose the method shape from the data flow, not habit:** unary for request/response commands and point reads; server streaming for large or open-ended result sets (a data-estate scan emitting assets as it discovers them); client streaming for large uploads assembled server-side (chunked document ingest); bidirectional for live, concurrent progress or control channels. Default to unary unless streaming earns its keep — it complicates load balancing and retries.
- **Put all cross-cutting concerns in interceptors, keep the service method thin.** Auth/tenant extraction, logging, metrics, tracing, recovery belong in a unary and a matching stream interceptor; the generated method body stays decode→validate→domain→encode, mirroring the Humble Object discipline `go-chi-handler` already enforces.
- **Map domain errors to gRPC codes through one status writer**, exactly as the REST edge maps to HTTP status through one error writer — never leak internal error strings; attach structured details for machine-readable failures; reserve `INTERNAL` for genuine bugs and prefer `INVALID_ARGUMENT`/`FAILED_PRECONDITION`/`NOT_FOUND` for domain conditions.
- **Set a deadline on every client call and honor it server-side.** Derive downstream contexts from the incoming one so cancellation propagates; treat a done context as a hard stop, not advisory.
- **Reserve gRPC for internal service-to-service traffic; keep REST for public and browser-facing APIs.** Browsers cannot speak native gRPC without a proxy (gRPC-Web); the repo's public/data-estate API stays REST+OpenAPI, and gRPC is the strongly-typed, binary, streaming-capable internal transport between Go services.

## Key Terminology

- **protobuf3 / proto3** — the current Protocol Buffers language version (`syntax = "proto3";`); the IDL and binary wire format underlying gRPC.
- **Field number** — the integer tag on a message field; the actual wire identifier. Permanent once shipped; governed by the never-reuse/never-renumber/`reserved` rules. Candidate glossary term alongside `Consumer-Driven Contract`.
- **Unary / server-streaming / client-streaming / bidirectional-streaming** — the four RPC method shapes, chosen per method with the `stream` keyword.
- **Interceptor** — server/client middleware for gRPC, in unary and stream variants; the chi-middleware analog.
- **gRPC status code** — the transport-independent result enum (`OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `PERMISSION_DENIED`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `INTERNAL`, …); distinct from HTTP status.
- **Metadata** — the gRPC key/value header/trailer channel (auth token, tenant ID, trace context); the analog of HTTP headers.
- **Deadline** — an absolute-time bound propagated to the server, surfacing as `DEADLINE_EXCEEDED`; distinct from a client-local timeout.

## Caveats

- **Confidence is high on the stable specs, approximate on structure.** The proto3 rules, the four method shapes, the status-code enum, interceptors, deadlines/metadata, and HTTP/2 transport are well-documented public specifications I am confident in. Chapter numbers above are best-effort signposts to the book's organization, not verified page references.
- **No invented numbers or benchmarks.** I have not asserted any throughput/latency figures for gRPC vs REST; the book's general claim is that binary + HTTP/2 multiplexing is more efficient than JSON-over-HTTP/1.1 for internal chatter, but any specific number should be measured on this repo's stack, not quoted.
- **gRPC is not a REST replacement for this product's public surface.** Browsers need gRPC-Web (a proxy translation) to speak gRPC; the data-estate product's external/browser-facing API stays REST+OpenAPI. Treat gRPC as the internal service-to-service transport, adopted per-boundary where its typing/streaming earns its cost — not a wholesale migration.
- **The book predates this repo's exact stack** (Go + chi + pgx, Linkerd, Redpanda, per-tenant physical isolation). Its examples are generic; every mapping onto this repo's agents, the Linkerd L7-balancing caveat, and the "internal gRPC vs public REST" split are this document's extrapolation of the book's language-agnostic model onto this stack, not text literally in the book.
- **The Linkerd L7-balancing point is a genuine operational gotcha, not a formality.** gRPC's long-lived HTTP/2 connections defeat connection-level load balancers; verify that traffic actually spreads across backend pods (Linkerd's per-request balancing, or a gRPC-aware balancer) rather than assuming a plain Kubernetes `Service` distributes it — it will not.
