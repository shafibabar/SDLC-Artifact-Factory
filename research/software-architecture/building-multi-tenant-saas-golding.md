# Building Multi-Tenant SaaS Architectures
**Authors:** Tod Golding (*Building Multi-Tenant SaaS Architectures: Principles, Practices, and Patterns Using AWS*, O'Reilly, 2024). Golding led AWS's SaaS Factory programme, and much of the book's vocabulary also appears in AWS material he helped write (the SaaS Lens of the Well-Architected Framework and the SaaS tenant-isolation and storage-strategy whitepapers).
**Domain:** Software Architecture — multi-tenant SaaS (deployment models, tenant isolation, tenant identity, data partitioning, tiering, tenant-aware operations)

## Core Concepts

- **SaaS is a business and operating model first, a technical pattern second.** Golding's opening argument: what makes a product SaaS is that all customers run on one operational footprint that the provider manages, onboards, upgrades and observes as a single thing, so the business gets agility, a lower cost to serve, and fast onboarding. A product that runs one separately managed copy per customer, each on its own version and upgraded by hand, is managed hosting, even if it is "in the cloud". So the test of a tenancy design is not only "is tenant data safe" but also "can the provider still operate, upgrade, observe and price the whole fleet as one system".
- **Control plane versus application plane.** The **control plane** holds the services that run the SaaS business across all tenants: onboarding, tenant management (the tenant registry and each tenant's tier and state), identity set-up, billing and metering, tenant-aware operations and the admin console. It is single and global, and it is not itself multi-tenant. The **application plane** is the product: the services that do the work for tenants, built in whatever mix of shared and dedicated resources the deployment model calls for. The repo already has this split in one sentence ("a Control Plane that manages tenants but never reads tenant data", `multi-tenancy-design/SKILL.md:76`), but only for the stamp model; the book applies it to every model.
- **Tenant identity and the tenant-aware token.** A user always belongs to a tenant, and that binding is made once, at onboarding, in the identity provider. After sign-in, the token the user carries holds the tenant identifier (and usually the tier and role) as claims: Golding calls the joined result **SaaS identity**. Every layer then resolves **tenant context** from that token, never from a value the client sends: the gateway (routing and throttling), each service (authorisation and data access), the data layer (scoping), and logs, metrics and traces (attribution). Tenant context travels with the request, including onto events and into downstream calls.
- **Deployment models: silo, pool, and mixes of the two.** A **silo** gives a tenant dedicated resources; a **pool** shares resources across tenants. The choice is made per resource, not once for the whole system: a product can pool its compute and silo one tenant's database. The book names the ends **full-stack silo** (every resource dedicated, which is what this repo calls a stamp) and **full-stack pool**, and treats **mixed-mode** deployments as normal: some services pooled and others siloed, or (the common tiered mix) basic-tier tenants pooled and premium or regulated tenants given silo resources. AWS's storage material uses **bridge** for the middle ground (in relational stores, a schema per tenant inside a shared instance); how far the book itself uses "bridge" is uncertain (see Caveats). Golding also describes grouping tenants into repeatable units of deployment (**pods**, close to what other sources call cells or stamps) to bound blast radius and scale the fleet.
- **The deployment model is chosen from forces, not from a default.** The forces the book weighs are: **tiering** (what each price point promises, which may include dedicated resources), **compliance and data-residency** commitments, **noisy-neighbour** risk, **cost to serve** (silos multiply the baseline cost per tenant and leave capacity idle), **operational complexity** (every silo is one more thing to deploy, upgrade and watch), **agility** (pooled fleets ship once), and **onboarding speed**. No single model wins on all of them, which is why mixed and tiered models are common.
- **Tenant isolation is a separate decision from the deployment model.** This is the book's most important distinction for this repo. The deployment model says where tenants' resources sit; **isolation** is the set of controls that stop one tenant reaching another's resources. A silo makes isolation simpler to enforce but does not enforce it on its own (a flat network or a shared credential still crosses it). A pool still needs isolation; there it is enforced at run time: each request gets credentials or a policy scoped to the tenant in its token, and the data layer refuses rows outside that scope. Golding's point is that a pooled design is only acceptable if isolation is **enforced by a mechanism**, not left to developers remembering a `WHERE` clause. The AWS material names the run-time pattern dynamically generated, tenant-scoped policies (a "token vending machine"); in this plugin's stack the equivalents are PostgreSQL row-level security driven by a per-transaction tenant setting, per-tenant broker principals and ACLs, and the ABAC tenant check in `access-control-model`.
- **Data partitioning follows the storage type.** Each store gets its own silo-or-pool choice at its own grain: relational (an instance or database per tenant, a schema per tenant, or shared tables with a tenant key and row-level security); key-value and document stores (a table per tenant, or a shared table with the tenant in the partition key); object storage (a bucket per tenant, or a tenant prefix with prefix-scoped policies); search indexes (an index or cluster per tenant, or a shared index filtered by tenant). Partitioning is a scaling and noisy-neighbour decision as well as an isolation one: a pooled partition needs a tenant-leading key so one tenant's data can be found, moved, exported and deleted.
- **Noisy neighbour, throttling and tiering.** In any pooled resource one tenant can use up capacity the others need. The book's answers are layered: per-tenant and per-tier throttling and quotas at the entry point, separate queues or worker pools by tier, scaling policies that account for tenant load, and, for the top tier, moving the tenant to dedicated resources. Tiers are a product decision (what each price point promises) that the architecture then has to enforce.
- **Tenant-aware operations, metering and cost attribution.** Operations must be able to slice health, errors and latency by tenant and tier: who is affected, who is causing load. Golding separates **metrics** (operational and business insight), **metering** (usage that feeds billing) and **cost per tenant** (what a tenant costs to serve). In a silo, cost is visible from resource tags; in a pool it has to be estimated from per-tenant consumption data recorded by the services. Without cost per tenant the business cannot tell whether its tiers make money.
- **Tenant lifecycle is a control-plane job for every model.** Onboarding is one automated flow: create the tenant record, set up identity, provision whatever the tier needs (a few rows for a pooled tenant, a full silo for a dedicated one), and apply the tier's policies. Tier changes (moving a tenant from pool to silo, or back) and offboarding are part of the same lifecycle and must also be automated. Deleting a pooled tenant means removing its data from shared stores, indexes, caches, event logs and backups, which is harder than destroying a silo; per-tenant encryption keys that can be destroyed (crypto-shredding) are a common answer, though that detail comes from general practice more than from the book.

## Actionable Techniques

- **Make the tenancy decision an explicit step with named inputs.** Inputs: tenant count and growth, data classification (`data-classification`), compliance and residency obligations (`compliance-design`), tiers and what each promises, noisy-neighbour NFRs, and the cost ceiling. Output: a deployment model per resource type (compute, each data store, broker, cache, search), the isolation mechanism for each, and the tier mix. Run it before the deployment view of `container-diagram`, because it decides the deployment topology (D047 item 7, W2-18).
- **Separate what a framework requires from what a customer or contract requires.** In this repo's reading (not Golding's text): **SOC 2** is an attestation against the AICPA Trust Services Criteria; the criteria are outcomes (logical access restricted, changes controlled, incidents handled), and the auditor checks that the provider's own controls meet them. It prescribes no deployment model, so a pooled design with enforced, tested logical isolation can pass; physical isolation is a commitment some providers make to customers, not a SOC 2 control. **HIPAA** and **GDPR** require appropriate safeguards and say nothing about physical separation; GDPR restricts transfers out of the EEA but does not on its own require in-region storage. **PCI DSS** accepts logical segmentation; it has extra requirements for shared hosting providers. What does push toward silo: data-localisation laws in some countries, government cloud programmes with their own boundaries, customer contracts that demand dedicated infrastructure or customer-managed keys, and customer-hosted deployment. Record each push with its source (law, contract, tier), never as "compliance requires it".
- **Enforce isolation per model, layer by layer.** For pooled PostgreSQL: row-level security on every tenant table, `FORCE ROW LEVEL SECURITY` (the table owner bypasses policies otherwise), the application connects as a non-owner role, and the tenant is set with `SET LOCAL` inside each transaction so a pooled connection cannot carry it over. For a pooled broker: per-tenant or per-service principals with topic ACLs, and the tenant on every event. For the API: tenant from the token, checked first (`access-control-model:106`). For silo: per-tenant credentials and a default-deny network. Either way, add a cross-tenant test (tenant A's token against tenant B's resource) as a gate.
- **Put tenant context into telemetry from the first service.** Add the tenant identifier and tier as attributes on spans, logs and per-tenant metrics (bounded so metric cardinality stays sane), and record usage events the control plane can turn into metering and cost per tenant.
- **Design tier changes and offboarding with onboarding.** Specify how a tenant moves between pool and silo (data copy, cut-over, routing change) and how a pooled tenant's data is found and deleted everywhere it lives, including backups.

## Key Terminology

- **Control plane** — the global services that onboard, manage, meter and operate tenants.
- **Application plane** — the product's tenant-serving services, in whatever silo and pool mix the model calls for.
- **Silo** — a resource dedicated to one tenant. **Full-stack silo** = every resource dedicated (this repo's stamp).
- **Pool** — a resource shared by tenants, with isolation enforced at run time.
- **Bridge** — AWS's term for a middle ground; in relational storage, a schema per tenant in a shared instance.
- **Mixed-mode / tiered deployment** — some resources or tiers siloed, others pooled.
- **Pod** — a repeatable unit of deployment holding a group of tenants (cell or stamp in other sources).
- **Tenant context** — the tenant identity and attributes resolved from the token and carried through each layer.
- **SaaS identity** — a user identity bound to its tenant, carried as token claims.
- **Tenant isolation** — controls that stop one tenant reaching another's resources, independent of the deployment model.
- **Noisy neighbour** — a tenant whose load degrades others sharing a pooled resource.
- **Metering** — per-tenant usage recorded for billing; distinct from metrics and from cost per tenant.

## Caveats

- **Recalled with confidence:** SaaS framed as a business and operating model; control plane versus application plane; silo and pool, full-stack silo and pool, and mixed-mode deployment; deployment model and tenant isolation as separate concerns; the tenant-aware token and tenant context; noisy neighbour, tiering and throttling; metrics versus metering versus cost per tenant; per-storage partitioning options.
- **Uncertain:** exact chapter titles and order (roughly: the SaaS mindset, fundamentals, deployment models, onboarding and identity, tenant management, building services, data partitioning, isolation, then Kubernetes and serverless worked examples, tiering and operations); whether the book uses "bridge" as a deployment-model name or whether that is only in the AWS SaaS Lens and storage whitepaper; whether "pod" is the book's term or AWS training material's; how deeply the book covers offboarding and deletion.
- **Not from the book:** the compliance reading (SOC 2, HIPAA, GDPR, PCI DSS) is this repo's understanding of the frameworks, not Golding's text. Check it against the AICPA criteria and the regulations before a skill quotes it. Crypto-shredding and the PostgreSQL RLS details (`FORCE ROW LEVEL SECURITY`, `SET LOCAL`) are general practice.
- **AWS-specific examples are translated.** The book's examples use AWS services (IAM-scoped policies, Cognito, DynamoDB, EKS, Lambda). Only the patterns carry over; this file maps them to the plugin's stack, and the rewrite should stay stack-neutral in Design.
