# Documenting Software Architectures: Views and Beyond
**Authors:** Paul Clements, Felix Bachmann, Len Bass, David Garlan, James Ivers, Reed Little, Paulo Merson, Robert Nord, Judith Stafford (2nd edition, SEI/Carnegie Mellon)
**Domain:** Software Architecture

## Core Concepts

- **"Architecture" is not a diagram — it is a set of coordinated views (Ch. 1–2).** The book's founding claim is that no single diagram can show a system's structure, because a system has many structures simultaneously (its module decomposition, its runtime processes, its deployment topology) and a diagram that tries to show all of them at once becomes unreadable. A **view** is a representation of the system from the perspective of one of these structures. This is a stronger, more precise claim than this repo's C4 skills currently make: `system-context-diagram`, `container-diagram`, and `component-diagram` are presented as a single graduated sequence of "levels" (C4's zoom metaphor), not as different *kinds* of structure that happen to share a numbering scheme. The book would say C4's Levels 1–3 are actually two different view *types* wearing one numbering convention — see the direct comparison below.
- **A viewpoint is a set of conventions for constructing one kind of view, built for a specific stakeholder audience with specific concerns (Ch. 2, 4).** A view is a concrete instance ("the container diagram for the Compliance service"); a viewpoint is the pattern that generates views of that kind ("the pattern by which we always draw component-and-connector diagrams"). The distinction matters because it separates the reusable *rule* (what element and relation types are legal, what notation is used, what questions this kind of view answers) from any one *drawing*. This repo's diagram skills already function as informal viewpoints — `system-context-diagram`'s "What Does NOT Belong" section and `container-diagram`'s "Container Diagram Rules" section are viewpoint definitions in substance — but none of the three skills names the term "viewpoint" or states explicitly which stakeholders and concerns the viewpoint exists to serve, beyond a one-line audience column in `system-context-diagram`'s C4 table.
- **The three major view types, and what each one is actually for (Ch. 2, 5–7):**
  - **Module views** show the system's static implementation structure — how the source code is divided into implementation units (modules, packages, classes, layers) and the relations between them: *decomposition* (is-part-of), *uses* (depends-on, for compilability/deployability), *generalization* (is-a), and *layered* (allowed-to-use, a restriction of *uses*). A module view answers: "if I need to change X, what else might I need to change or at least understand?" It says **nothing about runtime behavior** — a module view has no processes, no messages, no time dimension. `component-diagram`'s "Standard Layered Architecture for Go Services" and its dependency-direction rule are, in Views and Beyond terms, a *layered module view* — one of four legitimate module view styles the book names (decomposition, uses, generalization, layered), and specifically the one concerned with allowed-to-use restrictions between layers.
  - **Component-and-connector (C&C) views** show the system's runtime structure — the principal executing units (**components**: processes, threads, services, objects at runtime) and the pathways of interaction between them (**connectors**: procedure calls, pipes, event channels, message queues — anything that carries data or control flow at runtime). A C&C view answers: "what talks to what while the system is running, and how?" This is where `container-diagram` and `component-diagram`'s internal layer-to-layer arrows most directly live — but see the conflation finding below.
  - **Allocation views** show the mapping of software structure (modules or components) onto **non-software structures**: physical hardware/environments (deployment view — which process runs on which node), the file/directory organization of source control (implementation view), or the assignment of modules to development teams (work assignment view). An allocation view answers a fundamentally different question from the other two: not "how is the code organized" or "what talks to what," but "where does this run, and who owns building it?"
- **A view is not just a picture — it is a documentation package with a defined structure (Ch. 3, 9).** The book's most consequential and most-often-skipped idea: a picture alone is an underspecified view. A complete view's documentation package has (at minimum): a **primary presentation** (the diagram or equivalent notation), an **element catalog** (a table enumerating every element and relation shown, with its properties, that the picture's boxes and lines cannot carry on their own — e.g., a component's interface, a connector's protocol, a module's responsibility), a **context diagram** (how this view's system-of-interest relates to what is outside it, at that view's own level — every view type gets its own context diagram, not just the system as a whole), a **variability guide** (what varies across product variants or deployment configurations, and how — relevant here given this repo's per-tenant physical multi-tenancy model), and **rationale** (why the structure shown was chosen, over what alternatives — the view-level analog of an ADR, but scoped to explaining *this view's shape* rather than one architectural decision). A view missing the element catalog and rationale is, in the book's own words, "just a picture" — reviewable by eye but not usable as a specification engineers can build from or a record future engineers can trust.
- **Views are combined, not drawn all at once — "beyond views" is about relating and packaging them (Ch. 3, 10–11).** The "Beyond" half of the title refers to the practices that make a set of separate views into one coherent architecture document: documenting how views relate to each other (a **mapping between views** — e.g., which module maps to which runtime component, which is not always 1:1), choosing a **documentation roadmap** that tells a reader which views exist and why, and — most relevant for a resource-constrained, single-operator context like this repo — **selecting only the views a project actually needs**, rather than producing the full canonical set by default.
- **View selection is stakeholder-driven, not exhaustive (Ch. 4, 18).** The book is explicit that no project should produce every possible view "because the method defines them." Each view is produced because a specific stakeholder with a specific concern needs it: a new engineer onboarding needs a module decomposition view; an ops/SRE stakeholder needs a deployment (allocation) view; a security reviewer needs a C&C view showing trust boundaries and data flows; a build/release engineer needs an implementation (allocation) view of the source tree. The method's central discipline is enumerating stakeholders and their concerns *first*, then choosing the minimum set of views that addresses them — the same "why before how" discipline this repo already applies to ADRs (per `adr-authoring`, citing Richards & Ford) applies at the view-selection level too: draw a view because a named stakeholder concern demands it, not because the C4 sequence has four levels.
- **Combined view types exist for a reason, but should be used sparingly (Ch. 9).** The book allows overlaying two view types into one diagram (e.g., a C&C view annotated with deployment allocation) when the combination genuinely serves one stakeholder's concern better than two separate diagrams would — but warns this is an exception requiring deliberate justification, not a default, because combined views tend to silently grow until they are unreadable by anyone. This is the precise vocabulary for evaluating whether `container-diagram`'s current shape is a justified combined view or an unexamined conflation (see below).

## Actionable Techniques

- Before drawing any diagram, name the **stakeholder and the concern** it exists to serve — one sentence, e.g., "this C&C view exists so the security reviewer can see trust boundaries and data flows across service calls." A diagram with no named stakeholder/concern is a candidate for deletion or merging, per the book's stakeholder-driven selection principle.
- For any diagram graduating from "sketch" to "artifact," add the two missing documentation-package parts most commonly skipped: an **element catalog** (a table listing every box/line with its properties — this repo's diagram skills already do this partially via their "Elements"/"Containers"/"Components" tables, but stop short of covering connectors' properties, e.g. a specific protocol's retry/timeout behavior) and a **rationale** subsection explaining why this structure over an alternative (distinct from an ADR — this is "why does *this view* look the way it does," not "why did we choose this architecture decision").
- When a diagram mixes runtime interaction (C&C) with deployment placement (allocation) in one picture — as `container-diagram`'s worked example currently does by putting deployment-flavored annotations ("shared cluster," "Port: 8080") on what is otherwise a pure C&C diagram — make the combination deliberate: either split into two views (a C&C view of service-to-service communication, and a separate allocation/deployment view of physical placement) or explicitly label the diagram as a justified **combined C&C-and-allocation view** per Ch. 9, with a one-line note on why the combination serves the reader better than two views would.
- For an allocation (deployment) view specifically, add a **variability guide** covering this repo's physical multi-tenancy model — since `container-diagram`'s "Deciding Service Boundaries" table already names physical multi-tenancy as a constraint that "multiplies" deployment without a separate artifact tracking what varies per tenant deployment vs. what stays fixed.
- When a new stakeholder concern surfaces that none of the three existing diagram skills addresses — e.g., a build/release engineer needing to see the Go package/source-tree structure across all services, independent of any single service's component diagram — recognize it by name as a candidate **implementation view** (an allocation view type this repo does not currently have a skill for) rather than stretching `component-diagram`'s per-service Go Package Structure section to serve a cross-service concern it was not designed for.
- Add a **context diagram** at each view's own level, not just at the system level: `component-diagram` currently has no equivalent of `system-context-diagram`'s external-boundary framing scoped to *one service* (what does this service talk to, restated at Level 3, before component internals are shown) — the book treats a per-view context diagram as part of every documentation package, not a one-time system-level artifact.

## Candidate New Skills/Agents

**No new skill or agent is proposed.** Every finding in this document is a sharpening of the three existing diagram skills' vocabulary and completeness (module/C&C/allocation naming, element catalogs, per-view rationale) — not new domain expertise that needs its own owner. `enterprise-architect` already owns all three diagram skills; the book's contribution is precision within that existing ownership, not a new bounded context of knowledge.

**Explicitly not proposed:**
- **A standalone `architecture-viewpoint-catalog` skill enumerating all of Views and Beyond's view types.** This repo's product context (a small number of Go services, one architect agent, one PM reviewer) will never need the book's full catalog — generalization module views, work-assignment allocation views, and multi-stakeholder documentation roadmaps solve problems of enterprise scale (many teams, many long-lived subsystems, formal contractor handoffs) this repo does not have. Importing the full viewpoint taxonomy as its own skill would produce a component nobody's workflow calls into, which `skill-authoring-standards`' progressive-disclosure discipline treats as the same failure mode as an unread reference file.
- **A separate `deployment-view` or `implementation-view` skill split out from `container-diagram`/`component-diagram`.** The `container-diagram` conflation finding (C&C vs. allocation concerns mixed in one diagram) is real, but the fix is a structural edit to that skill's Output Format template (a second table, or an explicit combined-view justification per Ch. 9) — not a new skill. Splitting it into a separate skill would itself violate the book's own warning against producing views nobody asked for; the right-sized fix stays inside the skill that already owns the enterprise-architect's diagramming workflow.

## Key Terminology

Worth considering for `skills/glossary-management/`'s Ubiquitous Language:

- **View** — a representation of a whole system from the perspective of a related set of concerns (as distinct from "diagram," which is just the picture inside a view's documentation package). This repo's vocabulary currently uses "diagram" exclusively; adopting "view" would let skills distinguish the concept (a documentation package) from its primary artifact (the picture).
- **Viewpoint** — the conventions, element/relation vocabulary, and notation used to construct all views of one kind; the reusable pattern behind any one view. Distinct from a view (the instance). This repo's three diagram skills are each, in substance, viewpoint definitions and should be recognized as such.
- **Module View / Component-and-Connector (C&C) View / Allocation View** — the book's three major view types. This repo currently has no vocabulary distinguishing these; `container-diagram` and `component-diagram` would both benefit from being able to name precisely which type (or types, if deliberately combined) each diagram is.
- **Element Catalog** — the tabular enumeration of every element and relation in a view's primary presentation, carrying properties the picture cannot show. This repo's diagram skills already produce something functionally close to this (their "Elements"/"Containers"/"Components" tables) without using the term or the book's fuller checklist of what belongs in one.
- **Documentation Package** — the complete set of parts (primary presentation, element catalog, context diagram, variability guide, rationale) that makes a view reviewable and buildable, not just visually clear. Naming this term would let this repo's Output Format templates be checked against a known-complete checklist rather than an ad hoc one.
- **Combined View** — a deliberate, justified overlay of two view types in one diagram (e.g., C&C + allocation), as distinct from an unexamined conflation of concerns. Precisely the term needed to resolve the `container-diagram` finding above: either the skill's current shape is a justified combined view, or it is an unnamed conflation — the term forces the choice to be made explicitly rather than left implicit.
- **Mapping Between Views** — the documented correspondence between elements in two different views (e.g., which module in a module view is implemented by which component in a C&C view) — relevant to formalizing the currently-implicit relationship between `component-diagram`'s layered module view and its Go Package Structure implementation view.

## Caveats

- **This book predates and is more general than C4 (Simon Brown's C4 model postdates it and is explicitly presented as a simplified, opinionated profile of Views and Beyond's C&C viewpoint for software teams).** C4's four "levels" are not this book's four anything — C4 collapses this book's richer, stakeholder-driven view-selection process into a fixed sequence (Context → Container → Component → Code) aimed at approachability for teams that will never read a SEI report. Do not read this document as saying C4 is wrong; C4 is a deliberately narrowed, more prescriptive descendant of exactly the C&C viewpoint this book describes, optimized for teams (like this plugin's target user, a non-programmer PM) who need a fixed, learnable convention over full method flexibility. The finding here is that C4's fixed sequence occasionally blurs a distinction (module vs. C&C vs. allocation) that this book keeps sharply separate — not that C4 should be abandoned in favor of full Views and Beyond.
- **Do not read this document as recommending this repo adopt the full Views and Beyond method wholesale — that would over-serve a solo-operator, frugal context.** The book describes an enterprise/DoD-contractor-scale documentation discipline (its own running examples are large, multi-team, multi-stakeholder systems) with view types (generalization module views, work-assignment allocation views) that have no clear near-term need here. The actionable recommendation is narrower: borrow the *vocabulary* (module/C&C/allocation, viewpoint, documentation package, element catalog, rationale) to sharpen what the three existing diagram skills already do, and borrow *stakeholder-driven selection* as the discipline for deciding whether a new view type (e.g., an implementation view for the Go monorepo-wide source tree) is worth adding — not to mechanically produce all seven-plus view types the book catalogs.
- **Richards & Ford's book (already researched in this repo) touches this book's territory only in passing and does not cover its actual content** — its Ch. 19–20 "diagram/decision separation" observation (see `fundamentals-of-software-architecture-richards-ford.md`, Core Concepts) validates that diagrams, decisions, and characteristics are three separate artifact types that must stay synchronized, but never names module/C&C/allocation views, viewpoints, documentation packages, element catalogs, or stakeholder-driven view selection — all of which are this book's actual, distinguishing content and are new ground for this repo's research corpus.
- **"Views and Beyond" is a documentation *method*, not a diagramming notation — it is compatible with, not a competitor to, this repo's ASCII-diagram convention.** The book's primary presentations are typically UML or informal box-and-line notation; nothing about the method requires any particular notation, so this repo's existing choice (ASCII diagrams for PM-reviewability, per `CLAUDE.md`'s "Artifact Standards") is fully compatible with everything recommended here. The gap this document identifies is entirely about which concerns a diagram documents and how completely, never about what notation renders it.
- **The book's rationale concept and this repo's ADR concept overlap in name only, not in scope, and should not be merged into one artifact.** A view's Rationale (this book) explains one diagram's shape; an ADR (`adr-authoring`) explains one cross-cutting architectural decision, which may span or outlive many views. Collapsing them would violate `adr-authoring`'s own "mega-ADR" anti-pattern (a record covering unrelated concerns with different lifecycles) in the opposite direction — a "mega-rationale" burying view-shape notes inside decisions that outlive any one diagram, or vice versa.
