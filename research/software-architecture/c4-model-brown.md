# The C4 Model for Visualising Software Architecture
**Authors:** Simon Brown (the C4 model, published free at c4model.com; *Software Architecture for Developers, Volume 2: Visualise, document and explore your software architecture*, Leanpub)
**Domain:** Software Architecture — diagramming and lightweight documentation (C4 abstractions, diagram set, notation, diagrams as code)

This file grounds `system-context-diagram`, `container-diagram` and `component-diagram`, which all name Simon Brown but cite no research file for C4 itself (W2-26). It does not repeat `documenting-software-architectures-clements.md` (viewtypes, documentation packages, element catalogs, rationale) or `just-enough-software-architecture-fairbanks.md` (models answer a named question, risk-driven depth, the model-code gap). It covers what C4 actually defines, so the skills can say which rules are Brown's, which are Clements', and which are the plugin's own. Decisions D047-6, D047-11 and D047-13 set the frame.

## Core Concepts

- **Abstractions come before notation.** Brown's starting point is that teams draw confusing diagrams because they lack a shared vocabulary for the *things* in a system, not because they lack a notation. C4 fixes a small hierarchy of abstractions first; any notation (boxes and lines, UML, ASCII) can then show them. A diagram is only readable when every box is clearly one of these abstractions.
- **There are five abstractions, in a hierarchy:**
  - **Person:** a human user or role (a type of user, not a named individual).
  - **Software system:** the highest level of abstraction; something that delivers value to its users, owned and built by one team or organisation. Both the system being described and the external systems it talks to are software systems.
  - **Container:** a separately runnable or deployable unit inside a software system that executes code or stores data: a server-side web application, a single-page app, a mobile app, a database schema, a file store, a serverless function, a batch job. **It is not a Docker container.** Brown chose the word before Docker made it popular and has said many times the two are unrelated; a Docker container is a deployment detail that belongs on a deployment diagram.
  - **Component:** a grouping of related functionality behind a well-defined interface, inside one container. Components are not separately deployable; they run in their container's process. In code a component is usually a set of classes or a package, not a single class.
  - **Code:** the classes, interfaces, functions and tables that implement a component.
- **The four core diagrams zoom through that hierarchy, like an online map.**
  - **Level 1, System Context:** the system as one box, the people who use it and the software systems it interacts with. Scope: one software system. Audience: everyone, technical or not.
  - **Level 2, Container:** the containers inside that one system, their technology choices and how they communicate. Scope: one software system.
  - **Level 3, Component:** the components inside one container and how they relate. Scope: one container.
  - **Level 4, Code:** how one component is implemented, usually a UML class diagram or an entity-relationship diagram. Scope: one component.
- **Only the first two are needed by most teams.** Brown says Component diagrams are optional and worth drawing only where they add value, typically for a complex container, and that Code diagrams are rarely worth drawing by hand; generate them from the code with tooling if at all, because hand-drawn code diagrams go stale fastest.
- **Three supplementary diagrams answer questions the core four don't.**
  - **System Landscape:** like a context diagram with no single focus system; shows all the systems and people in an organisation or portfolio.
  - **Dynamic:** shows how elements collaborate at runtime for one feature, use case or story, with numbered interactions. It is roughly a UML communication or sequence diagram, and can be drawn at container or component level.
  - **Deployment:** shows how instances of software systems and containers map to infrastructure in one deployment environment (production, staging). It nests **deployment nodes** (a cloud region, a cluster, a node, a pod, a database server) and adds **infrastructure nodes** (load balancers, DNS, firewalls). One deployment diagram per environment.
- **C4 is notation-independent, but every diagram must explain itself.** Brown's notation guidance, also published as a diagram review checklist:
  - every diagram has a **title** that states its type and scope;
  - every diagram has a **key (legend)** explaining shapes, colours, line styles and arrowheads, even when the notation seems obvious;
  - every element states its **type** (Person, Software System, Container, Component), its name and a short description of its responsibility;
  - every **container** carries a technology label, and components may carry one;
  - every relationship is a **one-directional arrow** with a **descriptive label** that matches the direction ("Reads data from", "Sends order events to"), and inter-container relationships carry a **technology or protocol** label;
  - be explicit about **what a line means**: dependency, data flow or initiation. Pick one meaning and keep it consistent, and say which in the key. Avoid two-headed arrows, which hide what flows which way;
  - no unexplained acronyms; colours are a choice, not part of C4, and must never be the only way a meaning is shown.
- **Microservices are mapped by ownership, not by technology.** Brown's guidance: if one team owns the services inside the system boundary, each microservice is a group of containers (typically an API plus its own data store) on the Container diagram, optionally grouped with a boundary. If separate teams own them, each service can be modelled as its own software system, with its own context and container diagrams. The same rule decides whether a shared platform is a container or an external system.
- **A model is not a diagram.** In a modelling tool such as Structurizr, elements and relationships are defined once and each diagram is a view onto that model. Renaming an element changes every diagram; levels can't drift apart. Hand-drawn diagrams (whiteboard, ASCII, Visio, Mermaid flowcharts) are separate pictures and drift silently.
- **C4 sits beside the views tradition rather than inside it.** Brown credits Kruchten's 4+1 and the broader views literature, and says C4 simplifies them for developers: the core four diagrams are static structure, the Dynamic diagram covers the runtime scenarios (roughly the "+1"), and the Deployment diagram covers the physical view. In Clements' terms, Container and Deployment diagrams are C&C and allocation views, and a Component diagram sits between C&C and module views because a component is both a runtime part of a process and a grouping of code. Brown also borrows Fairbanks' **model-code gap** and architecturally evident coding style: components should be visible in the code's package structure.

## Actionable Techniques

- **Draw in order and stop early.** System Context, then Container. Draw a Component diagram only for a container whose internals a reader must understand before changing it; never draw Code diagrams by hand.
- **Set the scope before drawing.** One software system for Levels 1 and 2, one container for Level 3, one environment for a deployment diagram. An element outside the scope appears only as a neighbour (a person, an external system, another container).
- **Use the review checklist as the quality gate.** For each diagram: title, key, element types, descriptions, technology on containers and inter-container lines, one-directional labelled arrows, and a stated arrow meaning.
- **Keep levels consistent by naming.** Every person and external system on the Container diagram must appear, with the same name, on the System Context diagram; every component's container must exist on the Container diagram. With hand-drawn diagrams, check this explicitly, because no model does it for you.
- **Model a modular monolith honestly.** One application container plus its database on the Container diagram; the modules (for this plugin, the Bounded Contexts) are components inside that container, not separate containers.
- **Show message brokers so the reader can still see who talks to whom.** Brown's FAQ offers several options (the broker as a container, each topic or queue as a container, or labels that say "via topic X"). Avoid a hub-and-spoke picture where every arrow points at the broker and the real producer-consumer pairs vanish.
- **Use diagrams as code where tooling is accepted.** Structurizr DSL (open source; one model, many views, exports to PlantUML, Mermaid and others), C4-PlantUML, and Mermaid's C4 diagram types (`C4Context`, `C4Container`, `C4Component`, `C4Dynamic`, `C4Deployment`, still marked experimental in Mermaid) all render C4 from text. A plain-text ASCII picture plus element catalog tables still satisfies C4, because C4 does not require any notation.
- **Avoid the common mistakes:** mixing levels on one diagram (a database next to a person on a context diagram, or a class inside a container diagram); boxes with no type or description; lines with no label or labels like "uses"; ambiguous or two-headed arrows; no key; treating "container" as a Docker container; one diagram per microservice with no Container diagram tying them together.

## Key Terminology

- **Person / Software System / Container / Component / Code** — C4's five abstractions, from outermost to innermost.
- **Container** — a separately runnable or deployable unit that executes code or stores data; not a Docker container.
- **System Context / Container / Component / Code diagram** — the four core C4 levels; each has a fixed scope.
- **System Landscape / Dynamic / Deployment diagram** — the supplementary diagrams: all systems in an organisation; a numbered runtime flow; container instances on infrastructure in one environment.
- **Deployment node / Infrastructure node** — a nested place where containers run (region, cluster, server, pod); a piece of supporting infrastructure (load balancer, DNS).
- **Key (legend)** — the explanation of shapes, colours and line styles every C4 diagram carries.
- **Model vs diagram** — elements defined once in a model and rendered as many views, versus separately drawn pictures.
- **Diagrams as code** — C4 written as text (Structurizr DSL, C4-PlantUML, Mermaid C4) and rendered by a tool.

## Caveats

- **Recalled with confidence:** the five abstractions and the definition of a container (including that it is not a Docker container); the four core levels and their scopes; the three supplementary diagrams; Component diagrams optional and Code diagrams rarely hand-drawn; notation independence; title, key, types, technology labels, one-directional labelled arrows; the ownership-based microservices guidance; Structurizr DSL, C4-PlantUML and Mermaid's C4 support (marked experimental); Brown's chapter on packaging in Martin's *Clean Architecture*.
- **Uncertain:** c4model.com is revised over time, so its wording, page layout and FAQ answers (especially the message-broker options and the exact review checklist items) may differ from what is paraphrased here. The book's chapter names and order are not given because they are not recalled reliably; the "software guidebook" and decision log are recalled from Brown's writing but may sit in Volume 2 or elsewhere. Brown's statement of how C4 relates to 4+1 is paraphrased from memory of his FAQ and talks.
- **No quotations or page numbers.** Everything is paraphrased from working knowledge, not a fresh re-read.
- **Plugin choices are not Brown's.** ASCII as the primary notation, the colour scheme, the element catalog and rationale sections (from Clements), and the deployment view as a section of `container-diagram` are this plugin's decisions. They are compatible with C4, which prescribes abstractions and diagram discipline, not a format.
