# The API-First Transformation
**Authors:** Kin Lane
**Domain:** API Strategy and Organizational Transformation

## Core Concepts

- **API-First as an operating-model shift, not a design technique.** Lane's central claim (drawn from his API Evangelist writing and consulting practice) is that "API-First" is most often used to mean "write the OpenAPI spec before the code" — the definition `skills/api-contract-design/SKILL.md` already implements in full ("API-First design means the API contract is designed and agreed upon before any implementation code is written... The contract is the source of truth"). Lane treats that as necessary but shallow. His API-First is an organization-wide operating model: every internal capability, not just externally-facing ones, is built and exposed as an API by default, treated as a product with its own lifecycle independent of any one consuming application, and made discoverable so other teams reuse it instead of rebuilding it. The book is about the organizational discipline required to make that default actually hold at scale — governance, an internal marketplace, a portfolio view across dozens or hundreds of APIs — not about resource naming or schema shape, which is `api-design-patterns-geewax.md`'s territory (see Caveats).
- **The API as a product, with its own product manager, lifecycle, and roadmap.** Lane's most load-bearing idea: an API is not an artifact of a project that ships once and gets maintained as a side effect. It is a product in its own right — it has consumers (internal and/or external), a value proposition distinct from any one consuming application, a deprecation and versioning roadmap, and ideally an owner whose job includes the API's adoption and health, not just its uptime. This reframing is what makes an API "the product" rather than "the plumbing behind the product" — a genuinely different posture from treating the API as an implementation detail of one UI.
- **API governance as a scaling mechanism, typically instantiated as a review board plus a shared style guide.** As the number of APIs and API-producing teams grows, Lane argues an organization needs a governance function to keep contracts consistent, prevent duplicate/competing APIs for the same capability, and enforce a shared design standard before publication. In large organizations this literally means an API governance board or review committee that gates publication — a real, standing, multi-person institution with its own meeting cadence and escalation path. The mechanism (a board with review authority) is scale-dependent; the underlying discipline it enforces (a written style guide, checked consistently before an API is considered "done") is not — see Applies To and Actionable Techniques for how the latter survives without the former.
- **The internal API marketplace / API portfolio / catalog.** A recurring structural pattern in the book: once an organization has more than a handful of APIs, discoverability itself becomes a problem — teams don't know an API already exists for a capability they're about to rebuild. Lane's answer is an internal marketplace or portfolio: a searchable catalog of every API, its owner, its status (in development / stable / deprecated), its consumers, and its documentation, so "build vs. reuse" is a decision teams can actually make instead of defaulting to rebuild because discovery is too expensive. This assumes multiple producing teams and multiple potentially-competing consumers — a structural assumption this repo's context does not currently meet (see Caveats).
- **API lifecycle stages, from design through deprecation, each with its own required artifacts and gates.** Lane frames the API lifecycle as a named sequence — design, define (the actual OpenAPI contract), develop, deploy, document, discovery, testing, and eventually deprecation and retirement — with the insistence that each stage produces something checkable and durable (a spec, a changelog, a deprecation notice), not just tribal knowledge. `api-contract-design`'s existing Versioning Strategy table (additive vs. breaking, 6-month sunset, `Deprecation` header) already implements the deprecation/retirement end of this lifecycle in a mechanically precise way that meets or exceeds what the book asks for in prose.
- **API evangelism and internal developer experience as a deliberate discipline, not a byproduct.** A theme specific to Lane's own career (he coined "API Evangelist") — the book argues that internal adoption of an API-First culture requires active internal marketing: onboarding docs, a "getting started in 5 minutes" experience, internal advocates, and metrics on internal adoption, treated with the same seriousness as external developer relations. This is explicitly a many-team, many-consumer concern — evangelizing an API to teams who might otherwise ignore it — and has no clean analog when there is exactly one consumer of every API this repo's agents design (see Caveats).
- **Design-first consistency as the mechanism that makes an API portfolio composable.** Underneath the governance-board machinery, the actual technical claim Lane makes repeatedly is narrower and more durable: a portfolio of APIs is only valuable as a portfolio if they're consistent enough with each other that a consumer who learns one can predict the shape of the next (consistent auth, consistent pagination, consistent error shape, consistent naming). Governance-as-institution is one way to get there; a single, well-enforced style guide referenced by every API is another, cheaper way to get the same consistency without the standing committee. `api-contract-design`'s own conventions (standard error envelope, cursor pagination, BearerAuth applied globally) are already exactly this kind of cross-API consistency — just currently enforced by one skill's authority rather than a governance process, because there is currently one producing agent (`enterprise-architect`) rather than many competing teams.
- **"API as the primary interface" — the API precedes and outlives any one UI.** Lane's framing (echoed across the API-First literature he represents) is that in an API-First organization, the API is designed as the durable, primary product surface, and any given UI (web, mobile, partner integration) is one of potentially several consumers built on top of it — never the other way around, where the API gets bolted on after a UI ships to expose "whatever the UI needed." This is a direct match for this repo's existing sequencing: `enterprise-architect` designs the Command Catalog, Read Model, and OpenAPI contract before `frontend-engineer` or `backend-engineer` write a line of implementation — the API is already positioned as upstream of, not derived from, any UI.

## Actionable Techniques

- **Frame the API contract explicitly as "the product" in `api-contract-design`'s Purpose section**, not just as "the source of truth" it already is. The skill's opening sentence ("API-First design means the API contract is designed and agreed upon before any implementation code is written") is Lane's shallow/mechanical definition of API-First. Add one sentence naming the deeper claim explicitly relevant at this repo's scale: the OpenAPI contract is not merely a technical artifact that gates implementation — for any product this factory builds, it is the durable interface other systems (a future mobile client, a future partner integration, a future internal automation) will be built against, so its design quality is a product decision, reviewed with the same seriousness as a pricing model or positioning statement, not an implementation formality that happens to come first.
- **Adopt a lightweight "API Contract Review Checklist" as the solo-operator-scale substitute for Lane's governance board**, added to `api-contract-design` rather than proposed as a new skill. Lane's board exists to catch inconsistency across many producing teams before publication; with one producing agent, the same failure mode (an endpoint that quietly drifts from the skill's own conventions — a new error shape, an unversioned path, a missing idempotency header) is still possible, just caused by drift within one session rather than disagreement between teams. A short, explicit checklist — run once per OpenAPI spec before it's considered final — is the right-sized mechanism: it inherits every row already in the skill's existing Quality Criteria table (Ubiquitous Language resources, all Commands covered, all Read Models covered, standard error envelope, versioned, auth on all endpoints, idempotency header, pagination convention) rather than inventing new criteria. What Lane's book adds is not new content but the *discipline of running it as a distinct, named gate* — a self-review step an agent performs deliberately before calling a contract done, the same way `adr-authoring`'s `scripts/validate-adr.sh` is a deliberate, distinct gate rather than folded silently into "writing the ADR."
- **Add a one-paragraph "API as a Product" framing note to `adr-authoring`'s Architecture Principle guidance** (`references/architecture-principles.md`) as a candidate, illustrative Principle a product's enterprise-architect could adopt: "This product's public/partner-facing API contracts are designed and versioned as durable products, not as incidental plumbing for the current UI — breaking changes require the same sunset discipline regardless of how few consumers exist today." This is a genuine transfer: Lane's "API as a product" claim is a *principle* in exactly this repo's Decision-vs-Principle sense (Fundamentals of Software Architecture, Ch. 18) — general, durable guidance that would be cited by many future ADRs about versioning and deprecation, not a single point-in-time decision — so it belongs as a Principle candidate, not a rewrite of the skill's mechanics.
- **Do not add an API catalog, marketplace, or portfolio artifact.** Lane's discoverability mechanism solves a specific problem — many teams, many APIs, expensive discovery — that does not exist when one agent (`enterprise-architect`) designs every API contract for a product and already knows its full inventory by construction. If this factory ever produces multiple services with genuinely independent APIs for the same product, the closest existing artifact to extend is `api-contract-design`'s own `api-contract-summary.md` output (which already has a "Consumer Registry" section) — a manually-maintained per-product index of summaries would be the right-sized version of a catalog, not a new marketplace skill or agent.
- **When a product's OpenAPI contract is genuinely public-facing or partner-facing (not solely consumed by this repo's own `frontend-engineer`), have `enterprise-architect` explicitly flag that in the contract summary** — Lane's book is clear that the governance and lifecycle discipline matters most precisely at the point an API stops being purely internal. A contract with only one internal consumer can tolerate looser versioning discipline in principle (though `api-contract-design`'s existing policy does not currently relax it); a contract with external, uncoordinated consumers cannot skip the 6-month sunset window or the `Deprecation` header under any circumstance, because those consumers cannot be asked in a hallway. This is a distinction worth surfacing, not a new mechanism — the skill's existing Versioning Strategy table already provides the mechanism.

## Candidate New Skills/Agents

**No new skill or agent is proposed.** Every technique from this book that genuinely transfers at this repo's scale — the "API as a product" framing, a lightweight self-review checklist, an illustrative Principle — is a small addition to `api-contract-design` or `adr-authoring`'s existing Principle format, not new domain expertise requiring its own owner. This mirrors the same judgment call `api-design-patterns-geewax.md` made for the same skill in the same research cluster (no new skill proposed there either) and the pattern several other files in this repo's research corpus have already reached when a book's content turns out to be organizational-scale rather than technique-scale (see the SRE book's finding: "a solo operator has no rotation to formalize, so the honest output is a caveat and a small addition... not a fabricated on-call-scheduling skill serving a team that doesn't exist" — the same reasoning applies here to a fabricated API-governance-board skill serving teams that don't exist).

**Explicitly not proposed:**
- **An `api-governance` skill or agent modeling a review board, RFC process, or multi-team escalation path.** This repo has exactly one agent (`enterprise-architect`) producing API contracts for any given product. A governance board's entire reason to exist — arbitrating disagreement between independent teams and catching drift introduced by people who didn't write the shared style guide — has no referent when one agent, working from one skill, produces every contract. The governance *discipline* (a consistent, checked style) already exists via the skill's own Quality Criteria table; only the *institution* (a board) is being declined, and only because there is no plural "teams" for it to govern.
- **An `api-catalog` or `api-marketplace` skill.** Same reasoning as the governance board — discoverability-at-scale is a real problem only once "which team already built this" is a genuine unknown, which requires multiple producing teams and a nontrivial API count. A single small addition to the existing `api-contract-summary.md` template (a per-product index, if this repo ever needs one) is the right-sized fallback, not a new artifact type.

## Key Terminology

Worth considering for `skills/glossary-management/`'s Ubiquitous Language:

- **API-First Design** — already present in `skills/glossary-management/references/ubiquitous-language.md` line 64 ("The practice of defining an API contract before implementing either the provider or the consumer. The contract is the single source of truth for both sides."). This existing entry captures Lane's shallow/mechanical definition precisely; it does not currently capture his deeper organizational-operating-model sense (API-as-product, governed portfolio). Given this repo's single-producer context, extending the glossary entry to cover the deeper sense is not recommended — it would define a term for an organizational structure (a governed multi-team portfolio) that does not exist here, and the existing definition already matches what `api-contract-design` actually practices.
- **API as a Product** — Lane's framing of an API as having its own lifecycle, owner, and value proposition independent of any single consuming application. Not currently named in this repo's glossary. Low-priority addition: the concept is real and worth the one-sentence framing note recommended above in `api-contract-design`'s Purpose section, but does not need a standalone glossary entry at this repo's current one-agent, one-consumer-set scale — it would read as aspirational vocabulary for an organizational pattern (multiple independent products competing to consume the same API) this repo does not yet have.
- **API Governance** — Lane's term for the review/consistency-enforcement function, typically instantiated as a board. Not recommended for the glossary as defined in the book (an institution) — this repo's equivalent is a checklist, not a governed process with its own vocabulary, and coining the term here would overstate what the mechanism actually is.
- **Internal API Marketplace / API Portfolio** — Lane's terms for the searchable, multi-API catalog. Not recommended for the glossary; no referent exists at this repo's current scale (see Candidate New Skills/Agents above).

## Caveats

- **This is the organizational/strategic half of API-First; `api-design-patterns-geewax.md` (same directory, read in full before writing this file) is the technical/tactical half — the two do not overlap and should not be merged.** Geewax's book (JJ Geewax, *API Design Patterns*) covers resource-oriented design, standard methods, custom methods, the LRO `Operation` shape, error-model field structure, resource revisions/ETags, and field masks — all mechanics of what a single API contract's schema and endpoints should look like. Lane's book never engages with any of that; it has no opinion on whether pagination should use a cursor or a page token, no error-model schema, no resource-naming convention. It is about who owns an API, how many APIs an organization builds, how they're governed as a portfolio, and how internal teams discover and adopt them. This document intentionally contains zero content duplicating Geewax's — no resource naming, no HTTP method table, no error envelope, no pagination convention — and cross-references `api-design-patterns-geewax.md` above wherever the topics are adjacent (e.g., both touch "the contract as source of truth," but from organizational-ownership and technical-mechanics angles respectively).
- **Most of this book's central machinery — the governance board, the internal marketplace, API evangelism to internal teams, portfolio-wide metrics — assumes a multi-team organization with potentially competing or duplicate efforts, and does not transfer to this repo's single-operator, single-agent-per-domain context.** Per `CLAUDE.md`'s "Who Shafi Is" section, this plugin has exactly one operator (a PM, not an engineer) directing exactly one engineering agent per domain per product. There is no second team that might independently rebuild an API `enterprise-architect` already designed, no internal audience to evangelize an API to, and no portfolio large enough that discovery itself becomes the bottleneck. Treat the governance/marketplace/evangelism chapters as source material for vocabulary and for recognizing *when* (if ever) this repo's context changes enough to need them — not as content to force-fit into the current single-agent reality. This is the same judgment call this repo's research corpus has already made for Site Reliability Engineering's on-call rotation content and the DevOps Handbook's team-coordination/"swarming" mechanics: the honest output for an organizational-scale mechanism with no current referent is a caveat plus a small right-sized addition elsewhere, not an invented skill serving an audience that doesn't exist.
- **The book is written from Lane's vantage point as an external analyst and consultant surveying many organizations' API programs (API Evangelist), not as a single practitioner's hands-on implementation guide** — it is heavier on pattern description ("organizations that succeed at API-First tend to...") and lighter on prescriptive step-by-step technique than, say, Geewax's book or Richards & Ford's. Where this document extracts an "actionable technique," it is this document's own translation of a described organizational pattern into something a single agent can actually do — not a literal recipe lifted from the book, which does not target a single-operator audience at all.
- **Do not read the absence of a governance board or marketplace here as "this repo doesn't need API discipline."** The opposite is true: `api-contract-design`'s existing Quality Criteria table, standard error envelope, and global auth/versioning/idempotency conventions already deliver the *outcome* Lane's governance machinery exists to produce (consistency across every API surface) — this repo gets that outcome for free because one skill's authority is unambiguous, where a multi-team organization needs a board precisely because no single authority is unambiguous. The lightweight review-checklist technique recommended above exists to keep that outcome true over time, not to introduce discipline that was missing.
