# Let's Go & Let's Go Further: Practical, Production-Grade JSON APIs in Go, From Scratch
**Authors:** Alex Edwards
**Domain:** Software Architecture & Implementation (Go, applied/practitioner level — self-published, two continuous books treated here as one project/methodology)

## Core Concepts

- **A `cmd/api` + `internal/` + `migrations/` project layout, with the Go compiler itself as the enforcement mechanism.** Edwards builds one API service from an empty directory, and the very first structural decision he makes is putting all business logic under `internal/` specifically *because* the Go toolchain refuses to let code outside the module import it — not as a stylistic nicety but as a load-bearing constraint that keeps the package layout honest as the codebase grows. `cmd/api` holds only the composition root (`main.go`, flag/env parsing, routing, and the `application` struct that all handlers hang off); everything else — models, validation, the JSON helpers — lives in `internal/`.
- **Graceful shutdown as a deliberate, worked capstone pattern**, not an afterthought: a `shutdownError chan error` created before the server starts, a goroutine that blocks on `signal.Notify` for `SIGINT`/`SIGTERM`, calls `srv.Shutdown(ctx)` with a `context.WithTimeout` bound (so in-flight requests get a deadline to finish, not an unbounded wait), and reports the shutdown's own error back to `main` over that channel so a failed shutdown is itself a fatal, logged condition rather than swallowed.
- **A request-scoped, structured, leveled logger** (`log/slog` in the current edition; a hand-rolled `jsonlog.Logger` in the original) attached to the application struct and threaded through every handler via a small `logError`/`logRequest` middleware pair, so every log line carries a consistent set of fields (method, URI, status) without each handler re-deriving them.
- **One centralized error-response vocabulary**: `errorResponse`, `serverErrorResponse`, `notFoundResponse`, `methodNotAllowedResponse`, `badRequestResponse`, `failedValidationResponse` — a small closed set of helper methods on the `application` struct that every handler calls instead of writing `http.Error`/`json.NewEncoder` inline, so the JSON error shape (`{"error": "..."}`) and the status-code choice are made in exactly one place each.
- **Fail-fast, validated startup configuration**: a `config` struct populated from command-line flags (with `os.Getenv`-backed defaults for anything that must vary per-deployment, e.g. the database DSN), validated before the server starts — a missing or malformed value aborts the process immediately with a clear message, never surfaces as a nil-pointer panic three requests into production traffic.
- **Per-client rate limiting with `golang.org/x/time/rate`**, keyed by client IP by default (since early requests in the book's API are unauthenticated), implemented as a `map[string]*client` guarded by a `sync.Mutex`, with a background goroutine that periodically sweeps and evicts entries idle for more than a few minutes — explicitly framed as closing a memory-growth vector the naive "just add entries forever" version leaves open.
- **`database/sql` connection-pool tuning as an explicit, named topic**: `SetMaxOpenConns`, `SetMaxIdleConns`, and `SetConnMaxIdleTime` (`SetConnMaxLifetime` in earlier chapters) are each set from config flags with sane defaults and explained individually — too many open connections can exhaust the database's own connection limit or the host OS's file-descriptor limit; too many idle connections wastes memory for no benefit; a bounded idle lifetime avoids serving a connection the database or a middlebox has silently closed.
- **Versioned, `.sql`-file migrations run via the `migrate` CLI** (`golang-migrate/migrate`), with paired `.up.sql`/`.down.sql` files per change, applied as a discrete step separate from running the application — never auto-run inside the API binary's own startup path.
- **Panic-recovery middleware positioned outermost in the chain**, wrapping every other middleware and every route, that recovers from a panic, logs it, and — the specific, easy-to-miss detail — sets `Connection: close` on the response header before writing the 500, so Go's `net/http` server terminates the underlying TCP connection instead of returning it to the keep-alive pool in an unknown state.
- **URL-path API versioning (`/v1/...`) with a consistent JSON envelope**: every successful response is wrapped in a top-level named key (`envelope{"movie": movieData}`, `envelope{"movies": []Movie{...}}`) rather than returned as a bare array or object — deliberately, so a future field can be added at the top level (pagination metadata, a `next` link) without an existing bare-array response becoming ambiguous to extend.

## Actionable Techniques

- Add a one-line `Connection: close` header set to `go-middleware`'s `Recoverer` before it calls `writeError` for the recovered panic — the same "the server must not silently misbehave after an unrecoverable event" instinct the skill already applies to logging and span-recording, extended to the connection itself. A panic can leave the `http.ResponseWriter` mid-write or the handler goroutine's state undefined; returning that TCP connection to the keep-alive pool risks the *next* request on that connection reading a framing-corrupted response. This is a single header line, not a redesign, and it belongs exactly where `Recoverer` already lives.
- Where `go-chi-handler`'s worked example is a 204-No-Content mutation, add one worked GET/query-handler example showing the JSON success response actually written to the wire, and state explicitly whether it uses a named top-level envelope key (the pattern this skill's sibling `go-project-structure` already half-supports via its `Page[T]`/`Result[T]` generic wrappers) or a bare payload. Right now the error envelope (`ErrorResponse`) is fully specified and the success envelope is not shown anywhere in the skill — a query handler's actual wire shape is inferable from `queries.ListDataAssetsHandler`'s return type but never rendered as JSON in the skill itself, so a reader cannot confirm consistency between error and success response shapes from this skill alone.
- Note, as a documentation cross-reference rather than a new finding, that `go-middleware`'s `RateLimit` shows only the call site (`m.limiter.Allow(sub.ID.String())`) and defers the limiter's own construction to `security-implementation` — a skill outside this Go-prefixed roster. If that skill does not already show the store's eviction strategy for idle per-subject limiter entries, Edwards' worked cleanup goroutine (sweep + evict entries idle beyond a threshold, guarded by the same mutex used for lookups) is the concrete pattern to check it against; an unbounded `map[string]*rate.Limiter` that never evicts is the same class of slow leak `go-concurrency-patterns` already treats as a defect for goroutines, just applied to a map instead.
- When citing this repo's `pgxpool` configuration against Edwards' `database/sql` triplet (`SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxIdleTime`), note the field-name translation for future skill maintainers: `pgxpool.Config`'s `MaxConns`/`MaxConnLifetime`/`MaxConnIdleTime` are the correct pgx-native equivalents of the first and third, but `pgxpool.Config` also exposes a `MinConns` field (default 0, keeps a minimum number of warm connections) that most closely maps to what `SetMaxIdleConns` protects against — avoiding a burst of requests paying full connection-setup cost simultaneously after a quiet period. `go-service-skeleton`'s pool construction does not set `MinConns`; this is a minor, one-field-line completion, not a gap in method.

## Caveats

- **This is, as predicted, the closest real-world stack match in the cluster — and the yield reflects that: mostly confirmation, a small number of genuinely specific findings, no sweeping gaps.** Edwards builds the exact shape this repo's tech-stack defaults name (Go, a minimal router, PostgreSQL, a production JSON API), and the 24-skill Go roster already implements nearly everything the two books teach, in most cases more rigorously (graceful shutdown generalized via `errgroup`, error-mapping consolidated to one switch, migrations with expand/contract and tenant-awareness the books never need for a single-tenant demo app). Treat the three specific findings above (panic-recovery header, missing success-envelope example, rate-limiter eviction cross-check) as real and worth a small edit each — not as evidence of a deeper gap.
- **The `Connection: close` finding is the highest-confidence, most concrete gap in this document.** It is a single, well-known, specifically-motivated line from Edwards' own text (the panic-recovery chapter states the reasoning explicitly), checked directly against `go-middleware`'s full `Recoverer` code block, Rules, Quality Criteria, and Anti-Patterns — absent from all of them. This is the kind of narrow, mechanical, high-signal finding this research cluster is meant to surface.
- **The success-envelope finding is a documentation gap, not a confirmed behavioral gap.** It is entirely possible the repo's actual generated code already wraps success responses consistently and `go-chi-handler` simply never shows the example — the skill cannot currently prove or disprove this either way from what's written, which is itself the finding: a skill this mature should not leave its own consistency claim unverifiable.
- **The rate-limiter eviction finding is the weakest of the three, flagged with appropriate uncertainty.** `go-middleware` explicitly defers the limiter's internals to `security-implementation`, which this pass did not read (out of scope: not a Go-prefixed skill, and the task specified it as lower priority). The honest, calibrated statement is "verify this exists in the deferred skill," not "this is missing" — presented that way in Applies To and Actionable Techniques above.
- **Where the books are shallower than this repo (single-service scope, RBAC-less/simpler auth, no outbox, no CQRS, no multi-tenancy, `database/sql` instead of `pgx`), that is the expected, correct outcome of checking an introductory-to-intermediate, single-developer-project book against an already-mature, considerably more sophisticated skill set — not a signal to dilute this repo's skills toward the books' simpler defaults.** Edwards' books are explicitly written to take a reader with no prior Go experience to one working, deployed API; this repo's skills assume and build for a distributed, multi-tenant, event-driven system from the start. The alignment found here is strongest precisely in the areas — HTTP server hygiene, config validation, migrations, rate limiting, connection pooling — that are genuinely stack-shape-independent and therefore transfer cleanly regardless of that scope difference.
