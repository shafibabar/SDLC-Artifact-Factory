# Concurrency in Go: Tools and Techniques for Developers
**Authors:** Katherine Cox-Buday
**Domain:** Software Architecture & Implementation (Go concurrency, foundational/deep-dive level)

## Core Concepts

- **CSP (Communicating Sequential Processes) as Go's concurrency model, with an explicit, non-dogmatic decision procedure for channels vs. `sync` primitives.** The book's central move (ch. 2–3) is not "channels are always right" — it's a heuristic: reach for a channel when you are transferring *ownership* of a piece of data, coordinating multiple pieces of logic, or communicating an occurrence (a signal); reach for `sync.Mutex`/`sync.RWMutex` when you are guarding access to a struct's *internal* state and the critical section is small. Channels compose and make ownership explicit; mutexes are often faster and simpler for a tight, private critical section. The book is explicit that picking a mutex over a channel is not "doing Go wrong."
- **Confinement as a third alternative to both channels and mutexes.** Lexical confinement (a variable is only ever visible, by scope, to one goroutine) and ad hoc confinement (a convention — e.g., "only this goroutine writes to this slot" — enforced by discipline rather than the compiler) eliminate the need for synchronization entirely, by construction. The book treats this as underused and worth reaching for before either channel or mutex.
- **Composable pipeline vocabulary**: a *generator* function converts a discrete set of values into a channel; a *stage* is a function whose in-channel and out-channel are the same type, so stages compose by chaining; *fan-out* distributes one stage's input across N goroutines to parallelize CPU-bound work; *fan-in* (a dedicated multiplexing goroutine per source, joined on a `sync.WaitGroup`, closing the merged channel exactly once after all sources drain) merges results back into one channel. These are named, reusable shapes, not one-off code.
- **The `or-channel`, `or-done-channel`, `tee-channel`, and `bridge-channel` patterns** — small, general-purpose channel combinators built from first principles (recursion/goroutines wrapping raw channels) for the pre-`context.Context` (and still occasionally useful) world: combining several done-channels into one that closes when *any* closes (`or-channel`); wrapping a channel read with early-exit on a done-channel inside a `for...range`-like loop (`or-done-channel`); duplicating one channel's values to two independent consumers (`tee-channel`); and flattening a channel-of-channels into one channel (`bridge-channel`). The book presents these as the primitives you reach for when `context.Context` alone doesn't fit the shape of the problem — e.g., combining cancellation signals from *unrelated* sources that don't share a context tree.
- **`context.Context` as the idiomatic cancellation/deadline-propagation mechanism**, covered later in the book as the modern answer to much of what raw done-channels solve: `WithCancel`/`WithTimeout`/`WithDeadline`, `ctx.Done()` checked in a `select` inside any goroutine that could block, and the strict rule that `Context` is always the first parameter of a function, never a struct field — because storing it hides the cancellation scope from the call signature and invites a stale or wrong-scoped context being reused.
- **The `sync` package's full toolkit, each tool matched to one narrow job**: `sync.WaitGroup` to block until a known set of goroutines finish (with no result/error channel needed); `sync.Once` for exactly-once lazy initialization (thread-safe without a double-checked-locking hand-roll); `sync.Pool` to amortize allocation for short-lived, high-frequency objects under GC pressure; `sync/atomic` for lock-free counters and flags on the hottest, simplest shared state, cheaper than a mutex when the state is a single word.
- **Deadlock, livelock, and starvation as distinct failure modes with distinct vocabulary**, plus a sharp caveat on tooling: Go's runtime deadlock detector (the `fatal error: all goroutines are asleep - deadlock!` crash) only catches the case where *every* goroutine in the process is blocked simultaneously. A **partial deadlock** (some goroutines stuck, others still running) is invisible to the runtime and will not crash the process — it just quietly stops making progress in one corner. A **livelock** (goroutines actively running, repeatedly yielding to each other, making no net progress — the "two people in a hallway both stepping aside the same way" failure) is invisible to *any* automatic detector, including the race detector; it must be found by behavioral/load testing. **Starvation** (a goroutine that could proceed but is perpetually denied access — e.g., by an unfair lock or greedy sibling) is a related, distinct third mode.
- **The heartbeat pattern**: a long-running pipeline stage periodically signals liveness on a dedicated channel (a "still working" pulse — either time-based, on an interval independent of work, or event-based, one pulse per unit of work), so a supervisor can detect a *stalled but not crashed* goroutine — one that is still scheduled and technically alive but stuck (blocked on an unbounded dependency call, wedged in a loop) and therefore never produces on its result channel. This is a distinct signal from "did the output channel eventually produce a value" — a stalled goroutine produces neither an error nor a result, so nothing downstream ever times out on its own.

## Actionable Techniques

- Add a `sync/atomic` row to `go-concurrency-patterns`' sync Primitives table (lines 93–104) — the primitive is already used correctly downstream in `go-chaos-test`'s `faultyPublisher` (`atomic.Bool`, line 80) but is never named as an available tool in the skill that owns this exact topic. State its narrow job precisely, in the book's terms: lock-free counters/flags on a single word, cheaper than `Mutex` when the guarded state is that small — e.g., a consumer-lag gauge or an in-flight-request counter, not a substitute for `Mutex` on anything larger than one field.
- Add a **Deadlock, Livelock, and Starvation** subsection to `go-concurrency-patterns`, using the book's precise distinctions rather than folding them silently into "goroutine leak": name that the race detector (`go test -race`) proves absence of *data races*, not absence of deadlock/livelock; that Go's runtime deadlock detector only catches the *full-program* case (every goroutine blocked) and is silent on a partial deadlock or a livelock; and that both of the latter are found only by load/soak testing and goroutine-count/CPU-utilization observation (`go-performance-optimization`'s `runtime.ReadMemStats`/pprof goroutine profile already gives the mechanism — it's just not connected to this vocabulary today).
- Add one row each for **deadlock** and **livelock** to `go-chaos-test`'s "The Patterns to Validate" table (lines 96–106) — the existing seven rows (Circuit Breaker, Retry+Backoff, DLQ, Idempotent consumer, Graceful shutdown, Broker outage, Backpressure) are all *resilience-pattern* validations; none targets a *concurrency-correctness* failure mode. A concrete hypothesis-driven experiment already fits the file's own shape, e.g.: "if two workers acquire two shared locks in opposite order under contention, do we see a partial deadlock (goroutine count climbs, throughput to zero, process does not crash)?" — proving the worker pool's bounded-fan-out design (which never takes more than one lock at a time in every worked example read) doesn't regress.
- Add a short **Heartbeat** subsection to `go-concurrency-patterns` (or, more narrowly, to `go-event-consumer`'s consume loop) naming the pattern explicitly and distinguishing it from the metrics-level proxies the roster already has: consumer lag (`go-load-test`) and DLQ depth (`go-event-consumer`, line 165) both detect a *slow or failing* consumer, but neither detects a consumer goroutine that is alive, scheduled, and blocked indefinitely on an un-timeout-bounded call inside `handleRecord` — zero throughput looks identical to "no work available" until an operator notices lag is *also* zero and misreads that as healthy. A heartbeat channel checked by the supervising `errgroup` alongside the poll loop closes this specific blind spot.
- Cite **ad hoc confinement** by name where `go-service-layer`'s Parallel Orchestration example (lines 140–162) already practices it correctly: `assets` and `gaps` are two goroutine-private destination variables, each written by exactly one `errgroup` goroutine, joined by `g.Wait()` — this is confinement, not channel-based synchronization, and the existing inline comment ("no shared mutable state, no race") states the effect without the book's term for the cause. A one-clause addition — "(ad hoc confinement: each goroutine owns its own variable — no channel or mutex required)" — sharpens the citation without changing the code.
- Sharpen `go-concurrency-patterns`' "Prefer sharing by communicating... but a Mutex around a small in-memory map is simpler and faster" line (line 103) with the book's more precise two-question heuristic: *are you transferring ownership of data, or coordinating independent pieces of logic?* → channel. *Are you guarding a struct's own internal state, in a small critical section?* → `Mutex`/`RWMutex`. The skill's guidance is already directionally correct and non-dogmatic (matching the book's own stance exactly) — this is a vocabulary upgrade, not a correction.

5. **Deadlock/livelock experiments → two new rows in `go-chaos-test`'s existing table.** The file's hypothesis-driven-experiment shape already fits; no new test-strategy skill needed.

The lower-level channel-combinator patterns (`or-channel`, `or-done-channel`, `tee-channel`, `bridge-channel`) and the full generator→stage pipeline vocabulary were considered and explicitly **not** proposed as additions: this repo's actual concurrent code (worker pools, fan-in, parallel query orchestration) is uniformly built on `errgroup.WithContext` + a single shared `context.Context`, which already gives one cancellation tree and one join point — precisely the coordination problem those four combinators solve for *raw*, uncoordinated channels in code that predates or avoids `errgroup`. Introducing them would add a second, lower-level vocabulary for a problem the skill's higher-level tool already solves more simply. This is the same "book teaches a more general/lower-level version of a problem this repo already solves at a higher level" shape the sibling `designing-backend-systems-go-campbell.md` research found for `database/sql`+`sqlx` versus `pgx` — a confirmed, deliberate non-adoption, not an oversight.

## Key Terminology

Checked against `skills/glossary-management/references/ubiquitous-language.md` first: that file's existing entries are DDD/architecture/testing/platform/security terms (Bounded Context, Domain Event, Event Store, Resource Revision/ETag, Event Storming, Continuous Testing, Pipeline of Pipelines, …); it contains **no Go-concurrency-specific vocabulary at all** today — not goroutine, channel, deadlock, or confinement. None of the terms below are proposed as glossary additions in this pass, consistent with the glossary's current scope (cross-cutting architecture/process terms, not language-runtime vocabulary); they're recorded here only so a future concurrency-specific skill edit doesn't have to re-derive definitions:

- **Confinement (Lexical / Ad Hoc)** — structuring code so a piece of data is only ever reachable by one goroutine, by scope (lexical) or by convention (ad hoc), eliminating the need for a channel or mutex. Already practiced (ad hoc) in `go-service-layer`'s errgroup fan-out; never named.
- **Pipeline Stage** — a function whose input and output channels carry the same type, so stages compose by chaining. Not currently a shape any worked example in the roster needs (see Candidate New Skills/Agents), but worth defining if a multi-stage transform pipeline is ever built.
- **Fan-Out / Fan-In** — already both implemented and effectively named in `go-concurrency-patterns` (the section header literally reads "Fan-Out / Fan-In," lines 139–163); confirmed correct usage, not a gap.
- **Or-Channel** — a channel that closes as soon as *any* one of several input done-channels closes, used to combine cancellation signals from unrelated sources. Not currently needed (see Applies To) — `errgroup.WithContext` already gives one shared cancellation signal for every case observed in this repo.
- **Heartbeat** — a periodic liveness pulse from a long-running goroutine, distinct from its result/error channel, used to detect a stalled-but-not-crashed goroutine. Real, narrow gap — see Actionable Techniques.
- **Deadlock (Partial vs. Full)** — full: every goroutine in the process blocked, caught by Go's runtime detector. Partial: some goroutines blocked, others still running — invisible to the runtime detector. Not currently named anywhere in the roster's Go skills.
- **Livelock** — goroutines actively running and yielding to each other with no net progress; invisible to both the race detector and the runtime deadlock detector; found only by behavioral/load testing. Not currently named anywhere in the roster's Go skills.
- **Starvation** — a goroutine perpetually denied the resource/lock it needs to proceed, despite being otherwise able to run. Not currently named anywhere in the roster's Go skills.

## Caveats

- **This is a high-yield book for its target skill, unlike the thin-yield result the sibling `designing-backend-systems-go-campbell.md` research found for its target.** `go-concurrency-patterns` is already a mature, correct, and well-organized skill — its goroutine-lifecycle rule, `errgroup`-first design, channel-discipline rules, and Leak Prevention Checklist are all sound and match the book's guidance closely wherever they overlap. The yield here is not "the skill is wrong" — every finding above is either a citation upgrade to already-correct code, or a narrow, additive vocabulary/table-row gap (`sync/atomic`, deadlock/livelock/starvation, heartbeat, confinement-by-name). No correctness defect, goroutine leak, or missing cancellation path was found in any of the eight worked examples read across the nine skill files.
- **The channel-vs-mutex framing is a confirmed non-gap, not a near-miss.** `go-concurrency-patterns` line 103 already states the book's own non-dogmatic position almost verbatim ("a Mutex around a small in-memory map is simpler and faster than a channel-guarded goroutine, so use judgement, not dogma") — a plugin that got this wrong would show up as either "channels for everything" dogma or unexplained ad hoc mutex use; neither appears anywhere in the nine files read.
- **The low-level channel-combinator patterns (`or-channel`, `or-done-channel`, `tee-channel`, `bridge-channel`) are a deliberate non-adoption, not an oversight** — see the reasoning in Candidate New Skills/Agents. Flagging their absence as a "gap" would be citing the book's *general* toolkit against a codebase that already solved the same coordination problem one layer up, with `errgroup` + `context.Context`. This mirrors the `pgx`-vs-`database/sql` finding in the sibling Campbell research: a deliberate, justified departure from a book's more general default, not a defect to reconcile.
- **The heartbeat and deadlock/livelock/starvation findings are real but narrow-urgency, same calibration as the sibling research's CORS/timeout findings.** No product requirement in `sdlc-context.json` currently names an incident or a specific stuck-consumer/lock-contention scenario this would have caught; these are additions worth making because the vocabulary and detection heuristics are cheap, correct, and currently entirely absent — not because a gap was observed causing harm today.
- **Two sibling research files in this cluster (`the-go-programming-language-donovan-kernighan.md`, `100-go-mistakes-harsanyi.md`) did not exist at the time this file was written** — checked directly (`ls` on the directory) immediately before writing; no cross-references were forced. A future pass may find this file's confinement or `sync/atomic` findings echoed or sharpened by either book, since both cover Go's concurrency primitives from an adjacent angle (language-reference and mistake-catalogue respectively).
