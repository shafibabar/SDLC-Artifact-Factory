# Just Enough Software Architecture: A Risk-Driven Approach
**Authors:** George Fairbanks
**Domain:** Software Architecture

## Core Concepts

- **The central thesis: scale architectural investment to actual risk, not to habit or ceremony.** Fairbanks' title is the argument — most guidance in the field pushes toward either exhaustive upfront design (Big Design Up Front, BDUF) or reflexive "just start coding" hacking, and both are wrong as universal defaults. The book's discipline is a *decision*, made per architectural element or per choice, about how much deliberate design effort it warrants — not a fixed process applied uniformly to everything a project touches. This is a direct, sharper cousin of this repo's own **Budget and Frugality** principle (`CLAUDE.md`: "Prefer simpler solutions over sophisticated ones when outcomes are equivalent") — Fairbanks gives the missing mechanism for *when* outcomes are equivalent enough that the simpler, cheaper path is the right engineering call rather than corner-cutting.
- **Hacking is a legitimate strategy, not a failure mode — when the risk is low.** Fairbanks explicitly rehabilitates "hacking" (writing code without upfront design, observing what happens, adjusting) as a rational engineering choice for decisions that are cheap to reverse and cheap to get wrong. The failure mode isn't hacking itself; it's hacking on a decision that turns out to be expensive to unwind. Symmetrically, the failure mode on the other end is investing heavy modeling and design effort on a decision nobody will ever revisit and that costs little to change — over-engineering is as much a risk-management failure as under-engineering.
- **"Architecturally significant" is the actual criterion for where design effort belongs — defined by cost of change and breadth of dependency, not by subject matter.** An element or decision earns architectural attention when (a) it would be expensive to change once other work depends on it, or (b) many other decisions depend on it, so getting it wrong propagates broadly. Fairbanks' well-known **Architecture Bullseye** diagram makes this a picture: concentric rings with the highest-priority-for-design-effort elements at the center (broadly depended-upon, expensive to change, poorly understood, or risk-bearing) and progressively lower-priority elements toward the rim, where "just write it and see" is the correct, deliberate choice. The bullseye is a triage tool, not a completeness checklist — its point is to justify spending *less* effort on the outer rings just as much as spending more on the center.
- **The Risk-Driven Model (RDM): identify risks, weigh their cost and uncertainty, and let that weighing determine investment.** The book's concrete technique for populating the bullseye is explicit risk assessment: for a candidate decision, ask what could go wrong, how expensive it would be if it did, and how much is genuinely unknown or contested about the right answer. High cost-if-wrong combined with high uncertainty justifies deliberate design work (models, prototypes, documented decisions); low cost or low uncertainty does not. Fairbanks draws this directly from Barry Boehm's spiral model, an explicit intellectual ancestor — risk-driven iteration as a project-management idea, narrowed here specifically to the question of *architectural* design effort.
- **Engineering models exist to answer a specific question — not to describe the whole system.** Fairbanks reframes architecture models (diagrams, prose descriptions, formal notations) by analogy to other engineering disciplines: a bridge engineer's stress model exists to answer "will this beam hold this load," not to document the bridge exhaustively. A software architecture model earns its cost only if it lets someone answer a question they actually need answered — about a risk, a trade-off, or a decision under contention. A model built because "architecture models are what architects produce" without a driving question is waste, however polished it looks. This is the same discipline this repo already applies structurally (C4's leveled diagrams scoped by audience — see `system-context-diagram`'s Level/Audience table) but Fairbanks makes the *why* explicit: audience-scoping is really risk/question-scoping wearing an audience label.
- **Architecturally evident coding style.** Fairbanks argues code itself should make the architecture visible — module names, package structure, and interfaces should mirror the architectural elements and their relationships directly, rather than requiring a separate document to translate between "what the diagram says" and "what the code actually does." Where code and diagram diverge, one of them is lying, and it is usually the diagram (documentation rots; code runs). The practical implication: architecture documentation is a supplement to legible code structure, not a replacement for it — and an architect who never writes code loses the ability to judge whether the code is actually evident.
- **Architecture descriptions are for an audience with real questions — not exhaustive documentation for its own sake.** Fairbanks explicitly engages with the "views" tradition — Kruchten's 4+1 view model and, most directly, Clements et al.'s *Documenting Software Architecture: Views and Beyond* (module views, component-and-connector views, allocation views) — and argues the same risk-driven discipline applies to documentation itself: produce the views a specific stakeholder needs to answer a specific question, not the complete inventory of every view kind a methodology enumerates. A view nobody will read to make a decision is the documentation equivalent of hacking-when-you-should-have-designed, inverted: designing-when-you-should-have-hacked. This is the same conclusion `documenting-software-architectures-clements.md`'s own Core Concepts reach independently ("View selection is stakeholder-driven, not exhaustive") — the two books converge on identical guidance from different starting points: Fairbanks arrives at it via general risk-cost reasoning applied to documentation as one more design artifact, Clements et al. arrive at it as the view-selection discipline internal to their own method. Neither is derivative of the other; see the direct comparison in Caveats below.
- **Architects must keep coding to keep their risk judgment calibrated.** Similar in spirit to (but reasoned differently from) Richards & Ford's "T-shaped architect" — Fairbanks' version is narrower: an architect who has stopped writing code loses the felt sense of which decisions are actually expensive to change, and starts either over-modeling trivial things or under-modeling genuinely risky ones. The discipline of hands-on coding is instrumental to risk judgment, not a general-purpose virtue.
- **Architecture is still "the decisions that are expensive to change" — Fairbanks does not redefine architecture, he redefines the *process* for producing it.** He is consistent with the field's standard definition (shared with Richards & Ford, Bass/Clements/Kazman) that architecture = the structural decisions and constraints hardest to walk back later. His distinctive contribution is entirely about *how much deliberate process* should surround identifying and making those decisions, scaled to the specific risk each one carries — not a competing definition of what counts as architectural.

## Actionable Techniques

- Before committing design effort to any decision, run it through a two-question filter: (1) how expensive would it be to change this later, and (2) how many other decisions or components depend on it. Only decisions scoring high on both warrant an ADR, a model, or deliberate up-front design — everything else is a legitimate candidate for "write the code and see."
- Use the bullseye as a literal triage pass over a Container or Component Diagram's elements: for each service, integration point, or boundary, place it in a ring (center = architecturally significant, rim = hack it) before deciding how much design documentation or review it gets. Elements placed at the rim should get *no* ADR by default — writing one anyway is over-investment the book explicitly warns against.
- When building any architecture model or diagram, write down the specific question it exists to answer before drawing it. If no question can be named, the model is not earning its cost — skip it or replace it with a narrower, question-scoped artifact.
- Audit generated code against its architecture diagrams periodically for "evidence drift" — package names, module boundaries, and dependency directions that no longer match what the diagram claims. Treat a diverging diagram as the artifact that's wrong until proven otherwise, not the code.
- For any documentation deliverable (not just diagrams), name the specific stakeholder and the specific decision they need to make before producing it — skip or cut view kinds nobody will use to decide anything, even if a methodology's checklist lists them as standard.
- When a decision's cost-of-being-wrong is low and its uncertainty is low, explicitly record "hacked, not designed" as a conscious choice (even informally) rather than silently skipping documentation — this keeps the risk-driven decision itself auditable, distinguishing deliberate low-investment from an oversight.

## Candidate New Skills/Agents

**No new skill or agent is proposed.** Every finding in this document sharpens an existing decision *gate* inside skills and an agent this repo already has (`adr-authoring`'s "When to Write an ADR" criteria, `enterprise-architect`'s Decision Process and ADR Triggers table, and the frugality principle in `CLAUDE.md`) rather than introducing new domain expertise needing its own owner. Risk-driven investment judgment belongs inside the same skill/agent that already makes the decision it gates — a separate `risk-driven-architecture-assessment` skill would create a second place to look before every ADR, which is the opposite of "just enough" process.

**Explicitly not proposed:**
- **A standalone `architecture-risk-assessment` or `bullseye-triage` skill.** The two-question filter (cost-of-change × breadth-of-dependency, weighed against uncertainty) is small enough to live as a short addition inside `adr-authoring`'s existing "When to Write an ADR" section and as an inserted step in `enterprise-architect`'s Decision Process — not a new skill with its own SKILL.md, Quality Criteria, and Anti-Patterns tables. Per `skill-authoring-standards`' progressive-disclosure discipline, a skill this narrow (one filter, no reference material, no scripts) is exactly the kind of content that belongs folded into a skill that already owns the decision it gates.
- **A "hacking log" or informal-decision-tracking artifact type.** Fairbanks' "hacked, not designed" recording (see Actionable Techniques above) is a lightweight discipline, not a new artifact class alongside ADRs and Principles — formalizing it as its own tracked artifact would itself be over-investment by the book's own standard, ironic for a technique whose entire point is knowing when *not* to formalize.

## Key Terminology

Worth considering for `skills/glossary-management/`'s Ubiquitous Language:

- **Architecturally Significant** — Fairbanks' term for a decision or element that warrants deliberate design investment: expensive to change later, or heavily depended upon by other decisions. This repo currently expresses the same idea only through `adr-authoring`'s softer "Non-obvious / Consequential / Contested / Cross-cutting" list — adopting the precise term would let future skills cite a single, named significance criterion instead of restating the symptom list each time.
- **Risk-Driven Model (RDM)** — the book's core technique: weighing cost-if-wrong against uncertainty to decide how much architectural design effort a decision deserves. Not currently named anywhere in this repo; the closest existing analog is the CLAUDE.md frugality principle, stated as a value rather than a decision procedure.
- **Architecture Bullseye** — the concentric-ring triage diagram placing high-significance elements at the center and low-significance ("hack it") elements at the rim. A memorable, citable shorthand for "not everything gets the same design effort," useful as a literal exercise the enterprise-architect could run over a Container Diagram's elements.
- **Architecturally Evident (Coding Style)** — code whose structure and naming directly mirror the architecture, so the diagram and the implementation cannot silently diverge without one of them being visibly wrong. Related to, but distinct from, Richards & Ford's fitness functions (an automated check that a characteristic holds) — evidence is about legibility and correspondence, not automated verification.
- **Hacking (as a deliberate strategy)** — writing code without upfront design because the decision is cheap to reverse and cheap to get wrong, chosen consciously rather than defaulted into by neglect. Worth distinguishing explicitly from "skipping the ADR because no one got around to it," which is not the same act even though it looks identical from the outside.

## Caveats

- **`research/software-architecture/documenting-software-architectures-clements.md` did not exist in this directory when work on this file began, but was added to the directory (by a concurrent research effort) before this file was finished — confirmed present and read in full before finalizing this document.** The two books are complementary, not overlapping, exactly as anticipated: Clements et al. supply the taxonomy (module / component-and-connector / allocation views, viewpoints, documentation packages, element catalogs) and apply it to sharpen this repo's three C4 diagram skills directly — most consequentially, flagging that `container-diagram` conflates a component-and-connector view with an allocation view without naming the combination as deliberate (see that file's Applies To table). Fairbanks supplies the orthogonal question of *how much* documentation effort any of those views deserves in the first place, and *when a decision deserves an ADR at all* — a gate that sits upstream of Clements et al.'s view-selection discipline. A reader applying both: Fairbanks' risk filter decides whether a view or a decision record gets made at all; Clements et al.'s viewpoint vocabulary decides what shape it takes once that filter says yes. Neither book's findings should be merged into one artifact — `adr-authoring`'s ADR Rationale (a cross-cutting decision's justification) and a view's own Rationale (per Clements et al., why *this diagram* looks the way it does) remain intentionally distinct, per that file's own closing caveat.
- **This book is not a style catalog and should not be read as competing with `fundamentals-of-software-architecture-richards-ford.md`.** Richards & Ford catalog architecture *styles* (layered, event-driven, microservices, etc.) and characteristics trade-offs between them. Fairbanks is nearly silent on style selection by comparison — his subject is *process discipline* (how much design effort, for which decisions, decided how) that applies regardless of which style a team has already chosen. The two books answer different questions and this repo should draw on both rather than treating Fairbanks as a redundant or competing source.
- **Fairbanks predates this repo's DDD/Bounded-Context vocabulary and does not use it.** The book's running examples and terminology are generic object-oriented/UML-flavored (circa 2010) and do not map decisions onto Bounded Contexts, Aggregates, or Domain Events. The connection to this repo's `adr-authoring` and `enterprise-architect` content in the Applies To table above is this document's own extrapolation of Fairbanks' risk criterion onto this repo's DDD-flavored decision points, not literal book content.
- **The book is light on multi-tenant, cloud-native, and distributed-systems-specific risk examples.** Its risk-driven reasoning is domain-general; it does not address data residency, physical tenant isolation, or event-broker topology risk the way this repo's own NFR and integration-design content does. Treat Fairbanks as the source for the *decision procedure* (when to invest architectural effort) rather than for *which* risks this repo's specific product context should weigh — that judgment still belongs to the enterprise-architect applying this repo's own NFR and multi-tenancy content.
- **No named case study is asserted here with specificity.** The book does walk through worked examples using object-oriented design and UML notation, but this document deliberately avoids naming or describing a specific fictitious system from the book beyond what is confidently recalled, to avoid misattributing invented detail to Fairbanks' actual text. A reader wanting the worked examples in full should consult the book directly rather than this summary.
