# Alice and Bob Learn Application Security
**Authors:** Tanya Janca
**Domain:** Security — Secure coding & the secure SDLC

> Source note: synthesis of the book's practitioner framework for secure development (input validation, output encoding, authN/authZ, the OWASP Top 10, secure-SDLC "push left"), reconstructed from the book's well-known structure and public standards it teaches — not a page-cited extract, and no invented quotes or statistics.

## Core Concepts

- **Push left / security as a development activity, not an audit (Part 1, "Security Fundamentals").** The book's framing argument: security defects are cheapest to fix the earliest they are caught, so the goal is to move controls *left* — into requirements, design, and the developer's own commit — rather than discovering them in a penetration test weeks after merge. Concretely this means every developer owns a checklist of security requirements a change must meet *before* it merges (validated input, encoded output, server-side authorization, no secrets in code, security events logged), and those requirements are as much a merge gate as passing tests. This is the secure-SDLC spine the whole book hangs technique off of, and it maps directly onto this repo's phase-gate + TDD-gate model — security requirements become part of what the Implement-phase gate checks, not a separate later phase.
- **Input validation: allowlist over denylist, at every trust boundary (Ch. "Input Validation & Sanitization").** The book is emphatic that denylists (blocking known-bad characters/patterns) always lose to an attacker who finds an encoding the denylist missed; the only durable posture is an allowlist that accepts exactly the known-good shape (type, length, range, format, set membership) and rejects everything else. Crucially, validation happens at *every* trust boundary a value crosses — the HTTP handler is the first boundary, but a value arriving from a queue (Redpanda), from an ingested Google Drive/S3 file's metadata, or from another service is equally untrusted and re-validated on entry. This is the "parse, don't validate" discipline: turn an untrusted `string` into a validated typed value once, at the edge, so downstream code receives only well-formed data.
- **Output encoding / contextual escaping is a separate control from input validation (Ch. "Output Encoding").** The book's sharpest correction to a common developer mistake: input validation and output encoding are *not* interchangeable, and neither substitutes for the other. Injection (SQL, XSS, log injection, header injection) is fundamentally an *output* problem — a value that was perfectly valid as input becomes dangerous when it is interpolated into a different interpreter's syntax (HTML, JS, SQL, a shell, a log line, an HTTP header). The fix is to encode/escape *at the point of output, contextually* — HTML-entity-encode for HTML body, JS-string-encode for a `<script>` context, URL-encode for a query parameter, parameterize for SQL — because the correct encoding depends entirely on where the value lands. A single value ingested from an untrusted document can need three different encodings on three different sinks.
- **The OWASP Top 10 as a control map, not a vulnerability list (recurring spine).** The book walks the OWASP Top 10 and — this is its value for a developer — maps each category to the concrete code-level control that neutralizes it: A01 Broken Access Control → deny-by-default, server-side authorization on every request, IDOR prevention; A02 Cryptographic Failures → TLS in transit, proper at-rest encryption, no home-grown crypto; A03 Injection → parameterized queries + contextual output encoding; A05 Security Misconfiguration → secure defaults and hardening; A07 Identification & Authentication Failures → MFA, correct session lifecycle, secure password storage; A09 Security Logging & Monitoring Failures → log security events, alert on them, never log secrets. The framing turns an abstract risk taxonomy into a per-category "here is the line of code."
- **Authentication and session management done correctly (Ch. "Authentication" / "Session Management").** The book's concrete rules: store passwords only as salted adaptive hashes (bcrypt/argon2/scrypt — never fast hashes, never encryption, never plaintext); offer MFA and treat it as the highest-leverage single control against credential stuffing; give sessions an explicit lifecycle — generate a fresh, high-entropy session identifier *on* authentication (prevent fixation), enforce idle and absolute timeouts, and invalidate server-side on logout; and set session cookies with `HttpOnly`, `Secure`, and `SameSite` flags so client script cannot read them and they never traverse plaintext. Even in a JWT/JWKS architecture the session-lifecycle reasoning still applies to refresh tokens and any browser-held cookie.
- **Authorization: enforce server-side, deny by default, prevent IDOR (Ch. "Authorization").** Authorization decisions belong on the server, re-checked on *every* request, and default to *deny* — the absence of an explicit grant is a denial, never a fallthrough allow. The book gives IDOR (Insecure Direct Object Reference — reading or mutating object `id=124` because you can guess it) special attention: every request that names a resource by ID must verify the caller is entitled to *that specific object*, not merely authenticated. UI-level hiding of a button is never an authorization control.
- **Secure secrets handling and security logging (Ch. "Secrets" / "Logging & Monitoring").** Two disciplines the book pairs: secrets (DB passwords, API keys, signing keys) never live in source, in config committed to the repo, or in logs — they come from a secrets manager or injected environment and are rotated. Logging is its dual: *do* log security-relevant events (authentication success/failure, authorization denials, input-validation rejections, privilege changes) with enough context to investigate, but *never* log secrets, session tokens, or PII, and never let user-controlled input reach a log unescaped (log injection / forged log lines). A log is both a detection tool and, if mishandled, a fresh disclosure sink.
- **Secure defaults and hardening (Ch. "Secure Configuration").** Systems must ship *secure by default* — the out-of-the-box configuration is the safe one, and an operator opts *into* risk rather than opting out of exposure. Concretely: least functionality (disable unused features/endpoints/verbose errors), least privilege on every account and credential, no default/sample credentials, security response headers on, and error responses that never leak stack traces, versions, or internal structure to the client.

## Actionable Techniques

- **Allowlist validation as a typed boundary (Go).** For each inbound field, validate against an explicit allowlist and convert to a domain type in one step, at the handler and again at every non-HTTP entry point (Redpanda consumer, file-ingestion worker): `level := domain.SensitivityLevel(raw); if !level.IsValid() { reject }`. Validate type, length (min *and* max), range, format (compiled regex anchored `^...$`), and set membership. Never build the check as a denylist of bad characters.
- **Contextual output encoding at every sink.** Add an explicit output-encoding rule per sink: HTML/JS body rendered in the React frontend relies on React's default JSX escaping (and forbids `dangerouslySetInnerHTML` on any ingested value); values placed into HTTP response headers are stripped of CR/LF (header-injection); values written to logs are encoded so a newline in an ingested file name cannot forge a log line; SQL is *always* parameterized via pgx (`$N`), never `fmt.Sprintf`. Treat ingested document content, file names, and extracted-entity labels as untrusted at *every* one of these sinks.
- **OWASP-Top-10-to-control checklist as a merge gate.** Turn the Top 10 into a per-change checklist a reviewer (or a hook) can run: does this change validate all new inputs? encode all new outputs? enforce server-side authorization with a deny-by-default policy? avoid IDOR (object-level ownership check, not just authentication)? keep secrets out of code and logs? emit a security log event for the security-relevant actions it adds? A change that touches an endpoint and can't answer these is not merge-ready.
- **Session/cookie hardening for browser-held tokens.** Any cookie this platform sets (refresh token, CSRF token) gets `HttpOnly; Secure; SameSite=Strict|Lax`; session identifiers are regenerated on privilege change and authentication; refresh tokens have an absolute expiry and are revocable server-side; logout invalidates server-side state, not just the client cookie.
- **IDOR test as a standing security test.** For every endpoint that accepts a resource ID, add a test that authenticates as tenant/subject A and requests tenant/subject B's object ID, asserting `403`/`404` (indistinguishable) — this is the concrete regression guard for A01 and complements the repo's existing tenant-isolation SQL filter.
- **Security-event logging with a redaction discipline.** Emit structured security events (authN outcome, authZ denial, validation rejection, privilege change) into the audit path; route them through a redacting logger (the repo's `Secret` type pattern) so a token or PII value can never be serialized into a log even by mistake; alert on denial spikes (credential stuffing, enumeration).
- **Secure-defaults review for each new service.** Before a service ships: verbose errors off in production, no default credentials, unused endpoints removed, security response headers present, least-privilege DB role (the audit-log INSERT-only role is the model), and TLS/mTLS enforced (Linkerd handles transit — but the app still validates it is not the *only* layer).

## Key Terminology

- **Push left** — moving security controls earlier in the SDLC (into requirements/design/commit) where defects are cheapest to fix; the secure-SDLC posture, worth a glossary entry alongside `Test Pyramid` and the phase-gate vocabulary.
- **Output encoding / contextual escaping** — encoding a value at the point of output according to the interpreter it lands in (HTML, JS, SQL, URL, log, header); distinct from input validation and not substitutable for it. Candidate glossary term since the repo currently only has "parameterized query" for the SQL case.
- **Allowlist / denylist** — accept-known-good vs block-known-bad; the book's insistence on allowlist-first is worth a canonical one-line definition to standardize the terms across security skills (some prose still says whitelist/blacklist).
- **IDOR (Insecure Direct Object Reference)** — accessing an object by supplying its identifier without an object-level authorization check; the concrete face of Broken Access Control (A01). Worth glossarizing since the repo's ABAC discussion implies but never names it.
- **Deny by default** — authorization defaults to denial; access requires an explicit grant. Pairs with the existing `Principle of Least Privilege` glossary entry.

## Caveats

- **Confidence level, overall:** I am confident in the book's headline pedagogy and the public standards it teaches — push-left/secure-SDLC, allowlist validation, contextual output encoding, the OWASP Top 10 categories, session/cookie hardening, deny-by-default authorization, IDOR, and salted-adaptive-hash password storage are stable, widely-taught material and I have solid confidence in their substance. I am **less confident on exact chapter titles and their ordering** — the chapter labels above are approximate signposts to the book's structure, not verified against the physical text, and should not be cited as page references.
- **The book is an introductory, breadth-first practitioner primer, not a deep specialist text.** Its strength is a correct, complete mental model for a developer new to appsec; it does not go as deep on any single topic (e.g., cryptographic protocol design, advanced authorization models like ABAC) as this repo's existing skills already do in places. Read it as the connective *framework* (the OWASP map, the input-vs-output distinction, the push-left gate) that organizes the depth the other security-cluster skills already carry — not as a source of new depth on ABAC or crypto.
- **OWASP Top 10 versioning.** The book (2020) tracks the Top 10 of its era; the categories have since been re-grouped and re-numbered (e.g., the 2021 revision consolidated and renamed several). The *controls* the book maps to each category are stable and correct; the exact category numbers/names above should be treated as the concept, not a version-pinned citation — verify against the current OWASP Top 10 when writing the skill.
- **Stack mismatch — none of the examples are Go/React/pgx.** The book's code illustrations are language-generic (often C#/.NET-flavored in the author's other work); every Go+chi, pgx, React-JSX, and Redpanda-consumer application above is this document's extrapolation of the book's language-agnostic principles onto this repo's stack, not content literally present in the book.
- **Some controls are partly redundant with this repo's platform.** Transit encryption (A02) is largely handled by Linkerd's automatic mTLS, and physical per-tenant isolation backstops some access-control failures — so the book's transit-crypto and single-layer-isolation emphasis should be read as *defense-in-depth reinforcement* of layers this repo already has, not as gaps to fill from scratch. The genuinely new material for this repo is output encoding, the OWASP control map, IDOR testing, and session/cookie hardening.
