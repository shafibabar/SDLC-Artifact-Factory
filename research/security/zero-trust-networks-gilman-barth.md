# Zero Trust Networks
**Authors:** Evan Gilman, Doug Barth
**Domain:** Security — Network Architecture & Workload Identity

> Source note: synthesis of the book's zero-trust model and its control-plane/data-plane framework from my knowledge of the O'Reilly 2017 text, not a page-cited extract. Chapter signposts are approximate. The zero-trust model itself is a stable, widely-taught public architecture (later formalized in NIST SP 800-207); this file attributes the framing to Gilman & Barth, who wrote the first book-length treatment.

## Core Concepts

- **The network is always assumed hostile (Ch. 1–2).** The book's founding axiom: trust must never be derived from network location. There is no "internal" network that is safe by virtue of being behind a firewall — a packet arriving from `10.0.0.0/8` is exactly as untrusted as one from the public internet. This inverts the perimeter model, where a host's IP or VLAN membership implicitly granted it standing. For this repo, this is the argument against ever treating "inside the Kubernetes cluster" or "inside the Linkerd mesh" as a trust signal: a compromised pod on the same namespace is a hostile network participant, and authorization must not soften because the caller is `ClusterIP`-local. Every request is authenticated and authorized on its own merits, every time.

- **Control plane vs. data plane (Ch. 2–3).** The book's central architectural split. The **data plane** is where application traffic actually flows (the request from service A to service B); the **control plane** is the separate, higher-trust system that decides whether that flow is permitted and configures the enforcement points to allow it. Enforcement happens in the data plane, but the *decision* is made in the control plane and pushed down. The book is emphatic that these must be separated: the thing carrying traffic must never also be the sole authority on whether that traffic is legitimate. Mapping to this repo: Linkerd's data plane (the sidecar proxies doing mTLS) is transport enforcement; the control plane is where policy is decided — and in this repo the *authorization* control plane is the application's ABAC engine, not the mesh.

- **The trust engine and the policy engine (Ch. 3, 7).** The book decomposes the control plane into a **policy engine** (evaluates a request against declared policy — "is subject X allowed action Y on resource Z under conditions C?") and a **trust engine** (scores the risk/trustworthiness of the actors involved — this device, this user, this workload — often dynamically, from signals like device posture, historical behavior, and freshness of authentication). Policy is the rule; trust is the continuously-updated confidence that the actors are who they claim and are behaving acceptably. A modern authorization decision combines both: a valid credential (policy) from a device with a degraded trust score (trust engine) may still be denied. This repo's ABAC `Environment` attributes (time, IP, device posture) are exactly the trust-engine signals the book describes feeding into a policy decision.

- **Establishing trust independently in devices, users, and workloads (Ch. 5–6).** Zero trust refuses to conflate the three actors in any request. A **device** proves itself (hardware-backed identity, an enrolled certificate, attested posture); a **user** proves itself (strong IdP-issued identity, MFA); and an **application/workload** proves itself (a cryptographic workload identity, not a shared secret or a source IP). Each is authenticated on its own axis, and a request is only as trustworthy as its weakest axis. For this repo's server-to-server calls (data-classification service calling PII-extraction service) the relevant axis is *workload identity* — each service has its own cryptographic identity, independent of the human user whose request triggered the chain.

- **Dynamic, context-aware policy vs. static firewall rules (Ch. 7).** The book contrasts zero-trust policy with the traditional 5-tuple firewall rule (`allow src X dst Y port Z`). Static rules encode *network topology*, which is brittle, coarse, and blind to who is actually acting. Zero-trust policy is expressed against *logical identities and attributes* — "the `pii-extraction` workload, acting for a `Restricted`-clearance subject, may call `data-assets:read`" — and is evaluated fresh per request against current context, not baked into a firewall config that drifts. Policy should be stored as versioned, reviewable code (the book advocates treating policy like source), which maps directly to this repo's GitOps + Infrastructure-as-Code posture.

- **Mutual TLS and workload identity as the enforcement substrate (Ch. 5, 8).** The book identifies mTLS as the practical mechanism that makes zero trust real on the wire: every connection is mutually authenticated with certificates, giving both ends a verified cryptographic identity and encrypting the transport. Crucially, the certificate *is* the workload's identity — trust is bound to a short-lived, rotatable credential, not to an IP or DNS name that can be spoofed. This is precisely what Linkerd automates in this repo (automatic mTLS between meshed pods). But the book is careful — and this is the sharpest point for this repo — that mTLS answers *"who is this?"* at the transport layer; it does **not** answer *"is this actor allowed to do this?"*. That authorization question lives above the transport, in the policy engine.

- **A strong identity provider is the linchpin (Ch. 6).** Everything in zero trust bottoms out in identity, so the IdP that issues and vouches for identities is the highest-value component in the system. The book stresses centralizing identity issuance, short credential lifetimes, and continuous re-validation over long-lived static credentials. Weak or fragmented identity undermines every downstream policy decision. For this repo, this frames the JWT-issuing IdP (carrying `sub`, `tenant_id`, `roles`, `permissions`) and Linkerd's certificate authority as two identity planes — user identity and workload identity — that must both be strong and both be independently validated.

- **Zero trust degrades the value of a perimeter breach (Ch. 1, 9).** The model's payoff: because no lateral position confers trust, an attacker who breaches one host or one network segment gains almost nothing beyond that single compromised identity's own least-privilege grants. There is no "soft chewy center" to pivot through. Combined with micro-segmentation, a breach is contained to the blast radius of one workload identity rather than the whole flat internal network. This is the security case for per-tenant physical isolation *and* per-workload identity together: two independent containment layers, neither trusting the other.

## Actionable Techniques

- **Never let the service mesh be the authorization decision.** Wire Linkerd for automatic mTLS (transport-layer identity + encryption), but keep every `allow/deny` authorization call in the application's ABAC engine. Codify this as an explicit rule: a meshed connection succeeding proves *who* connected, never *what they may do*. A pod being inside the mesh is an identity fact, not a permission grant.

- **Feed trust-engine signals into ABAC as `Environment` attributes.** Extend the policy evaluation to consume dynamic trust signals — authentication freshness (token age), device posture, source-IP reputation, anomaly flags — as first-class inputs alongside `Subject`/`Resource`/`Action`, so a structurally-valid request from a low-trust context can still be denied. Don't treat authentication as a one-time binary gate.

- **Separate the two identity planes and validate both.** For any server-to-server call, require *both* a verified workload identity (Linkerd cert — "which service is calling") *and* a propagated user/subject identity (validated JWT — "on whose behalf"). Never let a trusted workload identity launder an unvalidated or over-broad user claim; re-derive the `Subject` from the token at the receiving service, don't trust an upstream service's assertion of it.

- **Express policy against logical identity, not network topology.** Write authorization policy in terms of workload identities, subject attributes, and resource sensitivity — never source IP, namespace, or port. Store it as versioned code reviewed like any other source (GitOps), so policy is auditable and diffable rather than living in mutable firewall/NetworkPolicy state that drifts.

- **Micro-segment to least privilege at the workload edge.** Default-deny all service-to-service traffic and open only the specific identity-to-identity paths a service actually needs (e.g., `pii-extraction` may receive from `data-classification` and nothing else). Use this to bound the blast radius so a single compromised workload identity cannot reach the whole estate.

- **Keep credentials short-lived and continuously re-validated.** Prefer short certificate/token lifetimes with automatic rotation (Linkerd already rotates its certs) over long-lived static secrets; treat a long-lived shared secret between services as a zero-trust anti-pattern. Re-authenticate and re-authorize per request rather than establishing a trusted session and coasting on it.

- **Audit every allow *and* deny with the deciding attributes.** Emit an OpenTelemetry span/log for each authorization decision recording the subject, workload identity, resource, action, and the trust signals that drove the outcome — so the control-plane decision is observable in Tempo/Grafana, not a silent gate. This makes "why was this allowed?" answerable after the fact, which perimeter firewalls never could.

## Key Terminology

- **Zero Trust** — a security model in which trust is never derived from network location; every request is authenticated and authorized on its own merits regardless of origin. Worth adding to `glossary-management`; complements the existing `Zero Trust Architecture` platform term with the book's canonical definition.
- **Control Plane / Data Plane (security sense)** — the separation between the system that *decides* whether traffic is permitted (control plane: policy + trust engines) and the system that *carries and enforces* it (data plane: the proxies/mTLS). Distinct from the routing sense of the same words; worth a glossary note to disambiguate.
- **Policy Engine** — the control-plane component that evaluates a request against declared authorization policy (subject/resource/action/conditions). Maps to this repo's ABAC evaluator.
- **Trust Engine** — the control-plane component that continuously scores actor trustworthiness from dynamic signals (device posture, auth freshness, behavior), feeding the policy decision. Maps to ABAC `Environment` attributes.
- **Workload Identity** — a cryptographic identity bound to a service/workload (e.g., a Linkerd-issued cert), independent of source IP, DNS name, or the human user on whose behalf it acts.
- **Micro-segmentation** — least-privilege network partitioning expressed against logical identities, default-deny, so a compromised workload's reach is bounded.

## Caveats

- **Confidence level:** I am confident in the book's headline model (network-always-hostile, control/data-plane split, policy engine + trust engine, independent device/user/workload trust, mTLS-as-substrate, degrading a perimeter breach). These are the book's well-known contributions and were later echoed in NIST SP 800-207. I am **less confident on exact chapter numbers and topic ordering** — the chapter signposts above are approximate, not verified against the physical text.
- **The book predates the mature service-mesh era it anticipates.** Written in 2017, *Zero Trust Networks* describes the *principles* (automatic mTLS, workload identity, dynamic policy) largely before Linkerd 2.x / Istio made them turnkey. The book's own examples lean on then-current tooling (e.g., host-based agents, PKI schemes) rather than a Kubernetes sidecar mesh. Everything mapped to Linkerd above is this document's extrapolation of the book's principles onto this repo's stack, not tooling literally named in the book.
- **The book is network/infrastructure-centric; this repo's hardest authorization problem is application-layer ABAC.** Gilman & Barth focus on getting *transport and connection* trust right; they say comparatively little about fine-grained, resource-level, per-tenant authorization (the `data-assets:read` on a `Restricted` asset problem). The book correctly insists authorization lives above transport, but the *content* of that application-layer policy is out of its scope — `access-control-model` and this repo's ABAC skills own that, and the book reinforces rather than replaces them.
- **Zero trust and this repo's physical multi-tenancy are complementary, not redundant.** Physical per-tenant isolation already contains cross-tenant blast radius at the deployment layer; the book's per-workload micro-segmentation contains blast radius *within* a tenant's deployment. Read the book's techniques as a second independent containment layer, not as compensating for an isolation gap this repo doesn't have.
- **"Never trust the network" can be over-applied into performance/complexity cost.** Re-authenticating and re-authorizing every request per hop, with dynamic trust scoring, adds latency and operational surface. The book advocates the posture; this repo should apply it proportionately — always for cross-service authorization decisions, but not as a mandate to, e.g., re-run full trust scoring on every intra-service function call.
