# Building Secure and Reliable Systems
**Authors:** Heather Adkins, Betsy Beyer, Paul Blankinship, Piotr Lewandowski, Ana Oprea, Adam Stubblefield (Google / O'Reilly, 2020)
**Domain:** Security — Security & Reliability by Design (system-level)

> Source note: synthesis of the book's four design principles and its reliability-security intersection argument as taught across its "Designing Systems" part (roughly Chs. 4–9), not a page-cited extract. The four principles and their sub-techniques are the book's stable, widely-cited framework; the Go/chi/pgx/Linkerd applications below are this document's extrapolation onto this repo's stack.

## Core Concepts

- **Security and reliability are the same discipline viewed under adversity (Chs. 1–2).** The book's founding argument — from a team that runs both Google SRE and Google security — is that reliability and security are both *emergent properties of a whole system*, not features bolted on, and both are fundamentally about what a system does under conditions its happy path never anticipated: reliability under random failure, security under an intelligent adversary who chooses the worst failure. The practical consequence for this repo is that the `security-architecture` and `nfr-*` skills should not treat availability and confidentiality as separate documents authored by separate concerns — the same failure-domain analysis feeds both. A design that fails open under load (reliability instinct) and a design that fails closed under attack (security instinct) are in direct tension, and the book insists that tension be resolved *explicitly per subsystem*, not left to whichever middleware happens to run last.
- **The four design principles (Chs. 4–8 framing).** The book organizes secure design around four principles that this repo's `security-architecture` skill currently only partially names: (1) **least privilege** — every component runs with the minimum authority to do its job, and that minimum is designed *in depth*, not just at the outer gate; (2) **understandability** — a system whose security you cannot reason about is not secure, because you cannot tell whether a change breaks an invariant; (3) **defense in depth** — distinct, independent failure domains so one breach does not cascade; (4) **recovery** — assume compromise will happen and design for detecting, containing, and reverting it. This repo's `security-architecture` already lives principle (3) well; it barely touches (1), (2), and (4) as *design-time* concerns rather than runtime controls.
- **Least privilege in depth: small functional APIs, breakglass, auditing, third-party trust (Ch. 5).** The book's least-privilege chapter is not "set RBAC roles narrowly" — it is a design discipline: expose *small functional APIs* (a service should offer `ClassifyDataAsset`, not a general `RunQuery`), so that the authority a caller can hold is bounded by the surface it can reach; provide **breakglass** mechanisms (explicit, heavily-audited, time-boxed emergency escalation) so that locking things down does not create an incentive to leave a permanent backdoor; make every privileged action **auditable** by construction; and treat **third-party and vendor trust** as an explicit privilege grant, not an ambient assumption. For this repo's data-estate platform ingesting from Google Drive and S3, "third-party trust" is load-bearing: an OAuth token for a customer's Drive is a standing privilege that must be scoped, time-boxed, and revocable.
- **Design for understandability: invariants, mental models, minimizing complexity (Ch. 6).** The book argues that a system's security rests on a small set of **invariants that must hold regardless of what an attacker does** — e.g., "a request is never processed under a tenant identity other than the one in its validated JWT," or "a secret value never leaves the process as plaintext." Security review is then the act of confirming each change preserves every invariant. Understandability is what makes that confirmation *possible*: minimize complexity, keep trusted computing bases small, prefer a design a reviewer can hold in their head. This is the concept most absent from this repo's security skills — they enumerate controls but never state the invariant each control exists to preserve, so a reviewer cannot tell whether removing a control breaks something.
- **Defense in depth = distinct failure domains and blast-radius control (Ch. 8).** The book sharpens "defense in depth" past the layered-controls cliché into **failure-domain** design: partition the system so that a compromise is *contained* to a domain, and the **blast radius** of any single failure (a leaked credential, a compromised pod, a poisoned dependency) is bounded and known in advance. This is precisely the framing this repo's physical per-tenant isolation embodies but never names — each tenant namespace *is* a failure domain, and the security architecture should state, per threat, "what is the blast radius if this control fails, and what independent domain contains it?" The book also formalizes **failing safe vs. failing secure**: a failure domain must have a defined, tested behavior under failure that does not default to granting access.
- **Design for recovery: rate-limiting, revocation, root-cause vs. rollback (Ch. 9).** The book's recovery chapter assumes compromise is inevitable and asks how fast and cleanly you can return to a known-good state. Its concrete levers: **rate-limiting** to slow an in-progress attack and buy detection time; **revocation** as a first-class, tested capability (can you actually invalidate a leaked token, key, or third-party grant *right now*, and how long does propagation take?); and the distinction between **rolling back** (returning to a prior state, which may reintroduce the vulnerability) and **root-causing** (understanding and fixing why the compromise was possible). For this repo, revocation is the sharp edge — the `secrets-management` and `zero-trust-design` skills describe issuing short-lived credentials but say little about the emergency-revocation path when a credential leaks before it expires.
- **Secure defaults and hardening as a design output, not a checklist (Ch. 6–7).** The book's "secure-by-default" argument is that the safe configuration must be the one you get by doing nothing — hardening should not depend on every operator remembering every flag. A framework, library, or service template should ship its most-restrictive posture on, with relaxation being the explicit, reviewed, logged exception. This repo's `security-implementation` skill has strong secure-default instincts already (deny-by-default ABAC, `Content-Security-Policy: default-src 'none'`, append-only audit role) but frames them as coding rules rather than as a *reusable secure-default posture* that new services inherit automatically.
- **Culture, review, and the security/reliability partnership (Chs. 19–21 framing).** The book closes on the organizational reality that secure-reliable systems come from *review practices and culture*, not just architecture: design reviews that explicitly hunt for invariant violations, blameless post-incident analysis shared between security and reliability, and making the secure path the path of least resistance for engineers. This is directly relevant to this repo's `methodology-review` and phase-gate hooks — the book supplies the *criteria* a security design review should apply (does each change preserve stated invariants? is the blast radius bounded and stated? is there a tested recovery path?).

## Actionable Techniques

- **State the invariants a design must preserve, then map controls to them.** For each Bounded Context, write the small set of security invariants that must hold regardless of attacker action (e.g., "no request is processed under a tenant other than its validated JWT's `tenant_id`"; "no secret value crosses the process boundary as plaintext"; "no audit entry is ever mutated or deleted"). Then annotate each control in the Security Control Matrix with *which invariant it preserves*. A control preserving no stated invariant is decoration; an invariant with no control is an unmet requirement.
- **Do a per-control blast-radius analysis.** For every control in the `security-architecture` matrix, record two things the current matrix omits: (a) *what is the blast radius if this control alone fails* (which data, which tenants, which services become reachable), and (b) *which independent failure domain contains that blast radius*. For this repo, the honest answer for cross-tenant leak is "physical namespace isolation contains it even if the ABAC check fails" — that is a failure-domain statement worth making explicit, not leaving implicit.
- **Design small functional APIs to bound authority.** When designing a service interface, prefer narrow, intent-named operations (`ClassifyDataAsset`, `ExtractEntities`) over general-purpose ones (`ExecuteQuery`, `RunJob`). The privilege a compromised caller can wield is bounded by the surface it can call. Audit each service's public API for any operation broad enough that holding it grants more authority than the caller's role needs.
- **Build breakglass as a designed, audited path — never an ambient backdoor.** For emergency access (a production incident needing elevated privilege), design an explicit breakglass mechanism: time-boxed, requiring a second party or recorded justification, emitting a high-priority audit event on use, auto-expiring. This turns "we left an admin credential around just in case" (the anti-pattern) into a reviewable, logged, revocable capability. Wire the breakglass audit event into the same non-repudiation hash chain the `security-implementation` skill already builds.
- **Make revocation a tested capability with a stated propagation time.** For every standing credential and third-party grant — JWTs, Linkerd certificates, Vault dynamic secrets, customer Google Drive/S3 OAuth tokens — document and *test* the emergency revocation path: how it is triggered, and the maximum time between "revoke" and the credential being universally rejected. Short-lived credentials bound the worst case; an actual revocation path shortens it further. Treat "we rely on the token expiring" as an incomplete answer.
- **Design failure-domain behavior explicitly: fail safe or fail secure, decided per subsystem.** For each subsystem, decide and document what it does when its security dependency is unavailable (e.g., the JWKS endpoint is unreachable, the ABAC policy store times out). The default must never be "allow." Where availability and confidentiality conflict — failing open keeps the service up but drops the check — that tension is resolved explicitly in the design, with the reasoning recorded, not left to whatever the code happens to do on error.
- **Ship secure-default service templates, not per-service hardening checklists.** Capture the hardened posture (deny-by-default NetworkPolicy, non-root SecurityContext, ABAC-on middleware order, security headers, append-only audit role) as a *default a new service inherits*, so a service is secure by omission and relaxation is the logged exception. This is the book's secure-by-default principle applied to this repo's `backend-service-scaffold` / template surface.
- **Prefer root-cause over rollback for security incidents.** When containing a compromise, distinguish reverting state (may reintroduce the vulnerability that allowed it) from fixing the cause. Rollback is a reliability reflex; for a security incident it can restore the exploitable condition. Record both the immediate containment and the root-cause fix as separate, tracked actions.

## Key Terminology

- **Failure domain** — a partition of a system designed so that a compromise or failure inside it is contained and does not cascade to other domains. In this repo, each physical tenant namespace is a failure domain. Worth adding to `glossary-management` as the precise name for a property this repo already has but never labels.
- **Blast radius** — the extent of what becomes reachable, corrupted, or exposed if a single control, credential, or component fails. A per-control blast-radius statement is the book's core defense-in-depth design artifact.
- **Breakglass** — a designed, audited, time-boxed emergency-access mechanism that grants elevated privilege through an explicit, logged, revocable path, so that tight least-privilege does not create an incentive for a permanent backdoor.
- **Security invariant** — a property that must hold regardless of any action an attacker takes (e.g., "no request is processed under a tenant other than its validated JWT's tenant"). Security review is confirmation that each change preserves every stated invariant.
- **Fail safe / fail secure** — a subsystem's defined, tested behavior when a security dependency is unavailable; the default must never be to grant access. Distinct from a reliability "fail open" instinct, and the two must be reconciled per subsystem.
- **Least privilege in depth** — least privilege designed at every layer (small functional APIs, scoped service accounts, scoped third-party grants), not only at the outer authentication gate.

## Caveats

- **Confidence level:** I am confident in the book's headline framework — the four design principles (least privilege, understandability, defense in depth, recovery), the security/reliability-as-emergent-properties thesis, failure domains and blast radius, breakglass, secure-by-default, and the recovery levers (rate-limiting, revocation, root-cause vs. rollback). These are the book's well-known, widely-cited contributions. I am **less confident on exact chapter numbers**; the chapter references above are approximate signposts to the book's "Designing Systems" part, not verified against the physical text, and should not be treated as page citations.
- **The book is Google-scale and Google-shaped.** Its examples assume planet-scale infrastructure, a mature security org, and Google-internal systems (BeyondCorp, Borg, internal certificate authorities). This repo is a single frugal data-estate platform on Kubernetes/Linkerd. The *principles* transfer cleanly; the *implementation scale* does not — breakglass here is a lightweight audited-escalation flow, not a global access-management system, and "failure domains" here are tenant namespaces, not datacenters.
- **It is a principles book, not a Go book.** No code is Go, chi, pgx, or Redpanda; every Go/stack-specific application above (breakglass into the non-repudiation hash chain, JWKS-unreachable fail-secure behavior, Drive/S3 OAuth revocation) is this document's extrapolation of the book's language-agnostic principles onto this repo's actual stack, not content literally in the text.
- **Reliability/security tension is stated, not always resolved.** The book is honest that failing safe (availability) and failing secure (confidentiality) genuinely conflict, and it gives a framework for deciding per subsystem rather than a universal answer. Applying it to this repo still requires a real per-subsystem decision — the book supplies the question, not a canned resolution.
- **Physical per-tenant isolation already gives this repo a failure-domain boundary the book's shared-tenancy examples must engineer from scratch.** Much of the book's defense-in-depth machinery exists to contain blast radius in a shared-deployment world; this repo's physical isolation provides a strong containment boundary by default. The book's value here is naming and reasoning about that boundary explicitly (and covering the domains isolation does *not* contain — third-party grants, secrets, the audit chain), not compensating for an isolation gap this repo does not have.
