## Core Concepts

- **Compound components share implicit state via Context to give a flexible, declarative composition API — `<Tabs><Tabs.List><Tabs.Trigger><Tabs.Panel>` is the book's canonical example**, and it is presented as the idiomatic answer to boolean-prop proliferation: rather than a single component accepting a combinatorial explosion of flags (`<Table compact bordered selectable withActions>`), a compound-component family exposes a small set of composable subcomponents that share state a parent-level Context provides and children consume without the caller wiring it explicitly. The book frames this as one of the highest-value composition patterns precisely because it scales to variation the boolean-prop approach cannot express cleanly.

- **The classic container/presentational split, and its modern replacement by custom hooks, are presented as the same underlying idea solved two different ways at two different eras.** The pre-hooks pattern (a "container" component owning data-fetching/state, rendering a "presentational" component via props) enforced a real and valuable separation — logic stays out of markup — but required an extra component layer purely to hold that logic. Custom hooks (`useX`) let a single component stay "presentational" in spirit (its JSX reads as pure UI) while delegating all non-trivial logic to a hook it calls, without the container wrapper. The book treats hooks as the more current mechanism for the *same* separation of concerns, not a different concern — the container/presentational vocabulary is retained for reading legacy code and for reasoning about the underlying principle, but new code reaches for a hook, not a wrapper component.

- **Controlled vs. uncontrolled components is a spectrum choice, not a binary rule, and the book's guidance is that complex forms benefit from a library that keeps inputs uncontrolled under the hood while presenting a controlled-feeling API** (React Hook Form is the standard modern answer to this in a 2nd-edition-era book) — because a fully controlled form re-renders the whole form tree on every keystroke unless carefully isolated, while a naively uncontrolled form loses the live-validation and dependent-field behavior most real forms need. The pattern is choosing the right default per field, not picking one mode for the whole form.

- **Code-splitting via `React.lazy` + `Suspense`, at the route boundary primarily and the component boundary secondarily, is presented as a standard, expected technique — not an advanced optimization reserved for large apps.** Route-based splitting is the default first cut (each page is naturally a chunk boundary a user doesn't need until they navigate there); component-level splitting is for anything heavy that isn't always visible even within a rendered page (a rich editor, a chart library, a modal's contents). The book's framing is that the fastest code is code never downloaded, and `lazy`/`Suspense` is the mechanism that makes "never downloaded until needed" the default posture rather than an afterthought.

- **HOCs and render props are covered as the prior generation's answer to cross-cutting logic reuse — legacy patterns worth recognizing when reading older code or a class-component integration point, but superseded by custom hooks for new code.** A HOC (`withAuth(Component)`) wraps a component to inject props, at the cost of wrapper hell (nested displayNames in DevTools, prop-name collisions between multiple HOCs) and an indirection that obscures where a prop actually came from. A render prop (`<DataFetcher render={(data) => <Table data={data} />} />`) avoids the naming collision but couples the caller to a specific children-as-function contract and nests visually. A custom hook solves the same reuse problem — extract `useAuth()`, `useDataFetcher()` — without wrapping, without an extra component in the tree, and without either downside. The book's stance (typical of any React book from the hooks era forward) is unambiguous: hooks are the default; HOCs and render props remain relevant only for the narrow cases hooks can't cleanly reach (some class-component-only integration surfaces, or a small number of library-authoring patterns) and for reading code written before hooks existed.

- **Accessibility is treated as a design constraint applied at authoring time, not a separate audit pass** — the book's ordering is semantic HTML first (native elements carry behavior, keyboard support, and AT semantics for free), ARIA only for the gap semantic HTML genuinely can't express (custom widgets: tabs, comboboxes, trees), and — specifically for the composition patterns this book is about — **focus management as a first-class part of any component that opens/closes a layer over the page** (modal, dialog, dropdown, popover): focus moves into the opened layer on open, is trapped within it while open, and is restored to the triggering element on close. This is presented as part of the *component's* contract, not a bolt-on the accessibility team adds later — a compound-component modal that doesn't manage focus is an incomplete implementation of the pattern, not a feature-complete component missing a nice-to-have.

- **Testing strategy follows the React Testing Library philosophy the book adopts wholesale: test the rendered output and the user-observable behavior, never the component's internal implementation.** Query by role and accessible name the way a screen reader or a human using the keyboard would find the element (`getByRole`, `getByLabelText`) rather than by internal state, instance methods, or CSS class/test-id as a first resort. The book explicitly names shallow rendering and implementation-detail assertions (checking `wrapper.state()`, snapshotting internal markup) as the anti-pattern this approach replaces — a test written this way survives a refactor that preserves behavior and fails a change that breaks it, which is the entire point of a regression test.

- **Performance patterns center on three tools used *after* profiling, not by default: `React.memo` for component-level memoization, `useMemo`/`useCallback` for value/reference stability, and windowing/virtualization for large lists.** The book's caveat on `React.memo` is specific and easy to miss: it does a shallow prop comparison, so a memoized component still re-renders every time if the parent passes a new object, array, or inline function literal as a prop each render — memoizing the child without also stabilizing what the parent hands it is a no-op that looks like it should work. The complementary, cheaper-than-any-memoization technique the book emphasizes is **pushing state down to the smallest component that actually needs it** — fewer components subscribed to a piece of state means fewer components in the re-render path in the first place, which is strictly cheaper than memoizing a large subtree that didn't need to be large.

## Actionable Techniques

- **Reach for a compound component when a parent needs to share state with an open-ended, caller-composed set of children** (tabs, an accordion, a stepper, a menu) — expose the subcomponents as properties on the parent (`Tabs.List`, `Tabs.Trigger`, `Tabs.Panel`) backed by a small Context provider the parent creates; this is the fix for boolean-prop proliferation, not a bigger union of `variant` strings.
- **Extract data-fetching/effect/derived-state logic into a `useX` hook before reaching for a container-component wrapper** — the hook is the modern realization of the container/presentational split; a component that both fetches data and renders markup directly is the anti-pattern the split exists to prevent, whichever mechanism (wrapper component or hook) does the extracting.
- **Default new forms to a form library that keeps fields uncontrolled internally** (React Hook Form is this repo's stated default) **and reserve fully controlled inputs for fields that genuinely need a live value read on every keystroke** (cross-field validation, a character counter, a dependent-field computation) — controlling every field "for consistency" pays a re-render cost the form doesn't need everywhere.
- **Put a `lazy()`/`Suspense` boundary at every route, and a second one around any in-page component that's heavy and not always visible** — the graph, a chart library, a rich editor, a modal's contents. Verify the win with a bundle visualizer, not by assumption: the boundary should show up as its own chunk that the initial bundle no longer contains.
- **When a Module Federation remote is already the code-split boundary, do not add a redundant `React.lazy()` wrapper around the whole remote import inside the exposing app** — the `exposes` entry is already an async chunk by construction (per this repo's own `typescript-and-tree-shaking.md`); the host's `lazy: async () => import("remote/App")` is the one legitimate lazy boundary at that seam. Reserve `React.lazy`/`Suspense` for splitting *within* a fragment (a heavy feature that fragment itself doesn't always render), not for re-wrapping the federation boundary a second time.
- **Write the failing focus-management test before the modal/dropdown/dialog component**: assert focus lands inside the layer on open, assert Tab/Shift-Tab stay trapped within it, assert Escape closes it, assert focus returns to the trigger element on close. A compound-component-style disclosure widget (`Menu`, `Modal`, `Combobox`) is not done until all four pass.
- **Query every component test by role and accessible name first; treat a `getByTestId` fallback as a signal to fix the component, not the test** — if an element can't be found by role/label, a screen reader can't find it either, so the fix belongs in the markup (add a label, use a semantic element, add an `aria-label`), not in the test's query strategy.
- **Before adding `React.memo` to a component, check what its parent passes it** — an inline object/array literal (`style={{...}}`, `data={rows.map(...)}`) or an inline arrow function defeats the shallow comparison every time. Stabilize the parent's props with `useMemo`/`useCallback` *first*, or `memo` on the child does nothing measurable; verify with the React DevTools Profiler's "why did this render" panel, not by inspection.
- **Virtualize any list that can realistically exceed roughly a few hundred rendered rows** — windowing keeps the mounted DOM node count constant regardless of data size; treat "it's fine, we tested with 20 rows" as an untested claim about production-scale data, not a pass.
- **When state is genuinely needed by more than one component, lift it only as far as their nearest common ancestor — never further "to be safe."** Every level a piece of state is hoisted past its actual consumers widens the set of components that re-render when it changes; this is cheaper to get right up front than to fix later with a `memo` retrofit.
- **Recognize a HOC or render prop in code review as a pattern to migrate to a hook when the surrounding code is touched anyway** — not a mandatory rewrite on sight, but a live signal that a `useX` extraction would remove a wrapper layer and a naming-collision risk with no behavior change.

## Key Terminology

Not proposed for `skills/glossary-management/references/ubiquitous-language.md` — checked directly against that file (no match found for any term below). This is a calibrated omission, not an oversight: the glossary's stated purpose is enterprise Ubiquitous Language — the vocabulary of bounded contexts, domain events, and the business/testing/platform/security domain this product is built in — not React implementation-pattern vocabulary. The terms below are already used correctly in the 13 skills' own prose (e.g., "compound components," "presentational/container") without being glossary entries, which is the right precedent to continue; adding them would mix implementation idiom into a glossary meant for domain and cross-cutting-concern terms.

- **Compound Component** — a component family (a parent plus named subcomponents, e.g. `Tabs`/`Tabs.List`/`Tabs.Panel`) that implicitly shares state via a private Context the parent provides, giving callers a declarative, composable API instead of a large flat prop surface.
- **Presentational / Container Split** — the separation of a component that renders UI from props/callbacks only (presentational) from the logic that sources and manages the data it's given (container); realized today primarily through custom hooks rather than a wrapper component.
- **Controlled Component** — a form input whose value is owned by React state and updated via `onChange`, giving the parent a live value on every change; contrasted with an **Uncontrolled Component**, whose value lives in the DOM and is read via a ref, trading live-value access for fewer re-renders.
- **Higher-Order Component (HOC)** — a function that takes a component and returns a new component with injected props/behavior (`withAuth(Component)`); a pre-hooks reuse mechanism, largely superseded by custom hooks for new code.
- **Render Prop** — a component that accepts a function as a prop (often as `children`) and calls it with data/state to let the caller control rendering; the other major pre-hooks reuse mechanism, also largely superseded by hooks except where the caller genuinely needs to control per-item rendering.
- **Windowing / Virtualization** — rendering only the list items currently within (and near) the viewport, so the mounted DOM node count stays constant regardless of total data size.
- **Shallow Comparison (in `React.memo`)** — the default prop-equality check `React.memo` performs (`Object.is` per prop, one level deep); a new object/array/function reference passed as a prop defeats it even when its contents are unchanged.
- **Focus Trap** — constraining Tab/Shift-Tab cycling to remain within an open overlay (modal, dialog, menu) so keyboard focus cannot silently escape to content behind it while the overlay is open.

## Caveats

- **This file's confidence is highest on the durable, well-corroborated content**: the compound-component pattern's Context-sharing mechanics, the container/presentational-to-hooks evolution, HOCs/render props as pre-hooks reuse mechanisms now superseded by hooks, `React.memo`'s shallow-comparison caveat, virtualization for large lists, and the React Testing Library behavior-first testing philosophy are all extremely well-established, book-independent React knowledge that a 2nd-edition (React 17/18-era) Packt title on this exact subject matter would unquestionably cover in this shape — these are not filler. It is less certain about this specific book's exact chapter ordering, page-level structure, or verbatim code listings, which is flagged here rather than asserted with false precision.
- **Every "Applies To" row in this file is a direct claim about what was read this session** (the 13 named `SKILL.md` files plus the four `references/*.md` files under `react-project-structure`, `react-routing`, and `react-state-management`) — no other skill file (`typescript-types`, `microfrontend-architecture`'s own reference file, the ux-architect's `ui-component-spec`) was opened during this pass, so any claim about those files' content is intentionally absent rather than inferred.
- **Several "Applies To" rows report alignment rather than a gap** — this is a deliberate departure from a gap-list format, because the honest finding for most of the six skills checked against this book's core content is that the pattern is already implemented correctly, not that it's missing. Reporting false gaps to make the file "actionable" would misrepresent the skill domain's actual, verified maturity.
- **The render-props finding is a precision gap, not a correctness gap** — `react-component-design`'s render-props bullet doesn't recommend anything wrong; it is simply less complete than its sibling patterns in the same section (no code example, no hooks-supersession note). This is worth a small refinement, not treated here as urgent.
- **This book's 2nd edition is Packt-published and React-hooks-era** (the compound-components-via-Context, hooks-over-HOCs, and RTL-testing content it's known for all postdate React 16.8) — a reader should not expect pre-hooks-era content (class-component lifecycle patterns as the primary teaching vehicle) to be this book's center of gravity, consistent with everything cross-checked against this repo's own (hooks-only, function-component-only) skill content finding no conflict.
