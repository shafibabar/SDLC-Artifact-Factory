# Learning React: Modern Patterns for Developing React Apps
**Authors:** Alex Banks and Eve Porcello
**Domain:** Frontend Engineering — React Component Model, Hooks, and Rendering Fundamentals (2nd edition, 2020, O'Reilly)

## Core Concepts

- **Function components plus Hooks are the whole paradigm — not a syntax variant of class components.** The book's central move (this is the 2nd edition, rewritten around Hooks after the 1st edition's class-heavy treatment) is that a function component is not "a class component with less boilerplate": state, lifecycle, and side effects all attach to the function's *call*, not to an instance. `useState` returns a state slot and its setter; `useEffect` replaces `componentDidMount`/`componentDidUpdate`/`componentWillUnmount` with a single unified "synchronize with an external system" primitive; `useContext` reads context without a `Consumer` render-prop wrapper. Every one of this repo's 13 React skills is written entirely in this idiom — no class components appear anywhere except the one place the book itself says a class is still mandatory (error boundaries; see below) — which is itself evidence the skill set correctly absorbed the book's central thesis rather than defaulting to older React idiom out of habit.
- **The Rules of Hooks exist because of *how* hooks are implemented, not as an arbitrary style guide.** React tracks each hook call by its **call order** within a single render — internally, each component instance holds an ordered list of hook "slots," and `useState`'s second call in a render must line up with the second call from the previous render for React to return the *same* state cell. Calling a hook inside an `if`, a loop, or after an early `return` changes how many hook calls happen on some renders and not others, desynchronizing the slot list — the failure mode isn't a lint nitpick, it's silently reading the wrong piece of state (or crashing outright when the count changes). The book states the rule as two hard constraints: (1) only call hooks at the top level of a function component or custom hook, never inside conditionals/loops/nested functions, and (2) only call hooks from React function components or from other hooks, never from a plain JS function. `skills/react-component-design/SKILL.md` states this rule twice — once in the body ("Rules for hooks: … follow the Rules of Hooks (top level, not in conditionals)") and once as a named Anti-Pattern ("**Conditional hooks** — calling a hook inside `if`/`map`/early-return breaks the Rules of Hooks. All hooks at top level, unconditionally; branch *after*.") — which is the correct treatment per this repo's own `CLAUDE.md` distinction between decision criteria (belongs in a skill) and reasoning (belongs in an agent): stating the rule as a hard constraint is knowledge, not a judgment call, so it belongs exactly where it lives.
- **`useEffect`'s dependency array is not an optimization knob — it is the correctness contract of the effect.** The book's treatment (echoed and later formalized by the React team as "exhaustive deps") is that the dependency array must list **every reactive value read inside the effect body** — every prop, state variable, or value derived from either. Omitting one doesn't make the effect run less; it makes the effect close over a **stale** value from the render that created it, silently using outdated data on every subsequent invocation until the omitted dependency's own change happens to also change something else in the array. This is presented in the book as the single most common real-world hooks bug, alongside its close sibling: **an effect that subscribes to something external (an event listener, an interval, a WebSocket, a manual DOM mutation) must return a cleanup function**, or every re-render (or every remount in React 18 Strict Mode, which double-invokes effects specifically to surface exactly this class of bug) adds one more listener/interval/subscription that is never released — a leak that compounds silently in a long-lived SPA.
- **Custom hooks are the book's answer to "how do I share stateful logic," explicitly superseding Higher-Order Components and render props for that purpose.** Pre-hooks React had two competing answers to reusing *stateful* logic across components — HOCs (`withData(Component)`) and render props (`<DataProvider>{data => ...}</DataProvider>`) — both of which wrap markup around the consuming component and can produce deep "wrapper hell" nesting that's hard to trace in DevTools. A custom hook (`function useX() { ...; return value; }`) extracts the same logic as a plain function call with no extra component in the tree, no prop name collisions, and no indirection — the book treats this as a strict improvement for *state and effect reuse* specifically. It does **not** claim render props are dead outright — a render prop / function-as-child still has a legitimate, distinct niche the book doesn't retire: caller-controlled *rendering* (a list virtualizer that knows how to measure rows but not what each row looks like), which is a rendering-composition problem, not a state-reuse problem. `skills/react-component-design/SKILL.md`'s own render-props note ("For reusable behaviour with caller-controlled rendering (a virtualiser, a data boundary)") lands exactly on this narrower, still-valid case — the skill doesn't misuse render props as a state-sharing tool, so there's no drift from the book's actual position here, just an implicit one worth naming explicitly if this skill is ever revised.
- **`useMemo` and `useCallback` are targeted performance escape hatches with their own cost — not a default habit.** The book is explicit that memoizing a cheap computation can be *slower* than just recomputing it: the memoization machinery (storing the previous dependency array, doing an equality check on every render, holding the cached value in memory) has a real cost, and for a computation cheaper than that bookkeeping, `useMemo` is pure overhead with zero benefit. The book's guidance is to reach for these two hooks only once profiling has shown a specific, real problem — an expensive computation re-running needlessly, or a referentially-unstable prop/callback breaking a `React.memo`'d child's bail-out — never as a reflexive wrap-everything habit. It also draws the sharper, more consequential distinction between the two: `useMemo` stabilizes a **value**'s reference (so a memoized object/array prop doesn't force a memoized child to re-render), `useCallback` stabilizes a **function**'s reference for the identical reason when the prop is a callback — they solve the same underlying problem (referential equality) for two different JS value kinds, not two unrelated tools.
- **Controlled vs. uncontrolled form inputs is a deliberate trade, not a stylistic choice.** A controlled input's value lives in React state (`value` + `onChange`) — the single source of truth is React, every keystroke round-trips through a re-render, and the value is always available for live validation, conditional fields, or a submit-time snapshot with zero extra work. An uncontrolled input lets the DOM hold its own value (`ref` + optional `defaultValue`) — React never re-renders on keystroke, which is cheaper for large or write-once forms, but the current value must be pulled out imperatively (via the ref) rather than being continuously available. The book frames this as the same trade-off HTML forms always had, made explicit and controllable in React rather than papered over; it doesn't declare one universally correct, and specifically flags that hybrid libraries (React Hook Form, which post-dates the book's 1st edition but the pattern is squarely in the book's own uncontrolled-for-performance logic) keep inputs uncontrolled internally while presenting a controlled-feeling API, precisely to avoid a re-render per keystroke on large forms.
- **The `key` prop is not a generic React attribute — it's the identity signal the reconciler uses to match elements across renders, and using array index breaks that signal the moment order can change.** React's diffing (reconciliation) compares a parent's new list of child elements against its previous list, sibling by sibling, and uses `key` to decide whether a given child element **is** the same logical thing as before (so its component instance, local state, and DOM node are preserved and merely updated) or is a genuinely new thing (so a fresh instance mounts and the old one unmounts). An array index is a stable identity *only* if the list never reorders, filters, or has items inserted/removed anywhere but the end — the moment it does, index-as-key causes React to match the wrong element to the wrong index position, which manifests as state (an open dropdown, a focused input, a checked checkbox) appearing to "jump" to the wrong row, or as unnecessary remounts destroying state that should have persisted. The book's rule is a stable, unique identifier drawn from the data itself (a database id, a UUID) — never the array index — for exactly this reason.
- **Context's cost is structural, not incidental: every consumer re-renders on any change to the value passed to its Provider, full stop, unless the value is split or memoized.** `useContext` doesn't support selecting a slice of the context value the way a store-with-selectors does — a component that reads `useContext(ThemeContext)` re-renders whenever *any* field the Provider passes changes, even fields that component never reads. The book frames Context correctly as a prop-drilling solution for low-frequency, broadly-read values (theme, locale, the current authenticated user) — not a general-purpose application state manager, and specifically warns that a Context value recreated as a fresh object literal on every Provider render (`<Ctx.Provider value={{a, b}}>`) defeats even React's own bail-out optimizations, since the object reference changes every time regardless of whether `a` or `b` actually did.
- **Error boundaries remain a class-component-only mechanism, even in a hooks-only codebase, because no hook equivalent exists.** `getDerivedStateFromError` and `componentDidCatch` are lifecycle methods with no Hook API translation — React has never shipped a `useErrorBoundary` hook, and the book (as of its 2020 edition, and this remains true through the book's currency) is explicit that catching a render error in a subtree requires exactly one class component, even inside an otherwise 100%-function-component application. This is presented as an accepted, permanent exception to "hooks replaced classes," not a temporary gap awaiting a future hook.
- **Reconciliation bails out of re-rendering a subtree when an element's type is unchanged and, for a memoized component, its props are referentially equal — this is the actual mechanism `React.memo`, `useMemo`, and `useCallback` all lean on.** The book explains React's diffing at the level relevant to app code: same element type at the same tree position → React reuses the underlying instance/DOM node and only updates changed attributes; different element type at that position → the old subtree unmounts and a new one mounts from scratch (all local state lost). A parent re-rendering does **not**, by itself, force a child to re-render forever — but a plain function component re-renders whenever its parent does, by default, regardless of whether its own props changed; `React.memo` is what makes a component skip that default re-render when its props compare referentially equal to the previous render, which is precisely why an unstabilized function or object prop (the exact case `useCallback`/`useMemo` fix) defeats it silently.

## Actionable Techniques

- **Enforce the Rules of Hooks and exhaustive-deps mechanically, not just in prose.** `eslint-plugin-react-hooks`'s two rules — `rules-of-hooks` (error: catches conditional/nested hook calls at lint time, before a bug ships) and `exhaustive-deps` (warn-or-error: flags a `useEffect`/`useMemo`/`useCallback` dependency array missing a value the body actually reads) — turn both of the book's two most load-bearing constraints from a convention documented in `react-component-design`'s prose into something CI actually verifies on every PR. Neither this ESLint plugin nor its two rules appear anywhere in `skills/react-project-structure/references/typescript-and-tree-shaking.md` (which does specify the full strict TypeScript family and the `any` lint ban in comparable detail) or in `agents/frontend-engineer.md`'s `npm run ci` gate description ("typecheck, lint incl. no-`any` + boundaries, a11y, unit/e2e, bundle budget, API-client freshness") — the lint-enforcement layer this skill domain already applies rigorously to types has no counterpart for hooks correctness.
- **Use `useRef`, not `useMemo`, for a value that must be created exactly once and persist for the component's full lifetime, especially a mutable object you intend to mutate imperatively.** `useMemo` is documented by React itself as a *performance hint*, not a lifetime guarantee — React is explicitly permitted to discard a memoized value and recompute it (e.g., under memory pressure, or with future offscreen-rendering behavior), which is safe for a pure derived value but wrong for a value that owns external, non-recreatable state (a `graphology` graph instance being mutated node-by-node, a `Worker`, a WebGL context). `useRef(() => new Graph())`-style lazy initialization is the correct tool because a ref's `.current` is genuinely guaranteed stable across the component's lifetime.
- **When an effect's cleanup function references something created outside that effect (a `Worker`, a socket, a timer id), that value must either be created by an effect with a matching cleanup, or be a `ref`/stable dependency the effect actually declares** — a cleanup referencing an out-of-scope variable that isn't part of the same effect's own lifecycle is a strong signal the effect boundary is drawn in the wrong place.
- **Treat "does the profiler show this render as wasted and repeated" as the *only* trigger for reaching for `React.memo`/`useMemo`/`useCallback`** — apply the cheaper fixes first (state co-location so fewer components sit in the re-render path at all, and passing JSX as `children` so the parent's own state changes don't force the child subtree to re-render) before reaching for memoization, exactly as `react-performance-optimization` already instructs.
- **Give the graph/list-key correctness discipline (`key={a.id}`, never `key={index}`) an explicit one-line rationale wherever a worked example already gets it right** — `react-component-design`'s `DataAssetTable` example already uses a stable id correctly; the skill just doesn't say *why* index would be wrong, which would cost one sentence and make the correct pattern legible rather than merely present.
- **When a form needs to be validated live or has dependent fields, use a controlled input; when it's simple and write-once, default to uncontrolled with a form library that keeps inputs uncontrolled internally** — `react-component-design` already states this correctly; the actionable follow-through is making sure any future worked form example in this skill domain doesn't reflexively reach for controlled inputs on every field "for consistency" once a form grows past a handful of fields, which is exactly the performance case the book's uncontrolled-for-large-forms guidance addresses.

## Key Terminology

Checked against `skills/glossary-management/references/ubiquitous-language.md` in full: none of the following terms currently appear there. Unlike the micro-frontends research cluster's terminology (deferred pending an architecture decision that hasn't been made), every term below is **already in active use** across the 13 React skills this file grounds — this is the actively-adopted default frontend stack (`CLAUDE.md`'s Tech Stack Defaults), not a hypothetical future one, so these are live candidates for `glossary-management` rather than speculative future-reference entries:

- **Custom Hook** — a `useX`-named function that calls other hooks internally to extract and share stateful logic across components, without adding a wrapper component to the tree. The book's hooks-era replacement for Higher-Order Components and render props specifically for state/effect reuse. Used throughout `react-component-design`, `react-state-management`, and `react-api-client`'s prose without a canonical definition on record.
- **Rules of Hooks** — the two constraints governing every hook call: only at the top level of a function component or another hook (never in conditionals, loops, or nested functions), and only from a React function component or a custom hook (never a plain function). Already stated as a hard constraint in `react-component-design`; not yet a defined glossary term.
- **Exhaustive Dependencies** — the discipline that a `useEffect`/`useMemo`/`useCallback` dependency array must include every reactive value the effect/computation body reads, so the effect never closes over a stale value from an earlier render. Underlies several existing Anti-Patterns across `react-state-management` and `react-performance-optimization` without being named as a single concept.
- **Stale Closure** — a bug where a function (typically inside an effect or callback) captures a value from the render that created it and continues using that outdated value on subsequent invocations, because the value was omitted from the dependency array that should have triggered the function's recreation.
- **Controlled Component** — a form input whose value is held in React state and updated via `onChange`, making React the single source of truth for the current value. Contrasted with Uncontrolled Component (below); both terms are used in `react-component-design` without a canonical glossary definition.
- **Uncontrolled Component** — a form input whose value is held by the DOM itself, read imperatively via a `ref` rather than tracked in React state on every change; preferred for simple or write-once inputs where the performance cost of a controlled input's per-keystroke re-render isn't justified.
- **Reconciliation** — React's algorithm for comparing a component's newly rendered element tree against its previous one to compute the minimal set of DOM mutations, using element type and (for lists) the `key` prop to determine whether a child is the same logical element (update in place) or a different one (unmount and remount).

## Caveats

- **This book's 2nd edition was published in 2020 and does not cover React 18's concurrent features** — `useDeferredValue`, `useTransition`/`startTransition`, `useId`, `useSyncExternalStore`, automatic batching, and React 18 Strict Mode's deliberate effect double-invocation in development all shipped in React 18 (March 2022), after this edition. `skills/react-performance-optimization/SKILL.md`'s "Part 6 — Keeping Interactions Responsive (Concurrent Features)" section and `skills/react-state-management/references/tanstack-query-patterns.md`'s `useSuspenseQuery` mention are both accurate, current React guidance, but this book is not their source and should not be cited as though it were — that guidance is grounded in React's own documentation and release notes, a different (and more current) source than this file represents. This caveat exists specifically so a future reader doesn't assume this research file validates concurrent-feature content it cannot actually speak to.
- **The book's own testing chapter is comparatively thin and dated next to this repo's `react-component-testing`/`react-e2e-testing` skills.** Testing Library's `getByRole`/`getByLabelText` query-priority guidance has matured considerably since 2020, largely independent of this book; the skills' testing depth should be understood as informed primarily by Testing Library's own documentation, not this book, even though the book does teach the same "test behavior, not implementation" philosophy at a foundational level.
- **This file is confident about the durable, well-corroborated mechanics** (the Rules of Hooks and their call-order rationale, the dependency-array/cleanup discipline, custom hooks superseding HOCs/render props for state reuse, the useMemo/useCallback cost-vs-benefit framing, controlled/uncontrolled trade-offs, key-prop identity semantics, Context's re-render-on-any-change cost, and the class-component-only error boundary requirement) as accurately representing this book's actual, well-documented content — these are the foundational, broadly corroborated teachings a canonical hooks-era React book covers, not filler. It is less certain about this specific edition's exact chapter ordering, code-listing verbatim syntax, or page-level structure, which is flagged here rather than asserted with false precision, consistent with how the sibling `research/micro-frontends/` files handle the same kind of uncertainty.
- **The `react-graph-visualization` findings (the `useMemo`-vs-`useRef` choice and the under-specified `Worker` cleanup dependency) are read directly off the skill's own published code examples**, not inferred or hypothesized — both snippets are quoted verbatim in the Applies To table above and can be checked directly against `skills/react-graph-visualization/SKILL.md`.
- **Nothing in this file should be read as a recommendation to add a new skill.** The Candidate New Skills/Agents section concludes none is warranted for the same reason the sibling `research/micro-frontends/` files are conservative about scope creep: this repo's `skill-authoring-standards` progressive-disclosure rubric already has a designated, lighter-weight home (a `references/` file under an existing skill) for exactly the kind of narrow, mechanical addition (an ESLint plugin, a checklist line) this review actually surfaced.
