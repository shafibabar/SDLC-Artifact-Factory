The epic list satisfies ALL of the following:
1. It begins with a frontmatter block containing at least name, version, phase, owner, created and a one-sentence summary, with phase "ideate"; and every epic traces by ID to a selected-path deliverable (SOL-1 or SOL-3), to a job story (JS-1.1, JS-1.2 or JS-2.1) and to the user requirement(s) it carries (UR-1 / UR-2, or TR-1 for transition work).
2. SOL-2 (the 4 pm rota slot) is NOT written as an epic: it is explicitly recorded as a non-software procedure or "not an epic" item. SOL-4 and the web order form are not epics either (they are options; mentioning them as excluded is fine).
3. Every epic has a falsifiable hypothesis (an actor's behaviour change with a signal or measure, linked to KR-1.1), AND a risk line covering all four of value, usability, feasibility and viability, each given a status (for example tested / assumed / low) — ASM-1 / T-1 must not be presented as already tested.
4. Priorities are provisional (for example high / medium / low, or value and penalty scores) and stated to be finalised later by MoSCoW prioritisation; no epic is labelled Must, Should, Could or Won't. Each epic has 3–5 high-level epic acceptance criteria, none written as Given/When/Then.
Fail if any of the four is missing.
