The response satisfies ALL of the following:
1. It does not keep `POST /approveInvoice` as a free-floating verb endpoint. It first considers whether approval is a state change on the invoice resource (for example PATCH of a status field with the allowed transition enforced), and if approval is a genuine business action that is not plain CRUD, it uses the custom method `POST /invoices/{id}:approve` with the invoice id in the path, not the body (`research/software-architecture/api-design-patterns-geewax.md`, Core Concepts and Actionable Techniques, custom methods as the fallback; `wave-2-findings.md`, `### api-contract-design`, eval idea (a)).
2. It separates the two failure kinds in the clerk scenario. Approving an invoice that is in the wrong state (for example already approved) is a business-rule conflict, returned as 409 with a distinct error code. The silent overwrite between two clerks is a lost update, prevented by an ETag or revision value returned on read and required back in `If-Match` on update, with a failed check returned as its own error (412 or a 409 with a different, named code) so a client can tell them apart. The reply does not just say "return 409" for both (`api-design-patterns-geewax.md`, Core Concepts, concurrency and errors; `research/testing/testing-web-apis-winteringham.md`, each error branch is a testable response).
3. It rejects holding the connection open for the multi-minute export and designs a long-running operation: the request returns 202 Accepted with a pollable Operation resource (a name or id, a `done` flag, and either a `response` or an `error`), and the finished file is fetched from a link in the result. It names the status-polling endpoint (`api-design-patterns-geewax.md`, Core Concepts, long-running operations).
4. It treats the export as a resource-oriented operation rather than a `GET /exportInvoices` verb: either a custom method on the collection (for example `POST /invoices:export`) or an export resource that is created, and it says why a plain GET that triggers work is wrong (`api-design-patterns-geewax.md`, custom methods; resource-oriented design).
5. It requires an Idempotency-Key header where a retry could repeat an effect, here on the POST that triggers the approve action and the one that starts the export, and says PUT and DELETE are already idempotent so need none. It states how long keys are kept and presents that window as a decision for this product rather than a fixed universal value (`api-design-patterns-geewax.md`, Core Concepts, request identification and retries; `wave-2-findings.md`, `### api-contract-design`, gap on Idempotency-Key and the 24 h window).
6. It rejects generating the spec from the handlers after the fact: the OpenAPI 3.1 contract is written first, reviewed and approved, and is what gates the handler code; code is then checked against it. It places the contract at the design-phase path `design/invoicing/openapi.yaml` (or `design/<service>/openapi.yaml`), copied into the service repo at implementation (`research/software-architecture/api-first-transformation-lane.md`, contract first, the contract as the product; `wave-2-findings.md`, W2-33).
7. It says each documented response header (ETag, Location or Operation link, Retry-After if used) and each error branch in the contract must be exercised by a contract test, so the contract is testable and not just documentation (`research/testing/testing-web-apis-winteringham.md`, testing status codes, headers and error responses).
8. It does not assume multi-tenancy: no tenant path variable such as `/tenants/{tenantId}/invoices` and no per-tenant physical isolation, because Ledgerline is one company's internal tool (D047-7).
9. The reply contains no Go, SQL or other implementation code, even though the request mentions Go developers. OpenAPI/YAML fragments and example JSON are the contract itself and are allowed (D047-10).
Fail if any of the 9 is missing.
