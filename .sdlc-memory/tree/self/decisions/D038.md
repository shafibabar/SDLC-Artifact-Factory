# D038: After the Chunk 44 grouped campaign closed (with the cross-cutting group — react-accessibility, react-observability, react-performance-optimization, react-dockerfile — returning zero file changes), Shafi requested individual deep rebuilds of all 13 react-* skills following the per-skill-sub-issue pattern (each skill gets its own GitHub issue, branch, and PR) rather than another grouped pass. Issues #394-#406 were executed sequentially across 2026-07-26 through 2026-07-30, each producing a full progressive-disclosure split (SKILL.md body trimmed to decision-shaping guidance, implementation detail and worked examples moved to references/), a references/ directory with 3-4 new reference files per skill, and a contract test at tests/skills/<name>.contract.sh grounded in a non-obvious fact confirmed absent from SKILL.md via grep. Housekeeping for the full campaign collected in issue #407 (this entry): CLAUDE.md /init improvements (layout section additions, skill-refactor branch-naming pattern, contract-test requirement), 3 new canonical glossary terms (ARIA, Core Web Vitals, WCAG) added in a new Frontend Engineering section, CHANGELOG entries for all 13 individual rebuilds, and sdlc-context.json updated with this decision.

**Date:** 2026-07-30

**Rationale:** The grouped campaign (Chunk 44, D037) established the right research-before-writing discipline and fixed two real bugs in react-graph-visualization, but the group-level sub-issues meant that each skill's body was checked once in context with 2-4 sibling skills rather than as a standalone review. The individual rebuild pass gave each skill its own focused session: cross-references were verified against actual current content on the branch rather than assumed states, SKILL.md bodies were tightened to the ~200-line progressive-disclosure threshold, and every skill that had no contract test gained one. The per-skill-sub-issue pattern (D025) had already been validated across access-control-model (#120), adr-authoring (#128), acceptance-criteria (#145), acceptance-sign-off (#155), access-control-model (#165), aggregate-design (#175), alerting-rules-design (#199), analytics-requirements (#217), api-contract-design (#231), artifact-manifest (#251), bdd-feature-file (#266), and beta-program-design (#282) — all of them individual skills with their own issue, not part of a grouped pass. Applying the same pattern to the react-* domain was consistent with established practice.

**Alternatives rejected:**
- Run a second grouped campaign (4 skills per sub-issue) rather than individual per-skill issues — rejected: the individual-skill pattern already has its own exec_start.py / exec_complete.py tooling and yields a focused, fully-auditable commit per skill; a second grouped pass would have the same coverage-per-sub-issue limitation the first pass had
- Treat the cross-cutting group's zero-change result as final and skip individual rebuilds for react-accessibility, react-observability, react-performance-optimization, and react-dockerfile — rejected: a 'nothing applies' result from a group-level sub-issue with 4 skills in context means the research was correct in aggregate, not necessarily that each skill's own body is already at the progressive-disclosure depth standard — the individual rebuilds confirmed that all four needed reference splits and contract tests
