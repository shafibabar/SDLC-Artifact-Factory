# D024: End the plan-start/plan-exit GitHub Project ceremony (parent issue + numbered sub-issues via save_draft/plan_exit) for future individual skill refactors. Skill refactors continue directly -- read the current skill, gap-check against research/industry sources, design a progressive-disclosure split, rewrite, commit -- without a new parent issue + sub-issue set per skill. Already-open sub-issues from in-flight plans (this chunk's #90-#98) were still completed via the existing exec-start/exec-complete flow rather than abandoned mid-flight, since abandoning already-created GitHub tracking would leave orphaned issues.

**Date:** 2026-07-22

**Rationale:** Shafi's explicit instruction, given after two full campaign cycles (ddd-agent-handoff issue #54, subdomain-distillation issue #68) and mid-way through a third (this chunk, issue #89): the plan/execute ceremony's value was establishing a repeatable, well-understood procedure (per D021's per-skill process) -- once demonstrated and understood, repeating the ceremony for every additional skill adds overhead without adding safety, given the process itself (gap-check against real sources, progressive disclosure, verification) is what's load-bearing, not the GitHub issue tracking around it.

**Alternatives rejected:**
- Keep using plan-start/plan-exit for every future skill -- rejected per Shafi's explicit instruction once momentum and shared understanding were established
- Also abandon the already-open #90-#98 sub-issues' tracking retroactively -- rejected: they were already created and tracked; finishing them via the existing lightweight exec-start/exec-complete flow avoided orphaning GitHub state for no benefit
