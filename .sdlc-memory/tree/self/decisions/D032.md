# D032: Extend api-contract-design with four patterns from JJ Geewax's API Design Patterns: a named custom-method escape hatch (POST /{resource}:verb) alongside the existing 'Verb endpoints' anti-pattern; a fully-specified Operation resource shape for the 202 Accepted status-check response, reusing the skill's existing ErrorResponse.error object by reference rather than redefining a new error type; a resource-revisions (etag/If-Match) optimistic-concurrency mechanism distinct from the existing 409 Conflict business-rule row; and a field-mask convention clarifying PATCH partial-update semantics. Explicitly declined to change the skill's existing per-field-query-parameter filtering convention to match the book's filter-expression-string approach.

**Date:** 2026-07-24

**Rationale:** research/software-architecture/api-design-patterns-geewax.md found api-contract-design had zero primary-source grounding despite being the authoritative contract between backend-engineer and frontend-engineer, and identified four specific, narrow gaps where the skill's existing conventions left a real question unanswered (most consequentially, what a 202 Accepted status URL actually returns when polled) rather than broad disagreement with anything already built. Declined the filtering-convention change because implementing a filter-expression grammar is real engineering cost CLAUDE.md's Budget and Frugality principle would weigh against without a concrete need for compound/boolean filter logic -- the research file itself frames the skill's existing named-parameter approach as a deliberate, defensible choice, not an oversight to fix.

**Alternatives rejected:**
- Migrate the skill's filtering convention to Geewax's single filter-expression-string parameter to match the book more closely -- rejected: this is real, unjustified implementation cost against a frugal, single-operator context with no concrete need for compound filter logic yet; the research file itself argues against this change
- Treat this as a modest, single-file content addition like the analytics-requirements precedent rather than a genuine multi-file rebuild -- rejected: the skill was already 323 lines before any additions, past the split threshold on its own, and the four new patterns (each with worked YAML examples) add substantial, cohesive new content that reads far better as a dedicated references/ file than crammed into an already-long single file
- Adopt Geewax's full Google-AIP-style API design system (gRPC/Protocol-Buffers-oriented conventions, the complete google.rpc.Status error model) wholesale -- rejected: most of that ground is irrelevant to this repo's REST/OpenAPI-only stack; only the REST-applicable subset (custom methods, LRO shape, revisions, field masks) closes an actual gap
