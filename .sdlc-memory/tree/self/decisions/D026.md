# D026: For issue-level-integration-branch plans (D025 pattern), do not call plan_status.py done when sub-issue work finishes merging into the integration branch -- only after Shafi has actually merged the final integration-branch-to-main PR. The parent GitHub issue itself still auto-closes correctly via its 'Closes #N' body text at that real merge; this decision only concerns the Project board's Status field, which plan_status.py done updates.

**Date:** 2026-07-23

**Rationale:** Direct correction from Shafi for issue #120: 'the parent issue should not be closed until the main PR is merged by me.' Investigation showed issue #110's actual GitHub close had in fact fired at the correct time (Shafi's real merge of PR #111) -- the real mistake was calling plan_status.py done immediately once sub-issues landed on the integration branch, before that merge, which prematurely marked the Project board Status as Done while the final PR was still awaiting Shafi's review.

**Alternatives rejected:**
- Leave the timing as-is on the theory that the GitHub issue-close mechanism is what actually matters -- rejected: Shafi's feedback was about the signal the Project board Status field sends, not just the issue-close event, and a premature Done status is still a misleading signal even if the issue itself closes correctly later
