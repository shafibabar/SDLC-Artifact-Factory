# D025: Re-introduced GitHub issue/sub-issue tracking (reversing D024's default, for this case) using a new pattern: an issue-level integration branch with its own draft PR, sub-issue branches cut from and PRs targeting that integration branch (not main) via exec_start.py's new --base flag, merged into the integration branch by Claude in sequence as each sub-issue completes, with only the single integration-branch-to-main PR left for Shafi to review and merge. Used for the acceptance-sign-off refactor (issue #110, sub-issues #112-#115, integration PR #111).

**Date:** 2026-07-23

**Rationale:** Shafi explicitly requested 'detailed issues and sub-issues and relevant PRs' for this refactor and asked that it be 'done automatically,' with only one final PR requiring his review -- a different, heavier-weight shape than D024's default direct-commit process, requested for this specific case rather than a reversal of D024 generally. The issue-level-branch pattern satisfies both asks at once: full GitHub tracking/traceability per sub-issue, but a single review/merge point for Shafi rather than one per sub-issue.

**Alternatives rejected:**
- Merge every sub-issue PR directly into main as in the original D021-era process -- rejected: contradicts 'I will review and merge the final PR,' which implies exactly one PR for Shafi to handle, not one per sub-issue
- Skip GitHub issues entirely per D024's default -- rejected: contradicts this specific request for 'detailed issues and sub-issues,' which D024 did not forbid for cases where Shafi explicitly asks for it again
