# D048: Fresh-Eyes Wave 3 testing decisions — full testing at every product size, 100% coverage, test-first for Python, micro-frontends stay, all test artifacts approved by the product owner

**Date:** 2026-11-25

**Rationale:** The Wave 3 audit (`discovery/fresh-eyes/wave-3-findings.md`, #1451) raised nine decisions (W3-D1 to D9). The product owner wants the plugin to run the SDLC with full agentic pipelines ("Claude AI level 5") and wants testing held to the highest bar.

1. **Test first (W3-D1):** accept any matching test layout, exempt test-support, configuration, type, entry and index files, and add Python.
2. **Testing per size (W3-D2):** every product size gets the full testing treatment. This overrides the recommendation to scale testing by profile.
3. **Micro-frontends (W3-D3):** the 2026-07-22 decision stands at every size.
4. **Lean acceptance criteria (W3-D4):** a small product gets the same treatment as other sizes, so example maps are required at lean.
5. **Approvals (W3-D5):** the product owner approves test strategy, feature files and test reports.
6. **Coverage (W3-D6):** 100%, not 80%. Measure and exclusions: see follow-up A.
7. **Python build skills (W3-D7):** repair the five the Python tests depend on, first.
8. **Real toolchains (W3-D8):** install and run them in a throwaway environment.
9. **Eval spending (W3-D9):** acknowledged ("Understood"); applied as a $450 ceiling with a check-in after four skills.

Engineering defaults W3-D10 to D31 stand, except where answers 2 and 4 override them (profile-based reductions in D14, D19, D26, D30, D31 are removed).

- **A. Coverage:** 100% of both lines and branches. Only machine-generated code is excluded; any other exclusion is listed with a reason for the product owner to approve. Whether Go needs an extra tool for branches is verified during the rebuild.
- **A, Go (product owner, 2026-11-25, option A):** Go's tooling measures statement blocks only (`research/testing/go-coverage-official-docs.md`, #1456). Enforce 100% of statement blocks as a hard gate, plus `gobco` branch coverage after a trial, with the unmeasured cases (including `select`, `range` and zero-iteration loops) stated in each report. If the trial fails, return to the product owner; do not drop to statements only.
- **B. Mutation:** every planted fault is caught by a test, or recorded with the reason it cannot be (the change does not alter behaviour). Replaces the 60% target in W3-D19.
- **C. Level 5:** agents and pipelines perform the work; the product owner keeps approval of each phase's key documents.

**Follow-up decision (product owner, 2026-11-26): gobco after its trial, option A.** The trial on Go 1.27.4 with gobco 1.3.4 was not a clean pass (build-tagged files silently unmeasured; several constructs panic or fail; package by package only). Keep gobco, strictly: any "no result" (tool failure or unmeasured file) blocks the build; the remedy is to change the code so it can be measured, or an exception listed for the product owner's approval. Never report unmeasured code as passing and never drop to statements only.

**Follow-up decisions (product owner, 2026-11-26): Python coverage exclusions, option A.** coverage.py's default exclusion of `...` placeholder bodies and `if TYPE_CHECKING:` blocks is approved once, as a class: no per-file approval, and every report still lists them. Any other exclusion still needs its own listed reason and approval. Also approved: unmeasurable cases (for example zero-iteration loops, one-line alternatives, docstring-only bodies counted as run) are stated in reports; skipped tests are reported, not blocking; the coverage gate ignores the product's own coverage settings and addopts.

**Follow-up decision (product owner, 2026-11-27): test-support code, option A.** The test-scaffolding folder (shared test harness, e.g. `internal/test/`) is approved once, as a class, for every product: excluded from the coverage gate without per-file approval, and every report still lists it. It covers test support only, never code that ships.

**Follow-up decision (product owner, 2026-11-27): Python test-support listing, option B.** The Python coverage gate lists the test-support code itself in its output (it is not measured), so reports show it without manual entry. This reopens the finished `python-unit-test` skill, which is re-evaluated.

**Follow-up decisions (product owner, 2026-11-28): contract testing (#1489). These replace W3-D22's "Pact only on the escalation trigger".**
- **API-description gate:** every pull request compares the description with the deployed one at the stricter level (`oasdiff breaking --fail-on WARN`); removing or renaming an optional response field and removing a documented error response are also failures. `api-contract-design` classifies a removed documented error response as breaking.
- **Exceptions:** a new enum value in a response fails by default; the product owner approves each case, recorded in an exceptions file printed on every run. The file covers nothing else: any other breaking change ships as a new major version.
- **Events:** both the compatibility mode the event design declares and the add-only pass on closed copies. No Pact message contracts.
- **Pact:** for every direct service-to-service request/response call, at every product size, lean included, on a self-hosted open-source broker, on top of the description checks. No trigger and no decision record is needed; a paid service needs approval.
- **When Pact runs:** as a daily scheduled run that produces an impact report for the product owner's approval, not on a build or pull request. A pull request is not blocked by Pact.
- **Deployment:** a service's deployment checks the latest recorded Pact result (`can-i-deploy`) and is refused when it shows a broken caller.
- **Retiring an endpoint:** removal after the sunset date also needs a recorded product-owner sign-off stating the evidence that no caller remains.
- **Still to align:** `python-contract-test` (#1490), and `test-pyramid`, `ci-pipeline`, `cd-pipeline` (#1503).

**Alternatives rejected:** scaling test depth by profile; an 80% coverage floor; a 60% mutation target; one single web app at lean.
