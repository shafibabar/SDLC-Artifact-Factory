# D048: Fresh-Eyes Wave 3 testing decisions — full testing at every product size, 100% coverage, test-first for Python, micro-frontends stay, all test artifacts approved by the product owner

**Date:** 2026-11-25

**Rationale:** The Wave 3 audit (`discovery/fresh-eyes/wave-3-findings.md`, #1451) raised nine decisions (W3-D1 to D9). The product owner wants the plugin to run the SDLC with full agentic pipelines ("Claude AI level 5") and wants testing held to the highest bar.

1. **Test first (W3-D1):** accept any matching test layout, exempt test-support, configuration, type, entry and index files, and add Python.
2. **Testing per size (W3-D2):** every product size gets the full testing treatment. This overrides the recommendation to scale testing by profile.
3. **Micro-frontends (W3-D3):** the 2026-07-22 decision stands at every size.
4. **Lean acceptance criteria (W3-D4):** a small product gets the same treatment as other sizes, so example maps are required at lean.
5. **Approvals (W3-D5):** the product owner approves test strategy, feature files and test reports.
6. **Coverage (W3-D6):** 100%, not 80%. Measure and exclusions: see follow-up A.
7. **Python build skills (W3-D7):** repair the five the Python tests depend on, first.
8. **Real toolchains (W3-D8):** install and run them in a throwaway environment.
9. **Eval spending (W3-D9):** acknowledged ("Understood"); applied as a $450 ceiling with a check-in after four skills.

Engineering defaults W3-D10 to D31 stand, except where answers 2 and 4 override them (profile-based reductions in D14, D19, D26, D30, D31 are removed).

**Follow-up decisions (product owner, 2026-11-28): contract testing (#1489). These replace W3-D22's "Pact only on the escalation trigger".**
- **API-description gate:** every pull request compares the description with the deployed one at the stricter level (`oasdiff breaking --fail-on WARN`); removing or renaming an optional response field and removing a documented error response are also failures. `api-contract-design` classifies a removed documented error response as breaking.
- **Exceptions:** a new enum value in a response fails by default; the product owner approves each case, recorded in an exceptions file printed on every run. The file covers nothing else: any other breaking change ships as a new major version.
- **Events:** both the compatibility mode the event design declares and the add-only pass on closed copies. No Pact message contracts.
- **Pact:** for every direct service-to-service request/response call, at every product size, lean included, on a self-hosted open-source broker, on top of the description checks. No trigger and no decision record is needed; a paid service needs approval.
- **When Pact runs:** as a daily scheduled run that produces an impact report for the product owner's approval, not on a build or pull request. A pull request is not blocked by Pact.
- **Deployment:** a service's deployment checks the latest recorded Pact result (`can-i-deploy`) and is refused when it shows a broken caller.
- **Retiring an endpoint:** removal after the sunset date also needs a recorded product-owner sign-off stating the evidence that no caller remains.
- **Still to align:** `python-contract-test` (#1490), and `test-pyramid`, `ci-pipeline`, `cd-pipeline` (#1503).

**Follow-up decisions (product owner, 2026-11-28): end-to-end testing (#1491).**
- **Environment:** a throwaway Kubernetes cluster (kind) created for the run, at every product size, lean included. No Docker Compose variant and no lighter lean environment. Never a shared, staging, production or tenant environment.
- **Quarantine:** a quarantined test is named in a list file with its issue and deadline, not marked with a build tag.
- **Images:** third-party images are pulled by the cluster node from their registry, not preloaded.
- **Still to align (#1503):** `ci-pipeline`, `environment-config`, `cd-pipeline`, `blue-green-deployment`, `disaster-recovery-plan`, `go-makefile`, `react-e2e-testing`, each listed with file and line on #1491.

**Follow-up decisions (product owner, 2026-11-28): load testing (#1493).**
- **Two tiers.** A small load check in the throwaway kind cluster on the nightly run, reported as indicative only: it catches a regression between runs and proves nothing about capacity. A verdict against the product's stated targets needs a designated performance environment that the product owner approves per product, sized and loaded with data as the requirements state. The test refuses to run against anything not designated. A lean product may have only the indicative tier until an environment is approved.
- **No load on any other system without a signed impact statement.** By default the test refuses every target that is neither the run's own throwaway cluster nor a designated environment. Load may be run against another system, staging or production included, for verification only when the product owner signs a statement that says exactly where the load runs and what its impact will be (amended by the product owner the same day; it replaces "no load on shared staging or production").
- **Designation:** a record naming the exact address, the product owner's dated sign-off and an expiry, plus a matching marker the environment serves. A scheduled verdict run gets a per-run token through the CI job's own identity, with no stored secret; until an environment supports that, verdict runs are started by hand. A run that both dropped load and failed its thresholds is INVALID, with the failed thresholds listed.
- **Credentials:** none stored for the indicative tier; for a designated environment a short-lived token the product owner approves, never a standing one.
- **One load tool: k6** (confirms W3-D18); vegeta is dropped.
- `python-load-test` (#1494) follows the same decision.

**Follow-up decisions (product owner, 2026-11-28): chaos testing (#1495).**
- **Where:** by default only in the run's own throwaway kind cluster. Any other system (a designated environment, staging, production) only with the product owner's signed statement of exactly where, which faults, the blast radius, the abort conditions and the impact. The staged rollout to real environments is withdrawn.
- **Privileged injector** (for example Chaos Mesh's daemon) only inside the throwaway cluster. Application-level and network-proxy faults first; cluster-level faults allowed there at every size.
- **No standing production chaos:** the weekly production experiments in `disaster-recovery-plan` are replaced by scheduled experiments in the throwaway cluster; a production experiment needs the signed statement each time.
- **Patterns:** the chaos skills test what the product implements, against `integration-design`'s thresholds, and say when a pattern is missing; building a circuit breaker, bulkhead and retry in the Go build skills is a gap for a later wave.
- `python-chaos-test` (#1496) follows the same decisions. Product owner, the same day: Python chaos experiments run in the throwaway kind cluster only (no per-test testcontainers stack); the shared runner `run-chaos-experiment.sh` runs both `go test` and pytest, identical in both skills; the Python build skills' missing circuit breaker, retry and bulkhead join the later-wave gap.

**Follow-up decisions (product owner, 2026-11-28): mutation testing (#1497).**
- **The release run blocks:** a full run before each release meets decision B (or is waived above 90% after review) and finishes before publication; scheduled runs between releases report only.
- **Scope:** all product code; a package left out is a listed exclusion with a reason for the product owner's approval.
- **Cadence:** a product may run mutation more often than the default, never less.
- **Tool:** Gremlins pinned to an exact version (pre-1.0 accepted); runs between releases may target changed code only, the release run covers everything.
- `python-mutation-test` (#1498) follows the same decisions.
- Rebuild details approved by the product owner on 2026-11-28 (#1497):
  - A timed-out mutant that a test kills when rerun with a longer time limit counts as killed.
  - A waiver names a fingerprint of the code, the mutation setup and the record. A later code change voids the waiver.
  - A record line that matches no planted mutant fails the run and cannot be waived.
  - A repository with several modules runs one full release job per module. A module that cannot finish within the 6-hour hosted limit uses a self-hosted runner.
- python-mutation-test rebuild details, approved by the product owner on 2026-11-29 (#1498):
  - mutmut is pinned at 3.8.1, the version proven in the rebuild lab. 3.9.0 comes later, as a deliberate upgrade that reruns the lab.
  - The type checker is off by default; a product may turn it on.
  - A timed-out mutant is rechecked at 60 times the tests' estimated time.
  - Python test support is everything under `tests/`. It is never mutated and is listed in each report.
  - The exclusions file has four fields: path, scope (file, folder or lines, with a fingerprint), approval, reason.
  - A file with no function in it needs no exclusion entry.

**Alternatives rejected:** scaling test depth by profile; an 80% coverage floor; a 60% mutation target; one single web app at lean.
