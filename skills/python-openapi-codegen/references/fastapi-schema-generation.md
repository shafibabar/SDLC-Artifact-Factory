# FastAPI Schema Generation

Full standard referenced from `SKILL.md`'s "The Direction Reversal", "The Process Fix" (steps 2–3),
and "Type-Mapping Direction" sections — precisely *how* FastAPI derives the OpenAPI schema from
Pydantic models and route decorators, how to pin the metadata FastAPI would otherwise auto-invent so
the emitted schema can match a hand-authored contract, and how to export the schema deterministically
for the CI conformance check. Self-contained — usable without the parent `SKILL.md` body in context.

---

## Where the Schema Comes From

FastAPI builds the OpenAPI document lazily, the first time it is needed, by introspecting the app:

- **Paths** come from the route decorators (`@app.get`, `@app.post`, …) and their `path` argument.
- **Request bodies / parameters** come from each handler's typed parameters — a Pydantic
  `BaseModel` parameter becomes a request body `$ref`; `Query(...)`, `Path(...)`, `Header(...)`
  markers become parameters.
- **Response schemas** come from `response_model=` and the `responses={}` map on the decorator.
- **Component schemas** (`components.schemas`) are generated by Pydantic's own
  `model_json_schema()` for every `BaseModel` FastAPI encounters, de-duplicated by class name.

The result is cached on `app.openapi_schema`. `app.openapi()` returns it (building it on first
call); the `/openapi.json` route serves it; `/docs` (Swagger UI) and `/redoc` render it. FastAPI
targets **OpenAPI 3.1** with Pydantic v2 (JSON Schema 2020-12), matching the 3.1 contract
`api-contract-design` authors.

```python
# app/api/models.py — the schema is DERIVED from these classes
import uuid
from datetime import datetime
from enum import Enum
from pydantic import BaseModel, ConfigDict, Field


class SensitivityLevel(str, Enum):
    public = "public"
    internal = "internal"
    restricted = "restricted"


class DataAsset(BaseModel):
    id: uuid.UUID
    display_name: str = Field(min_length=1, max_length=256)
    sensitivity: SensitivityLevel
    discovered_at: datetime


class ClassifyDataAssetRequest(BaseModel):
    sensitivity: SensitivityLevel
```

## Pydantic → OpenAPI Type Mapping

| Python / Pydantic | OpenAPI (3.1) emitted |
|---|---|
| `str` | `type: string` |
| `int` | `type: integer` |
| `float` | `type: number` |
| `bool` | `type: boolean` |
| `uuid.UUID` | `type: string`, `format: uuid` |
| `datetime` | `type: string`, `format: date-time` |
| `Optional[T]` / `T \| None` | `anyOf: [T, {type: "null"}]` (3.1 nullable) |
| `list[T]` | `type: array`, `items: T` |
| `Enum` subclass | `enum: [...]` |
| nested `BaseModel` | `$ref: '#/components/schemas/Name'` |
| `dict[str, Any]` / freeform | `type: object`, `additionalProperties: true` |

`format: uuid`/`date-time` are emitted only because the field is typed `uuid.UUID`/`datetime` — a
field left as bare `str` emits a plain `string` with no `format`, silently widening the contract.
This is the mirror image of `go-openapi-codegen`'s rule that a UUID field must not degrade to
`string`; here the discipline is "type the model precisely so the *emitted* schema is precise."

## Field Mask: omitted vs. explicit-null vs. value

A bare `sensitivity: SensitivityLevel | None = None` cannot distinguish "the client omitted this
field" from "the client sent `null`" — both decode to `None`, exactly the `*T` trap
`go-openapi-codegen` documents. Preserve the distinction with Pydantic v2's unset tracking:

```python
class PatchDataAssetRequest(BaseModel):
    # Only fields the client actually sent are considered "set".
    model_config = ConfigDict(extra="forbid")
    display_name: str | None = None
    sensitivity: SensitivityLevel | None = None


# In the handler: exclude_unset drops omitted fields; explicit null survives.
patch = request.model_dump(exclude_unset=True)   # {"sensitivity": None} iff client sent null
```

`exclude_unset=True` yields only the keys the client supplied, so an omitted field never appears
while an explicit `null` does — the field-mask update semantics `api-contract-design` requires.

## Pinning Metadata So the Schema Can Match the Contract

FastAPI auto-invents metadata that will *not* match a hand-authored contract unless pinned:

### Operation ids

By default FastAPI derives each operation id from the handler function name plus the full path and
HTTP method, producing long, unstable ids like `classify_data_asset_v1_data_assets__id__classify_post`.
A hand-authored contract uses short, stable ids (`classifyDataAsset`). Override globally with a
`generate_unique_id_function`, or per-route with `operation_id=`:

```python
# app/main.py
from fastapi import FastAPI
from fastapi.routing import APIRoute


def contract_operation_id(route: APIRoute) -> str:
    # Use the explicit name= on each route as the operation id, verbatim.
    return route.name


app = FastAPI(
    title="Data Estate API",
    version="1.0.0",
    generate_unique_id_function=contract_operation_id,
)
```

```python
# app/api/routes.py — pin id, tags, status, and per-status responses explicitly
@router.post(
    "/v1/data-assets/{id}/classify",
    name="classifyDataAsset",          # becomes the operation id via the function above
    operation_id="classifyDataAsset",  # or pin per-route directly
    status_code=204,
    tags=["DataAsset"],
    responses={
        404: {"model": ErrorResponse, "description": "Data asset not found"},
        422: {"model": ErrorResponse, "description": "Validation failed"},
    },
)
async def classify_data_asset(id: uuid.UUID, body: ClassifyDataAssetRequest) -> None:
    ...
```

### Tags, summaries, examples

Set `tags=[...]` explicitly (never rely on router-prefix defaults) so grouping matches the
contract. Attach request/response examples with Pydantic's `Field(examples=[...])` or
`model_config = ConfigDict(json_schema_extra={"examples": [...]})`, and per-parameter examples via
`Query(..., examples=[...])`. Set a stable `summary=`/`description=` per route rather than letting
FastAPI derive one from the function docstring.

## Exporting the Schema Deterministically

The conformance check needs the schema as a file, produced the same way every time. Dump
`app.openapi()` without starting a server:

```python
# scripts/export-openapi.py
import json
import sys
from app.main import app


def main() -> None:
    schema = app.openapi()  # the derived OpenAPI 3.1 document, as a dict
    json.dump(schema, sys.stdout, indent=2, sort_keys=True, ensure_ascii=False)
    sys.stdout.write("\n")


if __name__ == "__main__":
    main()
```

```bash
python scripts/export-openapi.py > openapi.gen.json
```

`sort_keys=True` makes the output byte-stable across runs (dict insertion order otherwise leaks into
the JSON), so the CI diff in `contract-conformance-check.md` never fails on cosmetic reordering.
`openapi.gen.json` is a **build artifact**, not committed as the contract — it is regenerated and
diffed, exactly as Go's generated file is regenerated and `git diff --exit-code`'d.

## What This Skill Does *Not* Own

Resource design, the versioning policy, and the Field Mask / Long-Running Operation / Resource
Revision *patterns themselves* are `api-contract-design`'s. Request validation wiring, the
`@app.exception_handler` error envelope, and `Depends()` injection are `python-fastapi-handler`'s.
This reference owns only how the schema is *derived and exported* for the conformance check.
