# Event Schema Checklist

Run after `./scripts/validate-event-schemas.sh` exits clean. The script checks structure; these items need judgement.

## Envelope
- [ ] Spec-required (four) and house-required attributes are listed separately; nothing house-only is called "required by CloudEvents".
- [ ] `id` is generated by the producer and unique within `source`; consumers use `source` + `id` for Idempotency.
- [ ] `time` is when the occurrence happened (from the Domain Event), not when it was published; the payload has no second occurrence timestamp.
- [ ] Each house extension says what it means and who sets it; `tenantid` appears only in a multi-tenant product.
- [ ] The content mode is chosen once; in binary mode, every forwarder (DLQ, relay) copies the `ce_` headers.
- [ ] `partitionkey`, if used, is the real ordering unit (the Aggregate, or the tenant).

## Payload
- [ ] Every field earns its place: a consumer reacts with it without calling back.
- [ ] No derived values that can drift, no whole-Aggregate dump, no raw sensitive values.
- [ ] Every optional field's default is true for old events; unknown history is "unknown", not zero or false.
- [ ] Field meanings agree with `domain-event-catalog`; names come from the context's Ubiquitous Language.

## Evolution
- [ ] Every change was classified with Young's test before choosing an action; a change of meaning is a new event, not a new shape.
- [ ] A unit or meaning change under the same field name is treated as breaking even though the registry would accept it.
- [ ] A new enum value has a notice and a window before it is produced.
- [ ] Each breaking change names its new type (descriptive, no suffix), the dual-publish window, the consumers told, and the telemetry that ends it.
- [ ] Stored events of an event-sourced Aggregate use weak schema, upcasting or copy-and-replace; nothing is edited in place; wrong facts get correcting events.

## Registry and gate
- [ ] The registry decision follows from consumers, format and teams, and is written down with its reason.
- [ ] Each compatibility mode fits the deploy order; retained or replayable topics use a transitive mode.
- [ ] The CI gate actually fails the build on an incompatible change; schemas are registered before the first publish and never deleted.

## Hand-off
- [ ] `traces-to` names the event catalogues and context map used.
- [ ] `go-event-publisher` can build the envelope and payload from this document without guessing.
- [ ] Consumers of every published type are named, or marked "none yet".
