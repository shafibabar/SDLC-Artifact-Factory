# The Envelope: CloudEvents 1.0

The detail behind `SKILL.md` § 1: every attribute, the house extensions, naming, and how an event rides Kafka (Redpanda). Grounded in the CloudEvents 1.0 specification, its JSON format, Kafka binding and Primer, as summarised in `research/software-architecture/cloudevents-spec.md`. Decision D047-1 sets the house rules. **Keep the two apart: what the spec requires, and what this plugin adds.**

## 1. Attributes

| Attribute | Spec | House rule |
|---|---|---|
| `specversion` | **required**: `"1.0"` (stays `"1.0"` for every 1.0.x patch) | — |
| `id` | **required**: non-empty String, unique **within its `source`**; `source` + `id` identifies one event, and consumers may treat a repeat as a duplicate | a UUID generated by the producer; the consumer's Idempotency key |
| `source` | **required**: URI-reference for the context the event happened in | a **stable** context URI, e.g. `/billing`; no deploy version (it would change every release and break filters on `source`) |
| `type` | **required**: non-empty String; SHOULD start with a reverse-DNS prefix | `<reverse-dns>.<context>.<aggregate>.<past-tense-verb>` (§ 2) |
| `datacontenttype` | optional: media type of `data`; absent means the format's own encoding (JSON in the JSON format) | always set, e.g. `application/json` or `application/protobuf` |
| `dataschema` | optional: URI of the schema `data` follows; an incompatible schema change SHOULD get a different URI | always set, to a **versioned** schema URI |
| `subject` | optional: what the event is about within the source | the Aggregate's ID |
| `time` | optional: RFC 3339 time **the occurrence happened** | always set, from the Domain Event's occurrence time, not the publish time |
| `data` / `data_base64` | the payload; never both | — |

`dataref` (the claim-check pointer to data held elsewhere) is a documented **extension**, not a core attribute; adopt it only for payloads too large for the broker.

Attribute values come from a closed type system (Boolean, Integer, String, Binary, URI, URI-reference, Timestamp): no maps, arrays or nulls. An attribute is present with a valid value or absent.

## 2. Type and source naming

- `type`: **lower-case, hyphenated segments**: `com.fernpost.lockers.parcel.deposited`. The reverse-DNS prefix is the organisation that defines the event's meaning (the product's domain, never a placeholder company). Context and Aggregate names come from the context map and the context's Ubiquitous Language; the verb is the Domain Event's past tense, as named in `domain-event-catalog`.
- **No version in the type**: never `.v2`, `_v2` or `V2`. A breaking change is a new type with a descriptive name (`./evolution.md` § 3).
- `source`: one URI per Bounded Context (`/lockers`). Absolute URIs (`https://events.fernpost.example/lockers`) are recommended once events leave the organisation.

## 3. House extensions (D047-1)

The spec allows extension attributes: flat, at the top level, named in **lower-case ASCII letters and digits only** (no hyphens, underscores or camelCase), terse, ideally ≤ 20 characters. A consumer that doesn't know one must ignore it. No CloudEvents document defines the three house extensions, so the house defines them:

| Extension | Type | Meaning | Set by |
|---|---|---|---|
| `correlationid` | String | the ID shared by every event and Command in one business flow | copied from the triggering Command or event; new at the flow's start |
| `causationid` | String | the `id` of the event or Command that directly caused this one | the producer, from what it was handling |
| `tenantid` | String | the tenant the event belongs to (multi-tenant products only) | the producer, from the Aggregate |

Adopted when needed, from the spec's documented extensions: `partitionkey` (the broker's record key; set to the ordering unit, often the Aggregate ID or the tenant) and `traceparent`/`tracestate` (W3C Trace Context, `distributed-tracing-design`). Tenant goes in `tenantid`, not in `data`; whether a product is multi-tenant, and how it isolates tenants, is that product's decision (D047-7).

## 4. On Kafka / Redpanda: one content mode per platform

- **Structured mode:** the whole event (attributes and `data`) is the record value, `content-type: application/cloudevents+json`. Forwarding the value byte for byte (a Dead Letter Queue, an outbox relay through Change Data Capture) carries everything.
- **Binary mode:** `data` is the value; each attribute is a header prefixed `ce_` (`ce_id`, `ce_type`, `ce_correlationid`); `datacontenttype` maps to the plain `content-type` header. Brokers and consumers can filter on headers without decoding, but every forwarder must copy the headers too. (HTTP uses `ce-`, not `ce_`.)
- The Kafka binding maps `partitionkey` to the record key.

Choose one per product and record it in the artifact's conventions. Structured is the simpler default; binary when routing on headers matters or the payload is Protobuf or Avro bytes.

## 5. What goes in `data`

A Domain Event is a fact that happened. Its payload carries what a consumer needs to react **without calling back**: the identifiers, the values that changed, the prior value where consumers act on transitions, and the actor. It leaves out:

- **envelope facts**: the event ID, type, occurrence time, source, version or tenant, which are attributes, not payload fields;
- **derived or duplicated values** that can drift from the authoritative record (a display name);
- **the whole Aggregate** ("so consumers have everything"), which couples every consumer to the write model and makes every internal change a contract negotiation (*stamp coupling*);
- **raw sensitive values.** A replicated, retained topic is the worst place for data that may need erasure; carry the identifier and let consumers fetch under access control (`data-retention-policy`).

What each field *means* belongs to `domain-event-catalog`; this skill fixes its name, type, whether it is required, and its default.

## 6. A worked event

A parcel deposited in a locker, in JSON structured mode:

```json
{
  "specversion": "1.0",
  "id": "5b0e7c62-6a43-4a5e-9a64-2f0c9b9f1d10",
  "source": "/lockers",
  "type": "com.fernpost.lockers.parcel.deposited",
  "datacontenttype": "application/json",
  "dataschema": "https://schemas.fernpost.example/lockers/parcel-deposited/3",
  "subject": "parcel-7Q4K2M",
  "time": "2026-11-05T09:14:03Z",
  "correlationid": "9d1f3a7e-0c55-4f0e-8b0d-61a1f6f2b0c4",
  "causationid": "c3e2a1b0-77d4-4b8e-9f10-0a2b3c4d5e6f",
  "data": {
    "parcelId": "parcel-7Q4K2M",
    "lockerId": "LK-0412",
    "compartment": "B07",
    "collectionCodeIssued": true,
    "collectBy": "2026-11-08T23:59:00Z"
  }
}
```

The same event in binary mode is a record whose value is the `data` object, keyed by `partitionkey` (here the locker, if per-locker ordering matters), with headers `ce_specversion`, `ce_id`, `ce_source`, `ce_type`, `ce_dataschema`, `ce_subject`, `ce_time`, `ce_correlationid`, `ce_causationid` and `content-type: application/json`.

The occurrence time is `time`, so the payload has no `depositedAt`. The collection code itself is not in the payload, only that it was issued. `dataschema` names version 3 of the schema.
