# Standard: Darkroom Rentals (handlers in scope, a build tag, a pending exclusion, weekly runs)

Self-contained. Read when a product has handlers, repositories, generated code and integration tests behind a build tag, or asks to run mutation more often than monthly. **Not run:** this product's code was not executed; every tool behaviour it relies on was observed in the lab of `./01-lean-rowing-boat-hire.md` or in `../references/gremlins-v0.6.0.md`.

## Input

A standard product renting darkroom bays by the hour. One Go module at the repository root:

| Package | Holds | Tests |
|---|---|---|
| `internal/domain/booking` | Bay booking rules (overlap, minimum two hours, late fee) | Unit, table-driven |
| `internal/application/rent` | Command handlers | Unit, with fakes |
| `internal/handlers/http` | chi handlers | `httptest`, unit |
| `internal/repository/pg` | pgx repository | `//go:build integration`, a throwaway PostgreSQL |
| `internal/repository/pg/db` | sqlc output (`// Code generated by sqlc. DO NOT EDIT.`) | None |
| `internal/application/rent/ports_moq.go` | moq mocks | None |
| `cmd/darkroom` | `main` | One start-up test |

The request: "Set up mutation testing; only the domain matters, skip handlers and the database code. And run it every week, it's cheap for us."

## What the agent does

1. **Scope: all product code** (M6). Handlers, repository and `cmd/` stay in. Skipping them is an exclusion only the product owner can approve; the agent does not add one on request. Generated sqlc code and the moq mocks are left out by marker and name, and listed.
2. **The integration tag.** Without it, every repository mutant is NOT COVERED (as the lab's tagged file was), and NOT COVERED is never recorded. Two ways out, put to the product owner:
   - run the release job with `MUTATION_TAGS=integration` and the PostgreSQL the integration tests already start: every repository mutant then reruns those tests (slow: one database setup per mutant, run time unmeasured);
   - or list `internal/repository/pg/` in `mutation/exclusions.txt` as **pending** with the reason, for approval. Pending excludes nothing: the verdict stays INVALID until the product owner decides.
3. **Weekly is allowed** (more often than monthly; never less). `sdlc-config.json` gets `methodology_parameters.mutation_test_cadence: "weekly"`; the workflow's cron becomes `"41 3 * * 1"`. The release run is unchanged.
4. Setup from the templates, the validator run until clean, then `make mutation MUTATION_TAGS=integration`.

## Output

### `mutation/exclusions.txt`, while the decision is open

```text
# Packages or files left out of mutation testing, each approved by the product owner.
# <path or folder/> | approved YYYY-MM-DD | <reason>      (or | pending | while awaiting approval)
# Generated code and internal/test/ are left out without an entry.
internal/repository/pg/ | pending | integration tests need PostgreSQL per mutant; cost not yet measured
```

The validator warns that it awaits approval; the verdict script refuses it (`INVALID: exclusion not approved or malformed`). If the product owner approves it, the line becomes `| approved 2026-12-02 |` and the report lists the package under **Approved exclusions**.

### Survivors a standard product typically meets

| Mutant | Triage |
|---|---|
| `booking.go`: `hours < 2` → `hours <= 2` LIVED | Real gap: no row at exactly two hours. Add `{"two hours is allowed", 2, nil}` |
| `http/bays.go`: `status == http.StatusConflict` → `!=` NOT COVERED | Only the application tests reach it (statement gate passed through `-coverpkg`). Give the handler package its own `httptest` case |
| `rent/late.go`: `fee += perHour` → `fee -= perHour` LIVED | Tests asserted only that no error came back. Assert the fee |
| `rent/late.go`: `fee %= cap` INVERT_ASSIGNMENTS LIVED | Equivalent by construction (Gremlins maps `%=` to `%=`): record |

### The answer, in words

"Every package stays in scope, handlers and repository included: leaving one out is an exclusion only you can approve, so I listed `internal/repository/pg/` as pending with its reason; until you decide, the release run reports INVALID. Weekly scheduled runs are fine (more often than the monthly default); they report only, on code changed since the last release. The release run covers everything and blocks publication. The target is 100%: each mutant is killed by a test or recorded with its reason; no lower percentage target. Not run: this setup was checked by the validator only."
