# Collaborative Specification and Living Documentation

Deeper content behind three of `SKILL.md`'s pointers: the checkable definition-of-ready for a scenario headed into automation, what "living documentation" actually requires beyond running in CI, and how to keep a growing Scenario Outline honest. Grounded in `research/testing/specification-by-example-adzic.md` (Gojko Adzic) and `research/testing/agile-testing-crispin-gregory.md` (Crispin & Gregory).

## Specification Workshop — Definition of Ready

`SKILL.md`'s "Where Feature Files Come From" section names the expectation: examples should come from a **Three Amigos** session — business, development, and testing perspectives deriving concrete examples together, before Gherkin is finalised. That naming gap was found by `agile-testing-crispin-gregory.md` (the skill's Given/When/Then discipline already realises the book's Q2, business-facing-supporting-the-team philosophy, but never states *who* is in the room). Gojko Adzic's **Specification Workshop** gives the same expectation a concrete, checkable shape — a short, focused session, timeboxed, with the facilitator keeping the conversation anchored to concrete examples rather than abstract rule debates (the same discipline `example-mapping`'s red/blue/green cards already enforce in this repo's own vocabulary — no new procedure to invent, just make the expectation nameable).

A specification is ready to leave the workshop and become an automated scenario once it satisfies three checkable criteria:

1. **Business language only.** No UI mechanics, no HTTP verbs, no database columns — the same declarative discipline `SKILL.md`'s Ubiquitous Language in Steps section already enforces (`she classifies "Q3 Report" as "Confidential"`, not `she sends a PATCH to /v1/data-assets/{id}/classification`). If a workshop participant can't state the example without naming an implementation detail, the example isn't ready.
2. **Traceable to a single rule.** Each example illustrates exactly one business rule. An example that's doing double duty for two rules at once is a sign the rules themselves haven't been teased apart yet — split the example, or split the rule.
3. **Explicit team agreement.** Not "someone wrote it down" but the people present — playing the business, development, and testing perspectives, even when a single agent plays more than one role because no live multi-role team exists — have actively confirmed the example represents the intended behaviour.

"We can't produce a real example" is itself a readiness signal — the same one `example-mapping` and Pugh's ATDD both already use: a feature with no derivable example isn't ready to leave Ideate, and a rule with no example isn't ready to become a Scenario.

## Living Documentation — The Full Definition

`SKILL.md`'s Living Documentation section names the half most teams stop at: feature files live in the repo, run in CI, and can't quietly drift because a stale scenario fails the build. That's necessary — but Adzic's actual definition of *living documentation* requires a second half this repo's skill has never named: the validated result must be mechanically rendered back to the team as a **readable documentation artifact**, typically an auto-generated report or site built from the executed spec suite, so that "documentation a PM can read" means a generated artifact produced from real, current test results — not a raw `.feature` file browsed in a repo viewer.

The distinction matters because the two halves fail independently. A suite that runs in CI but produces no readable output satisfies "current because tested" while still leaving Shafi (or any non-engineer reader) to open `.feature` files in a code browser to find out what the system actually does — which works, but isn't the payoff Adzic's practice is named for. A suite with a generated report but no CI enforcement would be worse: a beautifully rendered artifact describing behaviour nobody verified is still-born documentation, just prettier.

This repo already names `godog` as its Go BDD runner (`SKILL.md`'s Binding Steps to Automation section). Whether godog's own reporting output — or a lightweight equivalent — is sufficient to satisfy this bar, versus requiring an additional report-generation step, is a build-time decision for whoever implements this: check godog's actual reporter capabilities against the requirement (a browsable artifact grouping scenarios by feature, showing pass/fail status and last-verified date) before choosing a tool. The requirement is the artifact's existence and provenance (generated from execution results), not any specific tool.

## Key Examples — Minimality, Not Just Breadth

`SKILL.md`'s Golden Triangle answers *which angles* a feature must cover — happy, negative, edge. It says nothing about *how many examples per angle* is enough, and nothing catches a Scenario Outline's Examples table growing past what's actually useful. Adzic's **Key Examples** principle fills exactly that gap: a good specification illustrates a business rule with the *smallest* set of examples that fully pins the rule down, not one row per plausible input combination.

The practical test: for any row in an Examples table, ask whether removing it would change what the rule is proven to do. If the table would prove exactly the same thing without that row, the row is redundant — delete it. A table that keeps growing with near-identical rows is a symptom, not a virtue; it usually means either the rule is over-specified (the same distinction is being tested many times with no new information each time), or several genuinely *different* rules have been conflated into one table and need to be pulled apart into separate outlines.

This is explicitly an economy principle, not a completeness principle, and it is not in tension with formal combinatorial coverage techniques (decision tables, full condition enumeration) that ask a different question — has every condition combination been enumerated. A table can be both complete and minimal at once; Key Examples is about not paying for redundant rows that don't teach the reader anything the surviving rows don't already teach. Apply the prune test both when first writing a Scenario Outline and periodically as a feature's rules evolve — a table that was minimal at launch can accrete redundant rows over time just as easily as it can accrete legitimately new ones.
