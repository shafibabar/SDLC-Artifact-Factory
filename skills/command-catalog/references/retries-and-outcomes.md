# Retries, Idempotency, Concurrency and the Reply

The detail behind `SKILL.md` § 5–6. Grounded in Evans (separating commands from side-effect-free queries) and Vernon (optimistic concurrency on the Aggregate), as summarised in `research/domain-driven-design/domain-driven-design-evans.md` and `research/domain-driven-design/implementing-ddd-vernon.md`. The Go that implements it is `go-service-layer`.

## 1. Why every Command needs an idempotency rule

A Command crosses a network. The caller times out and retries without knowing whether the first attempt applied; a gateway or load balancer replays; a Policy's triggering event is delivered **at least once**. Without a rule, a retry applies the change twice: two refunds, two seats, two emails.

## 2. Choosing the key

| Issuer | Key | Why |
|---|---|---|
| A person through a client | A request ID the client creates **once per intent** and sends with every retry of it | The server cannot tell a retry from a new request; only the client knows they are the same intent |
| A Policy | The triggering event's ID (plus the Command's name, if one event triggers several Commands) | A redelivered event carries the same ID |
| A schedule | The schedule's name and the period it runs for ("nightly-fees 2026-11-06") | A re-run for the same period is the same intent |
| A natural business key | When the language already has one ("one capture per authorisation") | State it; it doubles as a rule |

A key generated by the server for each request makes every retry a new Command. A key reused for a **different** intent (same key, different inputs) is a caller error: reject it as invalid input rather than replay an answer to a question that was not asked.

## 3. What a duplicate gets

- **The first outcome, exactly:** the same success and identifiers, or the same rejection. Running the Command again instead is wrong both ways: a retry of a success would apply twice, and a retry of a rejection could succeed because state moved, giving one request two answers.
- **Nothing changes and nothing new is recorded.**
- **The dedupe record commits with the state change, in the same store and transaction.** If the change commits and the record does not, a retry applies twice; if they are in different stores, a failover can leave one without the other.
- **Two copies arriving at once:** exactly one applies. The store's uniqueness on the key decides the winner, and the loser returns the winner's outcome.

## 4. How long keys are kept

At least the longest time a retry can still arrive: the client's retry policy, a queued mobile request coming back online, a Policy's redelivery window, and a regional failover. A key dropped earlier lets a late retry through as new. State the window per Command, or once for the catalog when they are all the same.

## 5. A repeat with a new key

Different from a duplicate: a **new** request whose effect is already in place (cancel a booking that is already cancelled). Decide per Command and record it:

| Choice | Use when | Records an event? |
|---|---|---|
| Succeed, change nothing | The caller's goal is met; telling them "no" helps nobody (a second "mark as read") | No |
| Reject as *rule violated* | The repeat signals a misunderstanding the person should see (a second refund request on a refunded order) | No |

## 6. External effects

When the Aggregate's change goes with a call to an outside system (a payment provider, a carrier), pass the **same idempotency key downstream**, so a retry after a failover does not charge or ship twice. Record in the catalog which Commands have an external effect and that the key is passed on. How the call is made safe (an outbox, a process) is `event-driven-patterns`'.

## 7. Concurrency

The actor decided based on what they saw. If the target changed since, applying the Command may no longer be what they meant.

| Choice | Record as | Use when |
|---|---|---|
| The Command carries the version the actor saw; a mismatch is rejected | `conflict — actor reloads and decides again` | Acting on stale information would break the intent (approving a claim whose amount changed) |
| Re-check the rules against the current state and apply | `none needed — the rules are re-checked on the current state` | The rule, not the actor's view, is what matters (adding an item to a basket) |

How versions are stored is `aggregate-design` § 4 and the go-* skills'.

## 8. The reply

- **An acknowledgement and identifiers** (the new Aggregate's identity, the event's ID), not the changed state. Evans: a method that changes state should not also be the way to read it. Callers read a Read Model, so the read side can be shaped and scaled on its own.
- **Outcome now or later:** record whether the caller needs to know the outcome before continuing (a person waiting at a till) or can learn it from an event or a Read Model (an import). `api-contract-design` turns this into a synchronous or an accepted-then-poll response.
